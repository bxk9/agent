# Data Process 模块详细文档

## 1. 模块概述

### 1.1 模块职责
Data Process 模块负责Prompt工程相关功能，包括：
- **Prompt模板定义**：定义路由分类的完整Prompt
- **分类标准制定**：定义四个维度的分类标准和规则
- **示例构建**：提供典型示例帮助模型理解
- **训练数据生成**：支持生成带推理过程的训练数据

### 1.2 文件结构
```
data_process/
├── router_prompt.py           # 标准Prompt模板
├── router_prompt_special.py   # 特殊场景Prompt
├── router_prompt_4token.py    # 4token优化Prompt
├── run_router_data.py         # 训练数据生成脚本
└── run_router_data_with_tool.py  # 带工具的训练数据生成
```

## 2. 核心组件详解

### 2.1 router_prompt.py - 标准Prompt模板

#### 2.1.1 分类标准定义 system_prompt_core

这是Prompt的核心部分，定义了四个维度的分类标准。

**一、工具调用类型**

```python
system_prompt_core = """
# 分类标准
## 一、工具调用类型
1. multi：（多工具调用）用户任务包含多个子任务，需要调用多个不同工具才能完成任务。
   - 扩展规则：必须先调用额外的工具完成隐含的前置操作（如要先调用图片问答/问屏截图等）的情况，也属于multi。
   - 扩展规则：对于含single子任务+任意非single子任务（qa/unsupported/pend）的混合query，则整体归为multi。

2. pend：（工具待确定）用户诉求方向本身不明确，或该指令有多个相似候选工具可以选择，导致无法判断要执行什么任务、应调用哪个工具，需要先跟用户澄清"要做什么"。
   - 排除规则：若能明确该调用哪个候选工具，只是参数问题（参数不足或需要推理），则不属于pend。
   - 排除规则（播放类默认锚定）：仅针对播放类任务，"播放XX"（如"播放匆匆那年""播放活着"，同名内容可能是音乐/小说/影视等），虽然play_music/play_broadcast/play_video等多个工具字面均可承接，但用户的诉求对象（作品名XX）本身是明确的，"选哪个媒介/app"只是下游路由问题，不属于"要做什么"层面的歧义，无需向用户澄清，应默认锚定播放类工具，判single而非pend。

3. unsupported：（工具不支持）用户query是明确的任务指令，但当前候选工具中没有能够支持该任务的工具（无工具匹配）。或者能匹配到相关工具，但该任务的具体要求超出了工具的功能定义和参数支持范围（超出工具能力）。
   - 扩展规则：任务内容严重违反道德习俗、社会价值观或社会秩序，也属于unsupported。
   - 排除规则：若明确可匹配对应的候选工具，且未超出工具能力范围，仅参数不足/需要推理，则不属于unsupported。

4. single：（单工具调用）只需要调用单个候选工具，即可完成任务。
   - 扩展规则：只需要多次调用同一个工具的情况，也属于single。
   - 扩展规则（常识消歧）：当query的动作+对象齐全，对象虽为口语化/简略表述、字面看似存在多种解释，但结合用户习惯与生活常识存在唯一高概率指向时，应按该高概率意图锁定对应候选工具，属single，无需向用户澄清。如"打开灯光"（指控制IoT房间灯）、"打开遥控"（指打开遥控器页面/功能）、"打开镜子"（指手机镜子功能）。
   - 扩展规则：当query形如"打开/用XX应用+具体任务"，若该任务对应的候选工具自身已有app_name 参数可接收该应用名称（如多媒体类的play_music/play_video，导航类等），则"打开XX"仅作为该工具的app_name参数填充，不视作独立的open_app子任务，整体判single（而非multi）。
   - 排除规则：请严格按照当前可用的工具定义的范围和边界来判断，若用户要求超出工具能力或无候选工具匹配，则应判为unsupported（而非single）。

5. qa：（知识问答）用户提出涵盖生活娱乐、文化教育、医疗健康、时事财经、自然科学、人文社科、电子科技、学科数理等各领域的知识性问题，可使用knowledgeQA工具，基于自有知识和在线搜索能力回答。
   - 扩展规则：手机等电子产品的相关咨询与指导（问题排查、使用教程、参数功能咨询等），也属于qa。
   - 扩展规则：以任务形式要求输出特定内容的场景，包括文本创作/邮件起草/文本翻译/内容总结/改写扩写/代码编写等，也属于qa。
   - 扩展规则：若query中包含多个子任务，且所有子任务均为问答类（不涉及任何single/unsupported/pend类工具调用子任务），则整体归为qa。
   - 排除规则：若用户询问的对象是自己或身边人/事物（家人/伴侣/朋友/宠物/工作/偏好/经历等）的私人信息，无需也无法通过任何工具回答（不在公开知识库、不在搜索能力范围、也不属于手机功能/系统操作），则归为chat而非qa。

6. chat：（闲聊）不包含任何明确的功能操作或执行类诉求、纯满足对话交互或情绪价值的场景，也不需要调用工具，主要包括以下类型：
   - 日常交流：围绕日常/兴趣/观点/话题的闲聊交流，以及对话起止（打招呼、告别、呼唤小v、结束对话等），或无明确目的和意义的即兴对话。
   - 小v互动：涉及蓝心小v人设/特质（基础信息、能力范围、爱好特长等）的相关问题，或对小v的正面/负面评价。
   - 娱乐游戏：以互动性、过程参与感为主的游戏场景，包括角色扮演、游戏陪玩（猜谜、成语接龙、讲笑话/讲故事、心理/性格/星座/玄学测试等）。
   - 情感陪伴：情绪宣泄/鼓励/共鸣，或用户纯粹表达主观意见和观点，期望满足情绪价值。
"""
```

**分类要点**：
- **multi**: 多工具调用，包含隐含前置操作
- **pend**: 工具待确定，需要澄清"要做什么"
- **unsupported**: 工具不支持，无匹配或超出能力
- **single**: 单工具调用，包含常识消歧
- **qa**: 知识问答，包含文本创作等
- **chat**: 闲聊，纯对话交互

**二、意图明确度**

```python
"""
## 二、意图明确度
1. clear：（意图清晰）用户诉求方向明确，所有关键参数都已具备（用户明说、上下文可取、或有默认值），无需额外的推理转换或澄清补充。（chat/qa/unsupported场景不依赖精确参数，参数完整性条件自动豁免）
   - 扩展规则：（复合指令完整性）若query包含多个子任务，必须每个子任务均满足clear条件，整体才判clear；任一子任务缺参/模糊，按优先级vague>infer>lack取最高档。

2. lack：（参数信息不足）用户诉求方向明确，但缺少执行所需的关键参数，且无法从上下文中获取，也无法推理得到，必须依赖用户补充澄清。
   - 扩展规则：query中使用代词指代（如他、那里、这个、此等），且上下文中无对应内容可解析（指代不明），导致关键参数缺失，也属于lack。

3. infer：（参数需要推理）用户诉求方向明确，但给的关键参数无法直接使用、或未显式提供，需经过【一次推理转换】才能得到可用值。
   - 扩展规则：query中的实体是抽象/别名/约定俗成表达，需查常识或在线搜索得到具体可用值。如「节日/节气名→具体日期」、「地标别名/最高/最大的XX→正式名称与地址」、「某作者最新作品→具体名称」。
   - 扩展规则：query中涉及抽象场景化描述：用户用主观/场景化语言描述参数（"看电影合适的音量"、"护眼亮度"、"老人看得清的字体"），需基于常识把该场景映射为具体数值或档位。
   - 排除规则：当前query存在代词指代 history 中的内容参数，但无需转换可直接使用，则属 clear，不属 infer。
   - 判定锚点：缺的参数是否需要【常识/检索/系统数据/场景映射】中的至少一项做转换？需要→infer；不需要、但必须问用户→lack；已直接可用→clear。

4. vague：（意图模糊）用户诉求方向不明，或意图模糊，或指向不明，或表述宽泛，导致无法判断用户要做什么，必须先跟用户澄清"要做什么"才能继续。
   - 扩展规则：用户输入只包含单个实体对象（人名/地名/景点/影视剧/作品/时间等）、纯代词、纯感叹词，没有任何动作，也无法从上下文中获得动作信息，属于vague。
   - 扩展规则：用户只给了通用动作（打开/调整/关闭/清理等），却没有操作对象，且无法从上下文中获得对应操作对象，属于vague。
   - 扩展规则：用户给了完整动宾结构（有动作+对象，如买个票、查订单），但能同时匹配到多个相似候选工具，具体方向不明，必须跟用户澄清，也属于vague。
   - 排除规则（省略式属性查询）：若query由"实体+可量化/可查询的属性名词"构成（典型如"电池容量""深圳气温""手机温度""今日汇率""北京人口"），虽省略了"是多少/怎么样/查一下"等提问表述，但该属性名词本身已隐含唯一明确的查询诉求，且能直接映射到对应候选工具（手机状态/天气查询/在线搜索等），意图清晰，应按对应工具判single（或qa），意图明确度判clear，不属于vague。判定锚点：该名词短语是否指向一个可被某工具直接返回的确定属性值？是→clear；否（仅是孤立实体/代词，无可查询属性）→vague。
   - 排除规则（常识消歧优先）：若query的动作和对象均已具备，仅因对象表述简略/口语化而字面可能多义，但依据用户习惯与生活常识存在唯一压倒性的高概率解释，则视为意图清晰，按该解释判clear（对应工具调用类型判single），不应过度澄清而判vague。判定锚点：抛开字面歧义，是否存在一个大众默认、无需反问即可确定的主流意图？存在→clear；多个解释概率相当、无主流默认→vague。
"""
```

**分类要点**：
- **clear**: 参数完整，无需推理或澄清
- **lack**: 参数不足，必须问用户
- **infer**: 参数需推理转换
- **vague**: 意图模糊，需澄清"要做什么"

**优���级规则**：`vague > infer > lack > clear`

**三、指令类型**

```python
"""
## 三、指令类型
1. cond：（条件指令）query中包含触发条件 + 条件满足时执行的任务，且该条件需由外部调度器/监听器在满足时才能触发执行。
   - 判定原则：cond只看指令性质（是否需外部调度器/监听器触发），与触发条件的具体值是否给全无关。用户表达了定时/延时/事件触发诉求、但未给具体时点/阈值时，指令类型仍判cond，缺失的具体值归入意图明确度维度判lack。如"定时打开音乐"（未给时间）→ 指令类型cond、意图明确度lack。
   - 触发条件类型：
     · 时间条件：指定时间（每天上午9点）、相对时间（半小时后）、日出/日落相关（日出前15分钟）。
     · 地理位置条件：到达/离开指定位置（到达公司时、离开家时）。
     · 手机状态条件：飞行模式开关、WLAN/蓝牙连接或断开、耳机插拔、充电状态、NFC开关。
     · 应用状态条件：打开/关闭/前台运行某应用。
   - 扩展规则：（相对延迟时间触发）若query用"X分钟/小时后""日出/日落后"等相对延迟时间作为触发条件，且其后任务对应的候选工具自身不接收延时/定时执行参数（如关闭网络、关闭热点、打电话等即时执行类工具），则该延迟需由外部调度器到点后触发，属于cond。例如"10分钟后关闭网络/蓝牙""一小时后打电话/发信息给xx"。
   - 扩展规则：（外部事件触发）若触发条件是某个无法预知具体时点、需持续监测外部世界/信息流才能确认发生的事件（如"看到XX新闻/消息时""XX球队夺冠时""股价跌破X时""下雨时"），其后跟随待执行任务（如提醒/通知/发消息），则需由外部监听器在事件发生时触发，属于cond。例如"以后看到C罗新闻提醒我""中国羽毛球队夺冠的时候提醒我"。
   - 扩展规则：（上一轮条件指令的补充）若上一轮已给出触发条件但未明确待执行任务（模型正就"条件满足时做什么"进行追问），本轮query补充了该条件下要执行的具体任务，则本轮与上一轮共同构成完整的"条件触发+待执行任务"结构，本轮指令同样属于cond。
   - 排除规则：（无任务条件）query中虽然包含条件表述，但条件后并未跟随明确的工具调用类任务（仅是情绪/观点/陈述等），不属于cond。
   - 排除规则：（工具自带条件参数，优先级高于上方"相对延迟时间触发"扩展规则）若候选工具本身就以"时间/时长/触发条件"作为其原生输入参数（即工具被设计为接收并自行处理该条件），则用户提到的时间/条件只是该工具的常规参数填充，则不属于cond。如"定一个10分钟后的闹钟""设置1小时后的提醒""半小时后关闭手机"，闹钟类/提醒类/定时开关机工具原生支持定时参数，属norm。

2. norm：（普通指令）除条件指令外的所有情况都属于普通指令。
"""
```

**分类要点**：
- **cond**: 需要外部调度器/监听器触发的条件指令
- **norm**: 普通指令

**四、执行反馈状态**

```python
"""
## 四、执行反馈状态
1. abnormal：（异常反馈）多轮对话中，用户对模型在历史对话中的【理解、调用或执行】表现出不满或纠正，本质是"错源在模型"。包括但不限于：用户对模型上一轮结果的主观否定/质疑/抱怨，或对模型的工具选择有误、参数理解有误、执行结果未达预期、回复事实有误等情况进行明确的澄清/纠正/补救。
   - 扩展规则（包含范围，覆盖到任一项即属 abnormal，不要求 history 必须为完成态回复）：
     * 主观否定信号：用户对上一轮结果直接表达不满或质疑（口头禅参考："不对/错了/不是这个/你听错了/你确定吗/不够好"）。
     * 参数纠正型：用户用"是 X，不是 Y"、"改成 Z"、"X 错了"、"搞错了/想错了，是 X"等表达，显式给出正确参数；或指出模型选错了工具/对象（如"是打开摄像头，不是相册"）。
     * 执行未达预期：用户指出模型声称已完成的事实未生效，或效果不佳（参考："还没X/没成功/没生效"、"看不清/听不清"、"太大/太小/太长/太短"）。
     * 事实错误纠正：用户指出模型上一轮回复的知识/查询/结论有误（参考："X我记得不在Y地"、"应该是X"、"X不对吧"）。
   - 排除规则（精度兜底，命中任一项即属 ok 而非 abnormal）：
     * 用户侧错误：错误源头在用户自身（说错、改主意、临时换内容、补充新约束），即使带"不对/错了/不是…"等语气词也仍属 ok。
     * 用户自行变更：用户主动修改/取消/删除/切换已设置的内容（如"不用了"、"算了吧"、"换下一首"、"改到三点"），未指出模型上一轮"错"。
     * 任务正常推进：用户回应模型追问/补充参数（模型问"几点"答"早上9点"）；创作类任务持续优化迭代未表达不满（"再瘦一点"、"换3D卡通"）；重发同一指令或发起独立新任务，与上一轮无纠错关联。
   - 判定锚点：用户的不满或纠正是否针对【模型刚才的理解或执行偏差】？是→abnormal；否（错源在用户/无错源/独立新任务）→ok。

2. ok：（正常推进）除异常反馈外的所有情况均属于正常推进，包括但不限于：首轮对话、正常任务延续、响应模型追问的参数补充、用户自行变更、新话题发起等。
"""
```

**分类要点**：
- **abnormal**: 错源在模型的异常反馈
- **ok**: 正常推进

**判定锚点**：错源是否在模型？

#### 2.1.2 处理规则

```python
system_prompt_base = ("""你是一个手机用户的query意图拆解专家。你的任务是根据手机用户的当前query和历史对话，结合候选工具定义，从下面四个维度对用户当前query的意图进行分类。
"""
    + system_prompt_core
    + """
# 处理规则
1. 默认值规则：若工具定义中注明了某参数有默认值（如位置默认当前位置、日期默认今天、时间默认当前时间），用户未提供该参数时，使用默认值，视为clear，而不是lack或infer。
2. 工具调用类型优先级：若在工具调用类型的分类维度中，有多个标签符合定义，请严格按优先级判定：multi > pend > unsupported > single > qa > chat，输出优先级最高的那个。
3. 意图明确度优先级：若在意图明确度的分类维度中，有多个标签符合定义，请严格按优先级判定：vague > infer > lack > clear，输出优先级最高的那个。
4. 意图明确度强绑定：工具调用类型 ∈ {chat, qa, unsupported} → 强绑定clear；工具调用类型 = pend → 强绑定vague。
"""
)
```

**核心规则**：
1. **默认值规则**：工具定义的默认值视为已提供
2. **优先级规则**：按优先级选择最高档标签
3. **强绑定规则**：特定工具类型强绑定意图明确度

#### 2.1.3 输出格式定义

def generate_training_data(excel_path, output_path):
    """从Excel生成训练数据"""
    df = pd.read_excel(excel_path)
    
    training_data = []
    for _, row in df.iterrows():
        query = row['query']
        history = row['history']
        label = row['label']
        
        # 构建训练样本
        sample = {
            "query": query,

            "label": label
        }
        training_data.append(sample)

## 4. Prompt工程最佳实践

### 4.1 分类标准设计原则

1. **互斥性**：每个标签的定义应该互斥，避免歧义
2. **完备性**：覆盖所有可能的场景
3. **优先级明确**：当多个标签符合时，有明确的优先级规则
4. **扩展规则**：针对边界情况提供扩展规则
5. **排除规则**：明确哪些情况不属于该标签

### 4.2 示例设计原则

1. **典型性**：覆盖常见场景
2. **对比性**：提供对比示例（如Case 5 vs Case 6）
3. **边界性**：覆盖边界情况
4. **多样性**：覆盖不同维度的组合

### 4.3 输出格式设计

1. **简洁性**：输出格式尽可能简洁
2. **可解析性**：便于程序解析
3. **确定性**：输出格式严格约束
4. **兼容性**：支持多种���出格式（带/不带推理）

## 5. 设计理念总结

### 5.1 多维度分类

- 支持跨维度绑定规则

- 明确的分类标准和规则
- 优先级规则解决冲突

## 7. 常见问题

### 7.1 分类不准确
**现象**：模型输出的标签与预期不符

**原因**：
1. Prompt描述不够清晰
2. 示例覆盖不全
3. 规则存在歧义

**解决方案**：
1. 优化分类标准描述
2. 增加更多示例
3. 明确优先级规则

### 7.2 输出格式错误
**现象**：模型输出不符合要求的格式

**原因**：
1. 输出约束不够严格
2. 模型理解偏差

**解决方案**：
1. 加强输出格式约束
2. 添加更多格式示例
3. 使用后处理校验

### 7.3 推理过程不一致
**现象**：带推理的输出中reason与label不匹配

**原因**：
1. 推理引导不够明确
2. 字段顺序约束不严格

**解决方案**：
1. 强化推理引导
2. 明确字段顺序约束
3. 添加推理示例

## 8. 最佳实践

1. **定期审查**：定期审查分类标准，确保覆盖新场景
2. **示例更新**：根据实际case更新示例库
3. **A/B测试**：新Prompt上线前进行A/B测试
4. **效果监控**：监控分类准确率，及时发现问题
5. **版本管理**：Prompt版本化管理，便于回滚
6. **文档同步**：Prompt修改时同步更新文档

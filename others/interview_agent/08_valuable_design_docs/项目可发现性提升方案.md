# 项目可发现性提升方案

> **目标**：让 AI 助手和开发者更快定位问题代码
> **版本**：v1
> **日期**：2026-07-17

---

## 一、现状诊断

### 1.1 已有优势 ✅

| 层面 | 现状 | 效果 |
|------|------|------|
| **ARCHITECTURE.md** | ~8600 tokens，症状→模块→函数名索引 | 两次定位问题都靠它快速找到入口 |
| **文件级 docstring** | 所有核心 `.py` 文件开头有清晰模块说明 | `grep` 命中后能立即判断是否找对文件 |
| **`__init__.py` 包说明** | `resume_sidebar/`、`resume_docx/`、`vfs/`、`skills/` 等子包都有职责说明 | 目录级导航有效 |
| **`grep` 友好** | 函数名唯一、模块 docstring 含关键名词 | 搜索效率高 |

### 1.2 当前瓶颈（两次实际定位问题的耗时分析）

| 问题 | 定位耗时 | 瓶颈 | 根因 |
|------|---------|------|------|
| "字节元宝" query 从哪来 | ~3 分钟 | 需要 3 次 `grep` 逐层追踪 | 缺少调用链文档，不知道 Agent→tool 的参数是 LLM 生成的还是代码写死的 |
| `resume.docx` 命名不规范 | ~5 分钟 | 需要对比两条路径的差异 | 独立工具和主管道用不同的 file_id 格式、不同的命名逻辑，没有文档说明差异 |

**核心矛盾**：ARCHITECTURE.md 有"模块职责速查"和"症状速查表"，但缺少"数据/参数从哪来、到哪去"的**纵向调用链**。每次定位问题都需要手动追踪 3-5 层函数调用。

## 二、方案设计

### 2.1 核心思路：三层可发现性体系

```
第一层：调用链速查（纵向）
  └─ "这个函数被谁调用？参数是谁传的？数据最终落到哪个 VFS 路径？"
     已实现 → ARCHITECTURE.md §二（10 条调用链）

第二层：日志注入（横向）
  └─ "运行时这个参数到底是什么值？哪一步失败了？"
     待实现 → 关键节点增加结构化日志

第三层：文件级索引（静态）
  └─ "这个文件是干什么的？依赖谁？被谁依赖？"
     部分已有 → 扩展 docstring + 目录 README
```

### 2.2 第一层：调用链速查（✅ 已完成）

**文件**：`ARCHITECTURE.md §二、关键调用链速查`

已覆盖 10 条调用链：

| 链 | 覆盖范围 | 解决的核心问题 |
|----|---------|--------------|
| 链 1 | 搜索 → 面试题/JD/公司信息 | Agent 生成的 query 从哪来（prompt vs 代码） |
| 链 2 | 生成简历（主管道） | 9 步完整流程，每步对应文件+函数 |
| 链 3 | 独立 Word 工具（废弃路径） | 与链 2 的 4 个关键差异（文件名/file_id/company/LLM提取） |
| 链 4 | 文件命名与版本管理 | base_name 拼接规则、file_id 两种格式对比 |
| 链 5 | AI 标记 `<<<...>>>` 全生命周期 | 生成→渲染→持久化→隔离 完整链路 |
| 链 6 | 历史简历查询与版本选取 | 三级命中逻辑、分组视图 |
| 链 7 | 素材库（Master Profile） | 事实源可信度闸门、verified 过滤 |
| 链 8 | 文档格式调整（远端 Agent） | 路由规则：改意思 vs 改样子 |
| 链 9 | 语音面试 | WebSocket→vivo/chat/stream→ASR/LLM/TTS |
| 链 10 | 错题本与复习 | 入册→检索→艾宾浩斯复习→复盘报告 |

每条链附带：
- ASCII 调用树（显示函数调用层级）
- 关键差异标注（⚠ 标记陷阱点）
- 定位速查表（症状 → 查哪个文件/函数）

### 2.3 第二层：日志注入（待实施）

> **原则**：不在每个函数里加 log，只在"数据跨越模块边界"的关键节点加。

#### 建议增加的日志点位

| 节点 | 文件 | 注入位置 | 日志内容 | 解决的问题 |
|------|------|---------|---------|-----------|
| Agent 调用 smart_search | `interview_search.py:182` | 已有 `_ctx_log` | ✅ 已有 query/scene/extra | — |
| 简历渲染入口 | `pipeline.py:804` | 函数入口 | `company`、`template`、`export_format` 参数值 | 定位"为什么文件名缺公司字段" |
| 文件命名生成 | `pipeline.py:483` | `base_name` 拼接后 | `name_slug`、`company_slug`、`job_slug`、`_ver`、`ts` 各段值 | 定位"版本号为什么是 v1" |
| VFS 上传 | `pipeline.py:541` | 上传前 | 完整 `vfs_path`（含 file_id） | 定位"为什么路径格式不对" |
| AI 标记持久化 | `ai_marks_store.py` | `add_marks` 入口 | `user_id`、`person_id`、标记数量 | 定位"标记跨轮丢失" |
| 独立 Word 工具 | `_tool.py:153` | 上传前 | 完整 `vfs_path` + 标注"⚠ 独立工具路径" | 快速发现 Agent 误调了独立工具 |

#### 日志格式建议

```python
# 统一格式：模块前缀 + 键值对 + 关键差异标注
logger.info("[resume_pipeline] base_name=%s ver=%s company=%s", base_name, _ver, company)
logger.info("[resume_pipeline] vfs_path=%s file_id_fmt=%s", vfs_path, "hex8" if len(file_id)==8 else "ts_uuid")
```

## 四、效果预期

| 场景 | 当前耗时 | 预期耗时 | 改善方式 |

## 五、维护约定

1. **新增工具/模块时**：必须在 ARCHITECTURE.md §二 增加对应调用链
2. **修改调用关系时**：同步更新调用链中的函数名和文件引用
3. **发现新的常见问题**：补充到 §四"症状速查表"
4. **日志格式**：统一 `[模块名] key=value` 格式，便于 `grep` 过滤

# 简历 Prompt 优化方案：规则去重与可维护性提升（终版）

> 日期：2026-08-01  
> 背景：基于"局部优化场景自我评价被改写且位置异常"事故的深度分析  
> 涉及文件：`app/skills/resume_opt_head.md`、`app/skills/resume_generator.md`、`app/skills/_system_prompt.md`  
> 版本：v2.0（融合两轮审核意见后的最终方案）

---

## 1. 背景与问题

### 1.1 事故暴露的深层问题

2026-08-01 发生的"局部优化场景自我评价被改写且位置异常"事故，表面原因是 Agent 漏传 `scope`、`preserve_order` 等参数，但深层原因揭示了一个更根本的问题：

**即使 Prompt 层已经有完整规则 + 集中 checklist，LLM 在真实生成阶段仍可能不执行自检就直接调用工具。**

事故中最有力的证据：
- `resume_opt_head.md` L578-594 已有完整的 7 项自检清单
- 清单中明确列出 `scope`、`preserve_order`、`template` 等参数
- **但 LLM 依然漏传了这些参数**

这说明：**Prompt 规则已经足够充分，问题出在 LLM 遵从性和框架层防护不足**。

### 1.2 Prompt 规模与信息密度

当前简历相关 prompt 的规模统计：

| 文件 | 行数 | 角色 |
|------|------|------|
| `_system_prompt.md` | ~297 | 系统级 SOP + 工具纪律 |
| `resume_opt_head.md` | 1164 | 简历优化技能 |
| `resume_generator.md` | 963 | 简历生成技能 |
| **合计** | **~2424** | LLM 需要"记住"的全部规则 |

**问题**：LLM 需要在生成工具调用时"记住"所有规则，但注意力被前文的改写任务消耗，导致"知道规则但执行时遗漏"。

## 2. 核心问题诊断

### 2.1 规则重复率约 17%（按行数）

两个 skill prompt 存在大量近乎逐字重复的内容：

| 重复内容 | 估计行数 | 影响 |
|---------|---------|------|
| `<<<...>>>` AI 标记规则（含数字溯源、句内局部标记、多数字逐个标记） | ~150 行 | 每次修订需改两处，易漂移 |
| MECE 跨模块去重映射表 | ~30 行 | 同上 |
| 强动词参考表 | ~15 行 | 同上 |
| 量化锚点参考表 | ~20 行 | 同上 |
| 项目话术模板（技术/业务/研究三类公式） | ~80 行 | 同上 |
| 实事求是原则（参与度/熟练度/职级不得拔高） | ~60 行 | 同上 |
| 导出拦截规则（先查历史再渲染） | ~30 行 | 同上 |
| 模板选择规则（颜色/风格映射表） | ~40 行 | 同上 |
| **合计** | **~425 行** | |

**重复率**：425 / 2424 ≈ **17.5%**（按行数计算）

**风险**：任何一次规则修订都需要同步改两个文件，一旦漏改就会出现两个 skill 行为不一致。

**注意**：上述 8 类规则并非全部适合抽取——部分规则在两个 skill 中存在语义差异（详见第 4.2.3 节差异化分析）。

### 2.2 同一规则在单文件内多次重复

以 `resume_opt_head.md` 为例：
- `<<<...>>>` 标记规则在契约第 3 条、改写底层原则、Step 7 导出步骤中各写一遍
- `preserve_order` 规则在契约、Step 7、自检清单中各写一遍
- `template="rebuilt"` 规则在契约、Step 1、Step 7、决策树中各写一遍

**问题**：LLM 注意力被重复内容分散，反而容易遗漏关键细节。

### 2.3 自检机制不统一

| 文件 | 自检范式 | 交互方式 |
|------|---------|---------|
| `resume_opt_head.md` L578-594 | 打勾清单型 | "逐项确认，缺一不可" |
| `resume_generator.md` Step 3.5/3.7 | 逐条扫描输出型 | "必须作为对话回复输出给用户看" |

两种自检范式并存，增加 LLM 的执行负担。

### 2.4 信息密度过载导致"知道规则但执行时遗漏"

`preserve_order`、`scope`、`rebuilt` 等关键参数规则分散在不同位置：
- `_system_prompt.md` L201, L205, L227, L232, L236, L240, L246
- `resume_opt_head.md` L188-222, L634, L671-674, L691-703

LLM 在生成 `render_sidebar_resume` 调用参数时，注意力已被前文的改写任务消耗，导致"知道规则但执行时遗漏"。

### 2.5 Prompt 规则与框架层正则形成第二份重复（新发现）

`agent_executor.py` 中 `scope` 自动检测的关键词映射（`_specific_patterns`、强/弱触发词正则）明确标注"复刻自 `resume_opt_head.md` L188-194/221"。这意味着：

- Prompt 里的局部优化判定规则和框架层正则判定规则是**两份独立维护的逻辑**
- 若 Prompt 后续新增新句式，框架层正则不会自动同步
- 这恰好是"改一处忘一处"问题的**同构复现**

## 4. 最终实施方案

### 4.1 阶段一：低成本验证（1-2 周，推荐立即启动）

> 在投入架构重构前，先执行一轮低成本验证，建立基线并观察效果。

#### 步骤 0：建立基线指标

通过框架层日志统计当前状态：

| 指标 | 统计方式 | 用途 |
|------|---------|------|
| `scope` 漏传率 | 统计 `[参数自动补全] scope=` 日志频次 / 总会话数 | 衡量 LLM 对 scope 规则的遵从度 |
| `preserve_order` 漏传率 | 统计 `[参数自动补全] preserve_order=` 日志频次 | 同上 |
| `template` 错误率 | 统计 `[template 校验]` 告警日志频次 | 衡量 template 规则遵从度 |
| 事故复发率 | 人工跟踪"非目标模块被改写"类反馈 | 最终效果指标 |

#### 步骤 1：优先级分层标记试点（方案 E 缩小版）

仅在 `resume_opt_head.md` 的自检清单部分试点优先级分层标记：

```markdown
## 工具调用前自检清单（按优先级）

### P0 硬约束（违反 = 任务失败，框架层已兜底但仍需自检）
- [ ] `scope` 参数：局部优化时是否已传？
- [ ] `preserve_order` 参数：有文件上传时是否已传？
- [ ] `base_resume_json` 参数：scope 存在时是否已传？

### P1 重要约束（强烈建议遵守）
- [ ] `template` 参数：有文件上传时是否为 "rebuilt"？
- [ ] `resume_content` 格式：是否为合法 JSON？
```

#### 步骤 2：建立 Prompt-框架层同步机制

在 `agent_executor.py` 的 scope 正则代码块中添加醒目注释：

```python
# ── P0 自动补全：scope 局部优化意图检测 + 注入（20260801）──
# ⚠️ 同步要求：以下关键词映射表必须与 resume_opt_head.md L188-194/221 保持同步。
# 修改任一处时，必须同步修改另一处。
# 长期方案：考虑将关键词列表抽成配置常量供两处引用。
```

同时在 `resume_opt_head.md` 对应位置添加反向引用注释。

#### 步骤 3：观察 1-2 周

- 对比基线数据，观察各项漏传率变化
- 记录是否有新的事故类型出现
- 根据观察结果决定是否投入阶段二

### 4.2 阶段二：抽取公共规则（2-3 天，观察期结束后评估启动）

> 解决长期可维护性问题，避免规则漂移。定位为"长期可维护性投资"而非"治本"。

#### 4.2.1 创建公共规则文件

文件路径：`app/skills/_resume_common_rules.md`

**命名约束**：必须使用 `_` 前缀，避免被 `load_skills()` 误扫描为业务 skill（见 `_loader.py` L134）。

#### 4.2.2 差异化分析（实施前必须完成）

在抽取前，必须逐条标注 8 类规则在两个文件中的语义一致性：

| 规则类别 | 一致性判断 | 处理方式 |
|---------|-----------|---------|
| AI 标记规则 `<<<...>>>` | 待核实 | 完全一致 → 抽取；部分一致 → 抽取公共部分 + 各自追加差异 |
| MECE 去重映射表 | 待核实 | 同上 |
| 强动词参考表 | 待核实 | 同上 |
| 量化锚点参考表 | 待核实 | 同上 |
| 项目话术模板 | 待核实 | 同上 |
| 实事求是原则 | 待核实 | 同上 |
| 导出拦截规则 | 待核实 | 同上 |
| 模板选择规则 | **已知不同** | `resume_generator.md` 默认 `random`；`resume_opt_head.md` 优先 `rebuilt`。**不直接抽取**，各自保留 |

**产出物**：差异化分析表（标注"完全一致 / 部分一致 / 仅命名相似实际不同"）

#### 4.2.3 修改加载器

在 `build_system_prompt()` 层面执行 `{{INCLUDE_COMMON_RULES}}` 替换（而非 `_load_skill_from_file()`），原因：

1. `_render_skills_full()` 将 skill body 包在 `<skill name="xxx">` 标签内
2. 如果在 `_load_skill_from_file()` 中替换，公共规则会被包在某个具体 skill 的标签内
3. LLM 可能误认为公共规则只属于那个 skill，而非跨 skill 共享

**替换顺序**（避免二次替换污染）：

```python
def build_system_prompt(skills, tools, *, embed_skill_body=False):

    # 步骤 2：再替换其余占位符（{{PRODUCT_CONTRACT}} 等会被正确替换为实际内容）
    base = _SYSTEM_PROMPT_TEMPLATE

        base = base.replace("{{INCLUDE_COMMON_RULES}}", common_rules)

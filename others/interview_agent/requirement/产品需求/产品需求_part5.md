| **处理逻辑** | 1. **统一存储目录结构**（端侧）：`/蓝心小V/求职档案/{公司名_岗位名}/{文件类型}/{版本时间戳}.{ext}`例：`/蓝心小V/求职档案/字节_抖音电商产品/简历/v3_20260601.pdf`<br>2. **统一命名规范**：`{公司}_{岗位}_{文件类型}_{轮次或版本}_{日期}.{ext}`<br>3. **元数据索引**（轻量数据库 / JSON 索引）：<br>- 主键：文件 ID（uuid）- 字段：路径、类型、关联公司/岗位、关联 JD ID、关联简历版本 ID、关联面试事件 ID、生成时间、最近访问时间、用户标签（收藏/归档）<br>- 与 ⑥ 求职记忆的"求职履历池"共用主键，文件作为履历池下挂的二级资源<br>4. **调用接口**（供其他能力使用）：<br>- `file.save(type, content, meta)` → 落盘 + 写索引<br>- `file.query(公司, 岗位, 类型, 时间窗)` → 返回候选文件列表<br>- `file.load(file_id)` → 读取文件原文 + 元数据<br>- `file.link(file_id_a, file_id_b, relation)` → 建立"简历→录音→复盘"关联<br>5. **跨场景自动调用示例**：<br>- 进入"美团二面模拟" → 自动 `file.query(美团, *, 简历定制版, latest)` 加载最新定制简历 + `file.query(美团, *, 复盘报告, *)` 加载一面复盘- 简历倒查 → 通过 `file.link` 反查"该简历版本关联的面试录音"<br>6. **生命周期管理**：<br>- 默认保留 180 天，超期将内容精简提炼为最新版简历+求职集锦（总结此过程中的优缺点、建议）<br>- 用户标记"已 offer / 已拒"后，整个公司岗位文件夹打包为求职档案<br>7. **隐私与权限**：<br>- 录音原文、简历原文仅端侧存储，云端只保存脱敏元数据索引<br>- 用户可一键导出/清空全部求职文件 |
| **输出** | - **文件 ID**（供能力间引用，不暴露给用户）<br>- **跨场景调用结果**：进入新场景时自动注入相关历史文件<br>- **文件操作回执**：保存成功 / 路径 / 关联关系建立成功 |
| **本期判断** | **本期做**。是 ③⑤⑥ 三个能力共同的基础设施，不做则各能力的产物彼此孤立，"跨场景记忆调用"（阶段四/五）无法落地 |
| **依赖** | 端侧存储 SDK 与索引能力；<br>与 ⑥ 求职记忆的主键对齐；<br>~~跨端文件流转能力（与需求 5 的 PC↔手机互传共用）~~ |

### 4.2 阶段一：简历的"读懂 JD + 看清差距 + 定向生成/改写"

**核心目标**：

实现简历包装子场景的最小可用闭环，成为求职 Skill 的入口单元。所有素材范围限定在用户主动提供（粘贴 JD / 上传简历）或基于公开信息的联网检索，不依赖招聘网站的反爬合作。

**该阶段执行权限**：

仅做本机内的简历文件渲染/另存，不外发简历、不自动投递、不调用三方招聘 App。

**体验 Benchmark（上线标准）**：

- **看得准**：简历每条 bullet 与 JD 的对齐结论给到"匹配 / 漏 / 弱 / 风险"四象限，结论可点回 JD 原文第几条
- **写得对**：生成/改写后的 bullet 保留事实，仅在表述/侧重/用词层面对齐 JD，用户改动幅度 ≤ 30% 即可发出
- **像本人写的**：改写保留用户原稿的语气与节奏，不强行套大词
- **不瞎编**：简历中没有的事实绝不自造（如不存在的奖项、不存在的项目数字）
- **可溯源**：每条生成/改写建议标注依据来源（来自 JD 第几条 / 来自公司画像哪个维度 / 来自哪条样例）
- **不打分**：只输出对齐项与差距项，不给"7 分 / 8 分"这种主观评价
- **可中断**：长流程支持暂停-恢复（≥ 10 分钟编辑会话）
- **~~跨端同步~~**~~：PC 生成结果可一键同步到手机~~

### 4.3 阶段二：面试的"个性化模拟 + 对齐式反馈"

**核心目标**：

把简历包装的产出（定制版简历 + JD + 公司画像）顺势接入面试准备环节。引入面经库联检与个性化组卷，是产品差异化的关键高地。

**与阶段一的关键差异**：

阶段一是"单文档（简历）+ 单 JD"的静态分析；阶段二是"多轮对话 + 实时追问 + 即时反馈"的动态会话，需要 ⑥ 求职记忆作为简历/JD 上下文的注入源，需要**文件管理**调取阶段一的定制版简历。

**体验 Benchmark（上线标准）**：

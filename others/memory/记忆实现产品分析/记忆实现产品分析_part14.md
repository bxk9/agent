这种设计透明易懂：所有记忆都是可编辑的文本，使用 Milvus 等向量数据库对其进行语义检索。OpenClaw 的检索机制混合了基于上下文意义的向量相似度和精确关键词匹配，支持插件扩展（如 Honcho、QMD 等后端）。

虽然 OpenClaw 的记忆机制简单实用，但其缺陷也明显：记忆依赖于上下文窗口（过往对话被压缩存储，语义关联弱化）、检索仅基于语义相似度且缺乏逻辑推理、容量受限于本地存储。OpenClaw 本质上采用了**外部向量索引**方式的记忆（embedding + SQLite/Milvus），属于检索增强生成（RAG）范式。

## 整体流程（以查询天气为例）

### 用户接入

用户在 飞书、钉钉、QQ等平台发送消息："帮我查一下明天的天气，并设置提醒。"（可能还带有附件，例如地点列表等）

### 通道适配器（Channel Adapter）

> 【对接多平台，将原始消息转换为统一 JSON 格式，提取附件引用，屏蔽平台差异。】

消息首先进入通道适配器（Channel Adapter）：

  1. 将不同平台（飞书、钉钉、QQ等）的原始消息统一转换为系统内部统一的 JSON 格式。标准化消息包含平台元数据、用户身份、会话标识、时间戳、纯文本内容等核心字段，确保下游模块无需关心平台差异。
  2. 提取消息中的附件（如图片、文件），并保存或生成引用，供后续工具使用。
  3. 标准化后的消息（包含文本、附件引用、用户标识、会话标识等）发送给Gateway Server。

### 网关服务器（Gateway Server）路由与排队

> 【负责消息鉴权、会话路由与排队；维护 Agent 运行器的心跳，实时更新在线节点列表；按 FIFO 顺序将消息负载均衡分配给健康的运行器实例。】

网关接收到由标准化后的消息，首先执行基础的鉴权与安全审查，验证用户身份及操作权限。

随后，会话路由器（Session Router）根据消息中的用户标识和会话 ID，确定该消息所属的会话。若为全新对话，则创建新的会话记录。

消息被放入对应会话的通道队列（Lane Queue）中。该队列作为会话级别的流量控制层，确保同一会话内的消息严格按照 FIFO 顺序处理，避免并发冲突；同时可支持限流、优先级等策略。

最后，网关从队列中依次取出消息，并根据在线节点列表（registry）中维护的可用 Pi 节点信息，通过负载均衡策略将消息派发给一个合适的 Pi Runtime 实例（即 Agent Runner）进行后续处理。

### Agent运行器（pi-embedded-runner）准备阶段

> 【加载会话历史，动态构建系统提示（整合工具、记忆、附件等），驱动 ReAct 循环（调用 LLM、执行工具、迭代）直至生成最终回复；定期向网关发送心跳。】

当消息从通道队列中被取出后，pi-embedded-runner启动处理流程，依次执行以下步骤：

  1. 加载会话历史。从会话存储（如数据库或缓存）中加载该会话的历史消息记录，构建当前对话上下文。历史记录的存储与检索可能参考 [AGENTS.md](http://AGENTS.md) 中定义的会话配置（如保留策略）以及 [USER.md](http://USER.md) 中的用户标识，确保准确还原交互脉络。
  2. 构建系统提示。动态组装系统提示，整合以下内容：
    - 工具描述：引用 [TOOLS.md](http://TOOLS.md) 中定义的各工具（如天气查询工具、提醒设置工具）的功能、参数和调用方式。
    - 技能说明：引用 [SKILL.md](http://SKILL.md) 中定义的通用能力，例如推理步骤、输出格式约束等，以规范模型行为。
    - 长期记忆：从 [MEMORY.md](http://MEMORY.md) 中提取与用户相关的持久化信息（如偏好、历史事实），实现个性化交互。
    - 附件引用：若消息包含附件（如图片、文件），将附件的元数据（类型、URL、OCR结果等）一并加入上下文，供模型或后续工具使用。
    - 用户偏好：可结合 [USER.md](http://USER.md) 中的配置（如语言偏好、响应风格）微调提示语气。
  3. 模型解析。根据会话配置、任务复杂度或用户偏好，从可用的模型列表中选择最合适的 LLM。
  4. 上下文窗口管理。计算当前上下文的总 token 数（包括历史消息、系统提示、附件元数据等）。若超出所选模型的上下文窗口限制，则自动执行压缩策略：
    - 历史摘要：对早期对话进行摘要，用简短的总结替换冗长的历史记录。
    - 关键信息保留：仅保留与当前意图最相关的消息或实体。
    - 裁剪：丢弃最早的非关键消息。压缩后的上下文确保模型调用不会因超长而失败。

### Agent Loop阶段（ReAct循环）

> 【·Scheduler：执行定时任务（提醒、清理、缓存刷新、监控）。
> 
> ·Clawhub：技能注册与调用中心，支持 MCP 和 CLI 调用，供 Agent 执行具体工具。】

1. 首次 LLM 调用（Agent Loop – 迭代1）
  - pi-embedded-runner将构建好的完整提示（含系统提示、会话历史、工具描述、用户偏好等）发送给 LLM API。此时 LLM 进入 Reasoning 阶段，分析用户意图并决定是否需要调用工具。
2. Agent Loop 解析与工具执行（迭代1 – Acting 阶段）

LLM 返回响应，进入Agent Loop：

- 解析响应：识别 LLM 输出的工具调用请求（Function Call 格式）。
  - 示例：调用天气查询工具（参数"明天"，可能传递附件中的图片用于图像识别）。
  - 工具执行：Agent Loop 执行该工具（通过 skill handler），获取执行结果。
  - 示例结果："明天晴天"。
  - 观察（Observation）：将工具执行结果作为新的上下文信息，准备进入下一轮推理。
1. 第二次 LLM 调用（迭代2 – 包含调用工具的结果）

Agent Loop 将工具执行结果（"明天晴天"）追加到会话上下文，再次调用 LLM API：

  - 此时可能再次进行模型解析和上下文窗口管理（compact.ts）。
  - 实际使用与第一次相同的机制，但上下文已包含工具执行结果。
  - LLM 基于新信息进行下一轮推理，决定是否需要进一步行动。
1. Agent Loop 解析与工具执行（迭代2 – Acting 阶段）

LLM 返回第二个工具调用请求：调用提醒设置工具（参数"明天晴天提醒"）。

  - 工具调用：调用提醒设置工具（参数"明天晴天提醒"）。
  - 工具执行：Agent Loop 执行该工具，返回成功状态。
  - 观察：将工具成功结果追加到上下文，准备最终回复生成。
1. 第三次 LLM 调用（迭代3 – 包含最终结果）

Agent Loop将工具成功结果追加到上下文，第三次调用 LLM API。生成最终回复。

示例："已设置明天晴天的提醒。"此时 Agent Loop 检测到无新工具调用，判定任务完成，退出循环。

### 返回给用户

Agent Loop 将最终文本发送给 Gateway Server，Gateway 转发给 Channel Adapter，后者将内部消息格式转换为目标平台的格式，然后通过接入层（飞书、钉钉、Dashboard）返回给用户。、

## 记忆系统设计

### 1. 会话记录（短期记忆）

每轮对话以 JSONL 格式保存，前面提过。

### 2. 记忆文件（长期记忆）

纯Markdown 文件，存在 [MEMORY.md](http://MEMORY.md) 或 /memory 文件夹里。这些文件不是什么 API 写入的，就是 Agent 自己用文件写入工具直接写的。每开一次新对话，一个 hook 会自动抓取上一次对话，把摘要写成 Markdown 存下来。

#### 检索方式

向量搜索 + 关键词匹配（BM25/ FTS5）。比如搜"爱好"，向量搜索能找到提过"爱好"的文档（语义匹配），关键词搜索能精确命中原词。向量搜索基于 SQLite，关键词搜索用 FTS5（SQLite 的全文搜索扩展），embedding 模型可以自己配。文件变动时还会通过文件监听器自动触发索引更新。

![image.png](http://veditor.vivo.xyz/api/v1/attachment/file/bQwUr6s9O2ZnNJ-Xmhkl3odbA6fhsM1r_exikdLGR7L_VRaNTIfEql_EGDXCX4qT "image.png")

没有记忆合并，没有按周按月压缩，没有遗忘曲线，新旧记忆权重一样。Memory 就是纯 Markdown 文件，你可以直接读、改、用 Git 做版本控制，完全透明。重要信息写在本地，不只在对话历史里，即使上下文被压缩摘要了也不受影响。检索时不会把所有记忆塞进上下文，而是按需搜索，向量匹配语义、关键词命中原词，两者结合兼得。

# Benchmark

## 记忆基准

目前公开的**记忆评测基准**包括** LoCoMo** (Snap Research 提出的超长对话记忆集，约300轮对话、9000 token 平均长度，用于考察跨会话知识回忆与问题回答)、**EverMemBench **(首个多方协作对话记忆基准，涵盖超过100万 token 的多主题会话，评估细粒度回忆、多角色条件记忆等)、**LongMemEval **(聚焦多轮聊天中信息提取、跨会话推理、时间感知更新等，含多种任务和最大 150万 token 级的跨度)。此外，OpenAI 社区也出现了“600轮对话记忆评测”结果。基于不同场景选用：**闲聊场景**可重点用 LoCoMo 和 LongMemEval，因为它们设计了对话式问题和实体推理；**深研场景**（例如文档检索与总结）可参考WikiMultiHop QA、NarrativeQA 等多文档推理任务，以及 EverMemBench 的跨人群情景。

  - **LoCoMo**：检验对话连续记忆和推理，适用于聊天助手评测。（[论文链接](https://arxiv.org/abs/2402.17753)）
  - **EverMemBench**：检验跨主题、多角色协作记忆，适合企业团队助手。（[论文链接](https://arxiv.org/abs/2602.01313)）

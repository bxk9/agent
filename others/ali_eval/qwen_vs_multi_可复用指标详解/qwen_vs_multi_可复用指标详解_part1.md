# qwen3.6-agent vs 多引擎路由 对比评测 — 可复用指标详解

> 本文档详细说明从现有 8 引擎评测框架中可直接复用的 **D5 端到端答案质量** 和 **D6 性能与鲁棒性** 两个维度的指标定义、计算方式、归一化方法及综合评分逻辑。

---

## 一、为什么 D5 和 D6 可以复用

| 维度 | 数据依赖 | 为什么适用 qwen3.6-agent |
|------|---------|------------------------|
| D5 答案质量 | 每条 query 的 `answer` 文本 + `measureScore` 打分 | qwen3.6-agent 返回的就是自然语言回答，可以直接打分 |
| D6 性能 | 每次调用的耗时、成功/失败状态 | qwen3.6-agent 的 HTTP 调用同样有耗时和成功率 |

D1~D4（召回量、RankScore 分布、时效性、URL 多样性）依赖结构化搜索结果（`list[dict]`），qwen3.6-agent 返回的是纯文本，无法计算这些指标。

## 二、D5 端到端答案质量

### 2.1 核心问题

> 把搜索结果（或 qwen3.6-agent 的直接回答）喂给 LLM 后，最终产出的答案质量有多高？

### 2.2 单条评分标准

每条 query 的答案被打一个 `measureScore`，取值 0 / 1 / 2：

| 分值 | 含义 | 典型场景 |
|------|------|---------|
| `2` | 满意 | 答案准确完整，覆盖了 query 的所有核心问题，无明显事实错误 |
| `1` | 瑕疵 | 部分正确，但有小错、遗漏次要信息，或表述不够准确 |
| `0` | 不满意 | 大错、漏答核心问题、幻觉、完全无关 |

### 2.3 指标定义

#### 5.1 满意率 / 瑕疵率 / 不满意率

```
satisfied_rate = N₂ / N_total     # 满意占比
flawed_rate    = N₁ / N_total     # 瑕疵占比
bad_rate       = N₀ / N_total     # 不满意占比
```

- **方向**：`satisfied_rate` 正向（越高越好），`bad_rate` 反向（越低越好）
- **意义**：分层展示答案质量——"完全对的占比"比"平均分"更能暴露两极分化问题

**示例**：
- A 方案：60% 满意 + 40% 不满意 → `satisfied_rate=0.60`，`bad_rate=0.40`
- B 方案：20% 满意 + 80% 瑕疵 → `satisfied_rate=0.20`，`bad_rate=0.00`

A 方案的"完全正确"比例更高，但容错性差；B 方案从不完全错，但很少完全对。两个指标合看才能完整判断。

#### 5.2 加权平均分

```
weighted_avg = (2 × N₂ + 1 × N₁ + 0 × N₀) / N_total
```

- **方向**：正向（越高越好），范围 0~2
- **意义**：单一综合分，越接近 2 越好。相比 5.1 的分层展示，它给出了一个可直接比较的标量

#### 5.6 时效场景平均分

```
realtime_avg = mean(measureScore)  仅对 is_realtime=True 的 query
```

- **方向**：正向
- **意义**：专项评估——对时效敏感的问题（如"2026年最新政策"），答案是否准确。如果测试集中有 `is_realtime` 标注则可用

#### 5.8 溯源覆盖率

```
attribution_ge_half_rate = count(attribution_score >= 0.5) / N_total_references
```

- **方向**：正向
- **意义**：答案中引用的参考文档，有多少条可以达到 0.5 以上的溯源置信度。反映"答案有据可查"的程度
- **注意**：qwen3.6-agent 的回答通常不返回结构化引用，此指标可能为 0，这也是对比的一个维度——"多引擎路由方案能否提供更好的溯源能力"

### 2.4 分意图分析

```
by_intent[intent][engine].avg_score = mean(measureScore)  仅该意图下的 query
```

- **不进综合分**，只做热力图展示
- **意义**：发现"某方案在某类问题上特别强/弱"的局部信号，用于路由策略优化

### 2.5 在对比评测中的 D5 综合权重

```
D5 维度得分 =  5.1_satisfied_rate         × 0.30
             + 5.2_weighted_avg            × 0.30
             + 5.1_bad_rate（反向）         × 0.15
             + 5.6_realtime_avg            × 0.15
             + 5.8_attribution_ge_half_rate × 0.10
```

> **设计理由**：
> - `satisfied_rate` 和 `weighted_avg` 各占 0.30：前者看"完全对的比例"，后者看"平均对到什么程度"，视角互补
> - `bad_rate` 占 0.15：反向指标，惩罚"频繁完全答错"的方案
> - `realtime_avg` 占 0.15：时效场景专项加权
> - `attribution` 占 0.10：溯源能力，权重较低因为 qwen3.6-agent 天然缺失此项

## 三、D6 性能与鲁棒性

### 3.1 核心问题

> 搜索方案够不够快？够不够稳？会不会频繁失败？

### 3.2 耗时采集方法

在调用侧记录 `time.time()` 差值作为端到端耗时：

```python
t0 = time.time()
result = call_search(query)
elapsed_ms = (time.time() - t0) * 1000
```

对于 qwen3.6-agent（SSE 流式），`elapsed_ms` 是从发送请求到读完最后一个 chunk 的完整耗时。

### 3.3 指标定义

#### 6.1 API 调用成功率

```
success_rate = N_success / N_total
```

- **方向**：正向（越高越好）
- **意义**：硬底线。成功率低于 90% 的方案基本不可用，无论搜得多好

#### 6.2 超时率

```
timeout_rate = N_timeout / N_total
```

- **方向**：反向（越低越好）
- **判定**：错误信息中包含 `"timeout"` 或 `"timed out"` 字样，或调用侧计时超过设定阈值

#### 6.3a 端到端耗时 P50 / P95 / P99

```
elapsed_ms.p50  = percentile(elapsed_ms_list, 0.50)
elapsed_ms.p95  = percentile(elapsed_ms_list, 0.95)
elapsed_ms.p99  = percentile(elapsed_ms_list, 0.99)
```

- **方向**：反向（越低越好）
- **意义**：
  - `p50`（中位数）：反映"大多数用户的体感延迟"
  - `p95`：反映"最差用户体验"——业务通常有 SLA 要求"95% 请求 < 2s"
  - `p99`：极端长尾

#### 6.3c 服务端耗时

```
server_ms.median = percentile(server_ms_list, 0.50)
```

- **方向**：反向（越低越好）
- **意义**：剥离网络延迟后的纯引擎处理时间，反映引擎自身性能
- **注意**：qwen3.6-agent 是 SSE 流式，server_ms 即从首字节到末字节的流式传输时间

#### 6.3d 网络耗时占比

```
network_ratio_mean = mean(network_ms / elapsed_ms)
```

- **方向**：反向（越低越好）
- **意义**：瓶颈定位——如果 `network_ratio > 0.5`，说明瓶颈在网络（DNS/TLS/传输）而非引擎本身

#### 6.4 耗时标准差

```
elapsed_std = stdev(elapsed_ms_list)
```

- **方向**：反向（越低越好）
- **意义**：延迟稳定性。均值再低，抖动大也不行——用户会遇到"有时秒回、有时卡 10 秒"的糟糕体验

### 3.4 在对比评测中的 D6 综合权重

```
D6 维度得分 =  6.1_success_rate          × 0.20
             + 6.2_timeout_rate（反向）    × 0.10
             + 6.3a_elapsed_ms.p50（反向） × 0.15
             + 6.3a_elapsed_ms.p95（反向） × 0.15
             + 6.3c_server_ms.median（反向）× 0.15
             + 6.4_elapsed_std（反向）      × 0.10
             + 6.3d_network_ratio_mean（反向）× 0.05
```

> **设计理由**：
> - `success_rate` 权重最高（0.20）：先决条件，失败率高的方案直接出局
> - `p50` 和 `p95` 各 0.15：同时关注平均体验和长尾体验
> - `server_ms` 0.15：引擎自身能力（剥离网络因素）
> - `elapsed_std` 0.10：稳定性
> - `network_ratio` 0.05：弱信号，仅用于瓶颈定位参考

## 四、归一化方法

### 4.1 min-max 归一化

每个子指标在参评方案间做 min-max 归一化，映射到 0~100：

```python
# 正向指标（越高越好，如成功率、满意率）
norm = (value - min) / (max - min) × 100

# 反向指标（越低越好，如耗时、超时率）
norm = (1 - (value - min) / (max - min)) × 100
```

### 4.2 特殊情况处理

| 情况 | 处理 |
|------|------|
| 所有方案某指标值相同（`max == min`） | 统一给 50 分（"无差异即中庸"） |
| 某方案缺失某指标数据 | 给 0 分 |
| 只有 2 个方案参评 | min-max 会极端化为 0 和 100，结论需谨慎解读 |

### 4.3 两级加权

```
维度得分 DS(方案) = Σ 子权重_i × norm_i(方案)
综合得分 CS(方案) = Σ 维度权重_k × DS_k(方案)
```

对比评测只需要 D5 和 D6 两个维度，默认权重：

| 维度 | 权重 | 理由 |
|------|------|------|
| D5 答案质量 | 0.60 | 最终业务目标，权重最高 |
| D6 性能 | 0.40 | 决定能不能上线 |

> 可用 `--weights` 参数覆盖，例如 `--weights '{"D5":0.70,"D6":0.30}'`。

## 五、评分等级

| 综合得分 | 等级 | 含义 |
|---------|------|------|
| 90~100 | S | 卓越，可作默认方案 |
| 80~89 | A | 优秀，主力候选 |
| 70~79 | B | 良好，特定场景可用 |
| 60~69 | C | 及格，需谨慎 |
| <60 | D | 需改进，暂不推荐 |

## 七、与现有 8 引擎评测框架的差异

| 差异点 | 8 引擎评测 | 本对比评测 |
|--------|-----------|-----------|
| 参评对象 | 8 个搜索引擎 | 2 个方案（qwen3.6-agent vs 多引擎路由） |
| 适用维度 | D1~D6 全部 | 仅 D5 + D6 |
| 数据采集 | Phase 1 搜索采集 + Phase 2 端到端 | 一次采集（方案直接返回答案） |
| 打分方式 | FastAPI 服务的 `get_auto_acc_score` | 可复用或直接用 LLM judge |
| 指标数量 | ~50 个子指标 | ~12 个子指标 |

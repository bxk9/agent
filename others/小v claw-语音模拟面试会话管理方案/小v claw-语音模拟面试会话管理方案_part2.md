| 语音面试历史查询 | 面试一般是阶段性的，3-5月暑期实习面试，8-10月校招面试<br>**具体题目细节缺失**，此阶段最近几次面试，若轮次太多生成摘要，无法应对细节题<br>**可查询历史范围狭窄**，无法询问更久远的面试情况<br>**模糊要求无澄清**，用户询问“之前面的怎么样”，理应提供面试场次供用户确认 | 适时添加用户**确认组件2**，供用户澄清询问的是哪次面试历史<br>在语音根目录建**metadata**.json，保存所有语音历史对话。需要voice_session_id、公司、岗位、tag、chain_start、简单摘要，简历面试新增**分组筛选**机制，供确认组件1和2使用。<br>语音llm判断是否落入已提供的用户级最近3-5次历史<br>若落入，语音已有prompt，可自行回答；<br>否则，弹出确认组件2，拉取对应对话内容 | 提前注入最近几次语音的摘要或者轮次<br>所有历史会话metadata结构设计，根据公司、岗位、时间等信息查找id<br>设计上下文链路：<br>      （1）拿id：简历面试监听实时对话，根据query过滤                信息，比如公司-岗位-时间等，从meta筛选得到                候选id；中控调接口拿id对应的面试元信息，客                  户端渲染确认组件2<br>      （2）拿对话内容： 客户端按钮-中控-简历面试拿取id                对应对话内容，最终交给语音服务 |

### 3.1.1 重复链接的用户确认

- 概要：V2方案针对语音链接重复点击的边界情况进行了用户层面的分析，此前V1方案默认续接上一次的面试追加turns，现分析用户意图，串连续接面试、查看复盘、新开面试、面试重置四个基础操作。

假设用户已经有三个面试链接：

| 点击链接 | 最可能意图 | 次要意图 | 说明 |
| --- | --- | --- | --- |
| **链接 4**（未完成） | 继续上次面试 | 重新开一个面试 | 用户特意点击，更大可能是想继续这个链接的题目 |
| **链接 5**（已完成） | 查看复盘 | 重新开一个面试 | 已完成的面试，用户可能想看上次表现 |
| **链接 6**（最新） | 开始新面试 | 和之前面试对比分析 | 后续可能用最新链接完成所有面试操作 |

- 用户再次点击链接的行为可能出于：
  - 1.不记得面试内容想查看复盘
  - 2.面试中断，想继续面试
  - 3.图便利想在一个链接完成面试所有操作
- 用户重复点击链接行为背后意图未知，需要一个确认页面，继续上次未完成面试/查看复盘/重新开一个面试/面试新公司岗位。示例如下：

![image.png](http://veditor.vivo.xyz/api/v1/attachment/file/wYo-l2nVvqBZNf62GDrvT2U5-SFC839xrdpFV487OLecSN7oVXW8T0XYGSXO4_U6 "image.png")

- 渲染组件：
  - 链接点击，客户端跳转深度对话，调中控，中控去简历面试拉/context，发现已创建dialogue，从meta中筛选id，按公司岗位分组，整理成json，中控收到后转发客户端，客户端渲染用户确认组件1
  - 按照答题数，区分完成/未完成的面试，已完成的面试无法续接
- 组件点击五种情况：
  - **点击续接**：用户特意点击，更大可能是想继续这个链接上次的题目。
    - 优先询问此链接未完成面试，提示用户其他链接未完成会话，让用户自己选择。选择继续面试的话，复用之前context，添加turns摘要。
    - 拉取当前面试的最近有效dialogue，之前的续接已经融合turns，最近dialogue已经是之前所有的内容
    - 续接后可能衔接复盘、新开、重置等操作，新开塞入上次会话，重置清空，复盘依赖语音模型上下文，关键在切换任务题数的记录、状态的变更、续接复盘混杂对后续上下文的影响
  - **点击复盘**：用户好奇之前面试内容，点击查看一下之前面过什么
    - 拉取当前面试的chain_start整个会话链路，打包turns。
    - 用户可能会要求复盘后再检查复盘吸收效果，复盘后再衔接重新开始面试，把复盘对话内容塞入新面试。
  - **点击新开**：用户知道当前面试的公司岗位，想不受之前题目干扰重新开启面试；
    - 拉取当前面试的system_role、主对话memorysaver，复用公司岗位、面试配置，重新搜索生成；
    - 中控调面试接口，拿上下文再调语音
  - **点击面试新公司岗位**：用户把所有语音链接当作面试入口，语音中重置面试，跳过主对话文字确认
    - 客户端点击按钮-语音服务询问公司岗位-简历面试监听搜索生成-中控调/context-调语音服务
  - **点击其他链接的面试**：用户把语音链接当作面试入口，可能希望链接中有其他会话的最新记录，在单链接中进行最新面试更便利
    - 最新面试信息源于全局语音面试meta，已携带id
    - 客户端按钮点击后中控-简历面试-语音。重新开启语音session，客户端无感。
- 其中新开面试和重置的区别在于是否传入上次会话上下文和公司岗位信息是否复用。

## 3.2 会话管理细则

### 3.2.1 voice_id 管理

一个链接对应一个voice_id，每次点击链接新建对话为一个dialogue_id

| 操作 | voice_id | 说明 |
| --- | --- | --- |
| 链接首次面试 | 新建 | 生成新 id，开启全新面试 |
| 续接 | **复用** | 同一轮面试，继续未完成的对话 |
| 复盘 | **复用** | 同一轮面试，基于已有对话生成评估 |
| 新开 | **复用** | 同一公司岗位，重新开始一轮面试 |
| 重置 | **复用** | 不同公司岗位，开启全新面试 |

### 3.2.2 跨链接 vs 单链接

用户确认组件1，选择进行的面试，可能跳转其他链接的新面试，这时切换voice_id。链接之间的context不共享，避免语音服务prompt被覆盖

| 维度 | 跨链接 | 单链接内 |
| --- | --- | --- |
| 触发 | 用户点击新链接 | 用户在当前链接内操作 |
| 存储 | 新链接 → 新 voice_id → 新目录 | 同一 voice_id 目录下 |
| context | 链接间各自独立 | 链接内共享 |

### 3.2.3 metadata 记录

**存储位置**：语音会话根目录 `/users/{uid}/voice_sessions/meta.json`

**核心作用：轻量索引 - **"有哪些面试、每轮面试是什么状态"。

  - 确认页面的渲染：查找当前链接id的面试，和其他链接更新的面试
  - 分组展示：按 (company, position) 分组、按 chain_start 分轮次，都只需要 metadata 中的字段，不需要读完整对话。
  - 状态判断：questions_done >= questions_total → completed / in_progress，直接从 metadata 读取，不需要解析 turns。
  - 历史整体表现查询：LLM 从 metadata 的 summary 中直接回答，不需要加载完整对话。只有用户追问细节时才按需加载。

**记录时机**：结束面试时（点击叉号/ 新开 / 重置）

**记录内容**：

```json
{
    "voice_session_id": "hs-web-user_taskid123_a3f2", url唯一标识
    "voice_id"："hs-web-user_taskid123_a3f2-ts3"，此次会话标识
    "chain_start":"hs-web-user_taskid123_a3f2-ts1"，用于区分链接中不同轮面试
    "company": "腾讯",
    "position": "产品经理",
    "status": "completed",
    "questions_done": 10,
    "questions_total": 10, 总题数和已回答数量 用于判断当前轮面试是否结束
    "summary": "候选人在Redis缓存设计方面表现较弱，产品规划能力较强", 推送客户端渲染供用户查看选择
    "created_at": 1786013421,
    "completed_at": 1786013600
}
```

### 3.2.4 碎片化处理

用户多次误触/试探性点击会产生碎片化记录。处理策略：

- **检测**：dialogue 中无用户回复，或用户回复总字数 < 10 → 标记为碎片
- **记录**：dialogue文件不删除，meta过滤碎片不记录，避免影响续接和题目数量继承
- **展示**：碎片不在确认页面展示，首先根据公司岗位分组，再看属于第几轮，需要过滤碎片。

### 3.2.5 同面试上下文（续接 / 复盘 / 初次面试）

同一轮面试内的操作共享上下文：

| 操作 | 上下文来源 | 边界情况 | 说明 |
| --- | --- | --- | --- |
| 初次面试 | 简历面试preload 生成的 context |  | 搜索面经 + build context |
| 续接 | 当前 dialogue 的 turns | 先进行了复盘再续接：避免复盘qa对影响出题数量<br>多次续接：注入摘要，不容易影响续接质量；注入轮次，prompt可能太长； | 过滤碎片，注入历史对话，继续出题 |
| 复盘 | 当前轮面试的 turns | 复盘前多次续接：依赖续接注入摘要/轮次。<br>    （1）如果是轮次，不需要重新拉；<br>    （2）如果是摘要，需要根据chain_start拉取完整轮次。 | 过滤碎片，基于已有对话生成评估 |

### 3.2.6 跨面试上下文（新开 / 重置）

| 操作 | 是否带上次会话 | 上下文来源 |
| --- | --- | --- |
| 新开 | **带** | 重新 build context + 注入上轮面试摘要，保留上轮voice_id |
| 重置 | **不带** | 全新 build context，不注入旧面试信息 |

### 3.2.7 历史会话查询

**两层架构**：

```plaintext
第一层：已知 id（用户确认组件1，当前链接优先）
  → 用户点击确认组件1选择具体面试
  → 根据 voice_session_id+ts 直接拉取完整对话

第二层：未知 id（搜索匹配，用户确认组件2）
  → 用户问题模糊，无法确定哪次面试
  → 从 metadata 中搜索匹配的公司/岗位/时间
  → 找到 voice_session_id 后再拉取完整对话
```

**注入策略**：

| 层级 | 注入方式 | 覆盖范围 |
| --- | --- | --- |
| 最近 N 次语音会话latest_summary | 自动注入 prompt | 覆盖大多数场景（~90%） |
| 更早的历史会话 | 从 metadata 查询 id → 拉取完整对话 | 完整覆盖所有历史 |

## 二、场景 0：通用前置 · 公司画像构建

**产品期望**：用户说"我要投字节算法岗"，系统自动构建一份贯穿全程的"公司×岗位"画像，后续简历改写、题库生成、面试反馈全部基于这份画像，不重复构建。

---

### 技术点 0-0：Skill 定义设计（贯穿全部场景）

在 Open Claw 框架下，**触发哪个 Skill/Workflow 是主模型的职责**，主模型通过读取每个 Skill 的 `description`（触发描述）来决策，不需要算法团队单独构建意图分类器。

算法团队在这里的工作是：**把每个 Skill 的触发条件、参数 schema、调用时机写清楚**。

```plaintext
Skill 定义示例（context_bootstrap）：
{
  "name": "context_bootstrap",
  "type": "workflow",
  "description": "当用户首次提到一个明确的目标公司和岗位时触发（如'我要投字节算法岗'）。
                  若 session 中已存在该公司+岗位的画像则跳过，直接复用缓存。",
  "parameters": {
    "company": "string, 公司名（经归一化后的标准名）",
    "role":    "string, 岗位名（如算法/产品/客户端）",
    "jd_input": "string | image, 用户提供的 JD 文本或截图，可选"
  }
}
```

| 关键设计 | 说明 |
| --- | --- |
| description 精确性 | 描述太宽泛 → 主模型误触发（用户随口提到字节就触发）；太严格 → 漏触发（用户没说"投"只说"字节算法岗咋样"） |
| 缓存判断前置 | description 中明确"已有缓存则跳过"，避免主模型重复触发构建 |
| 各团队各自负责 | 每个承接团队负责自己模块的 Skill 定义；算法负责人统一审核触发边界是否合理 |

### 技术点 0-1：Skill 输入参数归一化（公司名/岗位名标准化）

> 这个问题不在"意图识别"层，而在 `**company.profile_cache**`** 的 key 查询层**——主模型提取出 `company="字节"` 后，缓存层负责将其映射到标准 key，才能命中已有画像。

| 项 | 内容 |
| --- | --- |
| **任务类型** | 字符串归一化 + 映射表查询 |
| **输入** | 主模型从用户话语中提取的公司名原始字符串（"字节" / "ByteDance" / "抖音"） |
| **输出** | 标准化公司名（"字节跳动"）作为缓存 key |
| **技术方案** | 维护一张公司别名映射表（人工维护，覆盖主流大厂常见别名）；查询时先过映射表，未命中则以原始字符串兜底 |
| **关键约束** | 子品牌粒度（抖音 vs 飞书）第一期统一到公司粒度（字节跳动）；映射表需要长期维护（公司改名/新品牌出现） |

### 技术点 0-2：JD 录入与解析 · `jd.extract`

> 这个技术点分两阶段，算法层必须从第一天就设计好统一的抽象接口，否则阶段一到阶段二的迁移会伤筋动骨。

**产品理想态**：用户在 BOSS / 拉勾 / 脉脉等 App 看到心仪岗位，一键授权给龙虾，JD 自动录入，无需截图或手动粘贴。

#### 阶段一（当前实现）：多模态解析

| 项 | 内容 |
| --- | --- |
| **任务类型** | 文档信息抽取（非结构化 → 结构化） |
| **输入** | 用户粘贴的 JD 文本 **或** JD 截图 |
| **输出** | 统一内部 Schema：`{jd_id, source, skills[], experience, explicit_req[], hidden_req[], team_style}` |
| **技术方案** | 文本输入：LLM prompt 抽取；截图输入：端侧 OCR 预处理 → 文本 → 同上（Qwen-VL 可端到端跳过 OCR 步骤） |
| **关键约束** | 隐藏要求（如"字节偏爱拍板型"）纯 JD 文本无法覆盖，必须依赖 `web.search` 补充；截图倾斜/低质需要前置图像矫正 |

#### 阶段二（理想态）：平台 API 直连

| 项 | 内容 |
| --- | --- |
| **任务类型** | Schema 映射（结构化 → 结构化，不再需要 NLP 抽取） |
| **输入** | 招聘平台 API 返回的原始 JSON（各平台字段不同） |
| **输出** | 同上，统一内部 Schema（`jd_id` 标注来源平台） |
| **技术方案** | 各平台写一套 Adapter（BOSS Adapter / 拉勾 Adapter / 脉脉 Adapter），将平台字段映射到内部 Schema；映射缺失字段（如隐藏要求）仍走 LLM 补充 |
| **关键约束** | 各平台 API 字段不统一，维护多套 Adapter 成本持续存在；平台 API 限流/鉴权需要额外工程投入 |

#### 关键设计：统一抽象接口

```plaintext
┌─────────────────────────────────────────────┐
│              jd.extract 抽象层               │
│                                              │
│  输入适配器（可插拔）                         │
│  ├─ TextAdapter      文本粘贴 → LLM 抽取     │
│  ├─ ImageAdapter     截图 → OCR → LLM 抽取  │
│  ├─ BossAdapter      BOSS API → Schema 映射 │
│  ├─ LaGouAdapter     拉勾 API → Schema 映射 │
│  └─ MaimaiAdapter    脉脉 API → Schema 映射 │
│                                              │
│  统一输出：内部 JD Schema（下游场景只认这个）│
└─────────────────────────────────────────────┘
```

**算法层动作**：阶段一就按这套 Adapter 架构实现 TextAdapter 和 ImageAdapter，预留插槽；阶段二平台合作谈成后直接插入对应 Adapter，下游场景零改动。

| 项 | 内容 |
| --- | --- |

**产品期望**：用户把通用简历扔进来，系统对照 JD 和公司画像自动改写每条经历，告诉用户改了什么、为什么改，最后输出可下载的多格式简历。**改写要有针对性，不是通用模板**。

### 技术点 1-1：简历解析 · `resume.parse`

| 项 | 内容 |
| --- | --- |
| **任务类型** | 文档解析 + 结构化信息抽取 |
| **输入** | PDF 或 DOCX 简历文件 |
| **输出** | 结构化 JSON：`{basic_info, education[], experience[{bullet_id, text}], projects[], skills[]}` |
| **技术方案** | PDF：PyMuPDF 提取文本；DOCX：python-docx；结构切分用 LLM NER（识别段落归属） |

### 技术点 1-2：简历存储与版本管理

> 这是产品文档未明确但**支撑整个闭环最关键的基础设施**，在算法层必须先设计好。

**存储分层**：

```plaintext
① 原始文件：本地加密存储（AES-256，TEE 托管密钥），不上云
② 结构化版本链（Room DB）：
   resume_id → version_no → parent_id（上一版）
                          → based_on_jd_id
                          → based_on_profile_id
                          → bullets[]{bullet_id, original_text, rewritten_text}
③ 面试快照（只读归档）：
   每次进入面试 session 时，fork 当前最新版本为不可变快照
   session_id → resume_snapshot_id（1:1）
   → 复盘时三重对照用的是"当时实际投出去的那版"，而非最新版
```

**版本链示意**：

```plaintext
v0（用户上传原始）
 ├─ v1_bytedance_algo（针对字节算法改写）
 │    └─ snapshot_s001（面试 session_001 锁定，只读）
 └─ v1_tencent_pm（针对腾讯产品改写）
      └─ snapshot_s002（面试 session_002 锁定，只读）
```

| 关键设计 | 说明 |
| --- | --- |
| bullet_id 稳定性 | 同一条经历从 v0 改写到 vN 保持同一 bullet_id，改写只更新 `rewritten_text` |
| 快照时机 | 用户确认"开始面试/模拟面试"时 fork，而非投递时（投递时机不明确） |
| 用户删除经历时 | bullet 不物理删除，打 `deleted=true` 标记，保留历史追踪 |

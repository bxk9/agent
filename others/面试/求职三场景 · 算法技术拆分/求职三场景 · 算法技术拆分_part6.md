| **任务类型** | 文件检索 + 时间匹配 |
| **输入** | 日历中的面试事件（时间戳 + jd_id） |
| **输出** | 匹配到的通话录音文件路径 |
| **技术方案** | 直接访问系统拨号器录音目录（厂商权限）；按通话时间戳与日历事件时间做 ±10 分钟容差匹配；多条候选时按时长排序（面试通话通常 > 30 分钟） |
| **关键约束** | **需与系统拨号器团队确认是否支持双轨录制（上行/下行分离）**——双轨时说话人天然分离，单轨需要额外 diarization，质量差距很大，这是 ASR 方案选型的前提 |

---

### 技术点 3-2：ASR 转写 · `audio.asr_batch`

| 项 | 内容 |
| --- | --- |
| **任务类型** | 语音识别 |
| **输入** | 通话录音文件（AMR/AAC，8kHz 窄带） |
| **输出** | 带时间戳的文字转写，含说话人标签 |
| **技术方案** | 方案 A（双轨录音）：两路音频分别 ASR → 说话人天然分离，推荐用讯飞/阿里云 8kHz 专项模型；方案 B（单轨录音）：pyannote.audio 做说话人分离 → 再 ASR，精度下降 10-15% |
| **关键约束** | 电话录音 8kHz 窄带是核心挑战，Whisper 对 8kHz 支持不佳；**需选择专门针对电话窄带音频训练的 ASR 模型**；嘈杂环境下（用户在外面打电话）需要前置降噪 |

---

### 技术点 3-3：对话切分 · `dialog.segment`

| 项 | 内容 |
| --- | --- |
| **任务类型** | 话语边界检测 + Q-A 配对 |
| **输入** | 带说话人标签的转写文本 |
| **输出** | Q-A 配对列表：`[{q: "面试官说的问题", a: "候选人的完整回答"}]` |
| **技术方案** | 按说话人轮次切分 → LLM 识别问题边界（一轮发言可能包含多个问题）→ 合并候选人连续发言为完整回答；短语气词（"嗯""好的"）合并到下一段 |
| **关键约束** | 终面多面试官场景（说话人 > 2）需要额外处理；面试官一次问多个问题时需要拆分成多个 Q-A 对 |

---

### 技术点 3-4：三重对照复盘 · `answer.review`

| 项 | 内容 |
| --- | --- |
| **任务类型** | 多维度文本评估 + 对比生成 |
| **输入** | Q-A 配对 + **面试时锁定的简历快照**（非当前最新版）+ JD + 公司画像 |
| **输出** | 逐题：`{diagnosis, high_score_reference, diff_with_original}` |
| **技术方案** | LLM 以三重 rubric 逐题评估：① 基础维度（逻辑/完整性）② JD 对齐 ③ 简历呼应（该题是否在追问简历某条经历）④ 公司画像匹配；高分参考答案**基于用户原始回答做增量改进**，不凭空生成通用模板答案 |
| **关键约束** | **长 context 管理**：1 小时面试转写约 10000-15000 token，三重基准再加进来逼近上限；**按题分批送评**（每题独立 prompt），异步并发处理提速；**简历快照必须取面试时版本**，不能用当前最新简历 |

---

### 技术点 3-5：简历-问题语义关联

| 项 | 内容 |
| --- | --- |
| **任务类型** | 跨文档语义匹配 |
| **输入** | 面试问题文本 + 简历所有 bullet 文本 |
| **输出** | 该题关联的 `bullet_id`（如"追问的是你简历里豆包 D7 那条"） |
| **技术方案** | Embedding 相似度（候选集小，直接暴力搜索）+ LLM 判断确认；面试官不会原文重复简历词汇，纯关键词匹配不可用 |
| **关键约束** | 这是整个复盘闭环最有价值也最难的技术点：关联准确才能让"这题答不好 → 弱化对应简历经历"的链路真正成立；误关联会导致经验池数据污染，初期可以设置置信度阈值，低于阈值不关联 |

### 技术点 3-6：错题本 · `mistake.book_build`

| 项 | 内容 |
| --- | --- |
| **任务类型** | 结构化信息组织 |
| **输入** | 逐题复盘结果 + 关联的 bullet_id |
| **输出** | 错题本条目：`{失分点, 我的原始回答, 漏洞分析, 高分参考答案}` 四段对照 |
| **技术方案** | 直接从 `answer.review` 结果结构化存储；按失分严重程度分级（小漏/结构勉强/完全跑题） |
| **关键约束** | 错题本需与 bullet_id 关联：同一条简历经历跨多场面试的失分可聚合分析（"这条经历在字节和腾讯都答崩了"） |

### 技术点 3-7：复盘优化计划 · `mistake.spaced_review`

> 不只是安排复习节奏，还需要先搜索外部信息，给用户提供"有依据的优化方向"——告诉用户这道题该怎么答，是因为搜到了该公司的真实倾向和他人的高分答法，而不是 LLM 凭空给建议。

**两阶段执行：先搜索，再规划**

```plaintext
第一阶段：外部信息检索（有无可用缓存则跳过）
  search.dispatcher(type=interview_exp,  company, role)  → 他人面经：该题的常见高分答法
  search.dispatcher(type=jd,             company, role)  → JD 要求：该能力维度公司最看重什么
  search.dispatcher(type=company_style,  company)        → 公司倾向：这家公司的文化/偏好/雷区
        │
        ▼
第二阶段：生成优化计划
  以错题本（用户原答 + 漏洞）+ 外部参考（他人高分答法 + JD要求 + 公司倾向）
  → LLM 生成逐题优化建议（"字节更看重数据归因，你下次可以这样组织..."）
  → SM-2 调度：按严重程度安排复习节奏
  → 写入日历 ICS + 更新 memory.job_journey 弱点画像
```

| 项 | 内容 |
| --- | --- |
| **任务类型** | 搜索增强的优化计划生成 + 间隔复习调度 |
| **输入** | 错题本（用户原答+漏洞）+ 外部搜索结果（他人面经/JD要求/公司倾向）+ memory 弱点重复次数 |
| **输出** | 逐题优化建议（有外部依据）+ 复习时间节点（ICS）+ 专项强化包（弱点重复≥2次时触发） |
| **技术方案** | 搜索结果与错题本一起送给 LLM，prompt 要求 LLM 在优化建议中明确引用外部依据（"根据字节面经，这类题通常考察…"）；调度算法：SM-2 变体，严重程度调节间隔（×0.5~×1.5）；**三类搜索与场景0 画像构建共享缓存，通常直接命中，无需重新搜索** |
| **关键约束** | 搜索结果若缓存未命中（如冷门公司），此步骤会有额外延迟；需要给用户展示"正在查阅该公司面试倾向…"的等待态；优化建议中引用的外部依据要标注来源，避免 LLM 伪造引用 |

## 六、共享基础设施 · `search.dispatcher` 多源搜索管理

**为什么需要统一管理**：产品里有三类搜索需求，来源不同、格式不同、更新频率不同，如果各自为政，缓存逻辑会散落在各场景造成重复外部请求，也无法统一做质量过滤和结果去重。

### 四类搜索来源对比

| 搜索类型 | 使用场景 | 数据来源 | 结果格式 | 推荐 TTL |
| --- | --- | --- | --- | --- |
| **JD 搜索** | 场景0·JD解析 | 阶段一：用户粘贴/截图；阶段二：BOSS/拉勾/脉脉 API | 招聘平台原始 JSON / OCR 文本 | 30天（JD内容基本不变） |
| **面经搜索** | 场景0·公司画像 / 场景2·题库排序 / 场景3·复盘优化 | **小红书**（求职面经帖）+ 牛客 + 看准 + 通用 Web | 非结构化摘要文本 | 7天（面经更新较快） |
| **简历样本搜索** | 场景1·改写参考 + 重排权重 | **小红书**（简历晒单/模板分享）+ GitHub 简历模板 + 技术博客 | 非结构化摘要文本 | 14天（写法变化慢，但小红书内容更新快于 GitHub） |
| **公司倾向搜索** | 场景3·复盘优化 | **小红书**（公司文化帖/入职感受）+ 脉脉（公司评价）+ 通用 Web | 非结构化摘要文本 | 30天（公司文化变化缓慢） |

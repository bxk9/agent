# 08 · VFS 存储演进四阶段：从"能存"到"多租户统一入口"

> **作者**：司棋 · **场景**：Agent 生态下的虚拟文件系统

---

## 一句话摘要

面对 Agent 场景下"文件散落多处 / URL 命名混乱 / 多租户隔离缺失 / 三种入口重复实现"的存储治理挑战，我在 6 周内推进 VFS 从**"首建"→"URL 治理"→"namespace 单一真理源"→"用户中心化 + 三头统一"**四阶段演进，最终形成一套 Agent 生态可复用的**虚拟文件系统**。

## 背景与问题定义

### 业务场景

Interview Agent 涉及大量文件：
- 用户上传的简历 PDF/DOCX
- 生成的简历 HTML/DOCX/PDF
- 复盘报告 HTML
- 面试音频（用户录音）
- 头像图片

早期问题：
- 文件散落（本地磁盘 / 云对象存储 / A2A 服务临时目录）
- URL 每种形态不同（内网 http / 云短链 / claw:// 协议）
- 多用户共享 namespace（数据可能串）
- Agent、工具、前端各自维护上传/下载代码

## 方案演进四阶段

### 阶段 1：VFS 首建（06-11）

**关键 commit**：`feat: BlueClaw VFS 首建` / `refactor(file): 统一文件操作到 VFS`

**做了什么**：
- 定义 VFS 抽象接口：`put / get / list / sign / delete`
- 统一后端存储（对象存储 + 数据库元信息）
- 所有工具的文件操作**必须**过 VFS

**为什么先做这个**：
- 存储抽象不建立，后续所有优化都会重复踩坑

---

### 阶段 2：URL 治理（W25, 06-16 ~ 06-22, 10+ commits）

**做了什么**：
- 定义 `claw://` 协议（对内部产物签发）
- 统一 URL 签发接口
- 区分"内部流转 URL"（长期）和"下发用户 URL"（短时效）

**关键决策**：**内部用 claw:// 协议 + 外部签发短链**——把"内网流转的 URL"和"给用户看的 URL"分开。

好处：
- 内部 URL 可跨服务传递、无过期
- 外部 URL 有效期短、权限受控

---

### 阶段 3：namespace 单一真理源（06-24）

**关键 commit**：`refactor(context): namespace 单一真理源`

**发现的问题**：
- task_store / VFS / ctx_log 各自维护"namespace"概念
- 三个地方定义不一致 → 数据关联失败

**做了什么**：
- namespace 定义**在一个地方产生**（Agent 入口）
- 所有下游（VFS / task / log）从同一处消费

**核心原则**：**Single Source of Truth**——任何数据在系统内只能有一处定义，其他地方消费而非重新定义。

---

### 阶段 4：用户中心化 + 三头统一（06-25 起）

**用户中心化 Phase 1（06-25）**：
- VFS 按 user_id 分区
- session_id 全局唯一但 user_id 是主 partition key
- 一个用户看不到另一个用户的文件（安全边界）

**tenant 固定值 → 跨会话记忆（06-30）**：
- 之前 tenant 按 session 变化 → 同一用户跨会话文件互相看不到
- 修复后同一用户跨 session 可以引用"我的错题本""我的简历"

**三头统一**（前端 / Agent / 工具）：
- 之前上传逻辑在前端、Agent、工具三处各有一份
- 统一为**一个 VFS SDK**
- 三头都用同一个客户端 → 修一次全都受益

---

## 关键设计模式

### 模式 1：分层 URL

```
内部流转：   claw://ns/user_id/session_id/xxx.pdf
外部下发：   https://vfs-public.xxx/short/abc123  (有效期 1h)
```

用户看不到 claw:// 协议，工程侧看不到 hash 短链——各得其所。

### 模式 2：主分区 + 二级分区

```
/user_id={A}/session_id={S1}/file
```

- 主查询按 user_id（安全 + 跨会话共享）
- 二级细分 session_id（可选，用于会话临时文件）

### 模式 3：抽象接口 + 多后端

```python
class VFS:
    async def put(path, data, meta) -> URL
    async def get(url) -> bytes
    async def sign(url, ttl) -> public_url
    async def list(prefix) -> [meta]
```

后端可以是对象存储、本地磁盘、云盘 —— 上层不感知。

## 方法论抽象与迁移

### 演进型架构的三个原则

1. **每阶段只解决一个痛点**：不试图一次做全对
2. **前期投资抽象层**：VFS 接口先建立，具体后端可换
3. **单一真理源**：任何"重复定义"都是未来 bug 温床

### 存储系统设计的常见误区

| 误区 | 教训 |
|:---|:---|
| **URL 一种就够了** | 内部/外部诉求不同，混用必踩坑 |
| **session 作主分区** | 跨会话场景直接失败 |
| **上传逻辑各自实现** | 修一次不修全部 → 数据不一致 |
| **namespace 各处定义** | 三处不一致时全链路对不上 |

### 可迁移场景

| 场景 | 迁移点 |
|:---|:---|
| **通用对象存储抽象** | Interface + 多后端 |
| **微服务的租户隔离** | user_id 主分区模式 |
| **协议演进** | 内部 URL 稳定 + 外部 URL 灵活 |

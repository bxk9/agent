# 09 · AI 标记契约与 15+ 模板矩阵：LLM 输出到模板渲染的稳定桥梁

> **作者**：11099826 · **场景**：AI 简历生成 · 多模板统一渲染

---

## 一句话摘要

面对"**LLM 输出结构 × 15+ 简历模板 × 三种输出格式（HTML/DOCX/PDF）**"的 M×N×K 组合爆炸，我设计了**"AI 标记契约"**——一份稳定的中间数据契约，把 LLM 侧和渲染侧彻底解耦，让新增模板只需 100 行 CSS 而不需要动 AI Prompt 或渲染核心。

## 背景与问题定义

### M × N × K 组合爆炸

- **M**：LLM 输出结构（15+ 字段，随迭代变化）
- **N**：15+ 简历模板（技术型、学术型、创意型、Master Profile、Academic CV...）
- **K**：3 种输出格式（HTML / DOCX / PDF）

不加治理：**M × N × K = 15 × 15 × 3 = 675 个耦合点**

任何一个字段变化都可能影响 45 个模板 × 3 个格式。

---

## 方案：AI 标记契约

### 核心思想

**在 LLM 输出和模板渲染之间插入一层"稳定契约"**：

```
LLM 输出（M 变化） ──▶ AI 契约（稳定） ──▶ 模板渲染（N × K）
```

**契约特点**：
- 字段名固定
- 语义明确（每个字段的存在/缺失/取值范围都文档化）
- 版本化（v1 / v2，向后兼容）

### 契约示范

```yaml
# AI Contract v1
basic:
  name: str                    # 必填
  gender: str | null           # 可选
  avatar_url: str | null       # 可选，claw:// 协议
education:
  - school: str                # 必填
    degree: str                # 必填
    major: str | null
    start_date: str            # 必填，YYYY-MM 格式
    end_date: str | "至今"     # 必填
    courses: list[str] | null  # 可选
work_experience:
  - company: str
    position: str
    start_date: str
    end_date: str | "至今"
    bullets: list[str]         # 每条 40-80 字
project_experience: [...]
extra_sections:                # 弱字段
  awards: list[str] | null
  languages: list[str] | null
  hobbies: list[str] | null
```

### 关键决策 1：区分主字段与 extra_sections

- **主字段**（教育/工作/项目）：所有模板必渲染
- **extra_sections**（奖项/语言/爱好）：模板可选择性渲染

**为什么**：
- 主字段的模板差异只是"排版顺序"
- 弱字段（extra_sections）不同模板差异很大（学术模板不放爱好、创意模板可能放）

**协作**：与 11197109 的"降级 extra_sections 静默丢失"修复配套。

### 关键决策 2：日期用 canonical form

`YYYY-MM` 或 `至今`——就这两种。

**为什么**：15+ 模板可能用不同显示方式（"2020.03" / "2020 年 3 月"），但**存储层必须只有一种**。

渲染时按需转换，与配套的三层防御（01 号文档）归一化层配合。

### 关键决策 3：向后兼容策略

契约版本化：
- v1 → v2 新增字段：默认值兼容，老模板忽略新字段
- v2 → v1 删除字段：**禁止**，只能标记 deprecated
- 字段改语义：**禁止**，必须新字段 + 迁移

## 15+ 模板矩阵

### 分类

| 类别 | 模板 | 特点 |
|:---|:---|:---|
| **技术型** | 3-4 套 | 突出技术栈、GitHub / 项目链接 |
| **学术型** | 2-3 套 | 论文、导师、Academic CV |
| **通用型** | 5-6 套 | 标准商务、时间线、双栏 |
| **创意型** | 2-3 套 | 配色、图标、非标准布局 |
| **Master Profile** | 1 套特殊 | 学生个人档案（不同于简历） |

### 模板层实现

每个模板 = **一份 CSS + 一份 Jinja 结构**（复用共享组件）：

```
resume_templates/
├── shared/            ← 共享组件（教育块、工作块）
├── modern_dark/
│   ├── template.html  ← Jinja 结构
│   └── styles.css     ← 差异化样式
├── academic_cv/
│   └── ...
└── ...
```

**核心不变量**：所有模板都从**同一个 AI 契约**渲染。

### 新模板的成本

- **不需要**：动 LLM Prompt、改数据结构、修 DOCX/PDF 核心代码
- **只需要**：一份 CSS + Jinja（约 100-300 行代码）

---

## 三种输出格式共享上层

### 关键设计：渲染分层

```
AI 契约（稳定）
    ↓
渲染适配层（把契约转成中间 IR）
    ↓
────────────────────────────
HTML 渲染   DOCX 渲染   PDF 渲染
    ↓          ↓          ↓
resume_html  python-docx  weasyprint
```

**IR（中间表示）**：把契约映射为"通用文档结构"（章节、段落、列表、表格），再让各格式各自渲染。

**收益**：
- 15 模板 × 3 格式的 45 个组合，共享上层逻辑
- 每种格式的核心代码只有一份

### 与 11197109 的协作

- 11197109 的 `04_html_to_word.md`（LibreOffice 方案）是本方案 DOCX 的另一路径
- 两条路径互补：结构化数据 → python-docx（本人主链）；富格式 HTML → LibreOffice（11197109 副链）

## 量化验证与效果

| 指标 | 无契约 | 有契约 |
|:---|:---|:---|
| 新增一个模板成本 | 改 LLM prompt + 数据结构 + 3 种渲染代码（~周） | **100-300 行 CSS/Jinja（~小时）** |
| LLM prompt 修改影响面 | 所有模板都可能挂 | **契约层拦住** |
| 15 模板×3 格式的耦合点 | 675 处 | **~50 处**（分层） |

## 方法论抽象与迁移

### 中间契约的三个价值

1. **解耦上下游**：LLM 侧和渲染侧独立演进
2. **稳定的 API**：契约是团队协作的"公共接口"
3. **可测试性**：契约层可以独立造样本、测试

### 与"数据契约"运动的关系

现代数据工程有个概念叫 **Data Contract**（Data Mesh 相关）——本设计是其在 LLM 应用中的实践。

### 可迁移场景

| 场景 | 迁移点 |
|:---|:---|
| **AI 应用 + 多渲染** | 完全适用 |
| **多前端复用同一后端** | 契约 = 前后端合约 |
| **数据仓库表设计** | 稳定契约 + 多下游消费 |
| **微服务 API** | Interface segregation |

### 反例警示

- **反例 1**：不建契约，LLM 输出直接进模板 → 改一次 prompt 45 个模板全挂
- **反例 2**：契约字段过多细节 → 变成"模板专属字段"，失去解耦价值
- **反例 3**：不做版本化 → 无法向前兼容

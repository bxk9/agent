# 12 · 错题本领域建模与四方业务闭环

> **作者**：yitong · **场景**：错题本作为面试系统的记忆中枢

---

## 一句话摘要

把"错题"从"某次面试的附属产物"升级为**独立领域实体**，用统一数据模型贯穿**语音面试 → 复盘 → 错题本 → mock 面试**四个业务场景，形成"练→错→复→再练"的闭环，是我在系统架构层面最完整的一次 DDD 实践。

## 背景与问题定义

### 初版设计的痛点

**v1（错题作为面试附属）**：
```
面试 session
    ├── 对话记录
    ├── 评分
    └── 错题列表  ← 附属字段
```

问题：
- 复盘想看"所有错题" → 要扫全部面试
- mock 面试想"针对错题练" → 无从查询
- 用户跨会话看"我常错什么" → 做不到
- 错题的"知识点标签、掌握度"无处安放

### v2：错题本一等公民

```
error_book_v2 (聚合根)
    ├── question：具体题目
    ├── user_answer：用户答案
    ├── correct_answer：标准答案
    ├── knowledge_tags：知识点标签
    ├── mastery_level：掌握度（1-5）
    ├── review_count：复习次数
    ├── source_session_id：来源面试
    └── created_at / last_reviewed_at
```

## 四方业务闭环

```
       ┌─────────────────┐
       │  语音面试        │
       │ （生产者）       │
       └────────┬────────┘
                │ 生成错题
                ↓
       ┌─────────────────┐
       │  error_book_v2  │◀───┐
       │  （聚合根）      │    │
       └────────┬────────┘    │
        ┌───────┼────────┐    │
        ↓       ↓        ↓    │
    ┌───────┐┌───────┐┌───────┴┐
    │ 复盘 ││Master ││ mock  │
    │      ││Profile││ 面试  │
    │(消费)││(消费) ││(消费+ │
    │      ││       ││ 生产) │
    └───────┘└───────┘└───────┘
```

### 场景 1：语音面试（生产者）

- 面试结束后 → LLM 判定用户答错的题 → 写入 error_book_v2
- 关键：**知识点标签由 LLM 自动打**，避免手工分类

### 场景 2：复盘（消费者）

- 展示"本次面试错题" + "历史相似错题"
- 用户能看到"这个知识点你已经错第 3 次了"
- 掌握度实时更新

### 场景 3：Master Profile（消费者）

- 用户档案 = 简历 + 错题本聚合视图
- "常错知识点" 作为用户能力画像
- 与 11099826 的 Master Profile 联动

### 场景 4：mock 面试（消费+生产）

- 消费：可指定"针对我的错题练习"→ 从 error_book_v2 取题
- 生产：mock 面试再次答错 → 更新 review_count 与 mastery_level

---

## 关键决策

### 决策 1：错题聚合根按 user_id 分区

- 主分区 key = user_id
- 支持跨 session 查询（"我所有的错题"）
- 与司棋的 user 中心化架构（10 号文档）对齐

### 决策 2：knowledge_tags 用 LLM 自动打

- 手工分类：用户不会做、面试官也懒得打
- 关键词提取：太粗
- **LLM 提取 3-5 个知识点标签**：语义精准、可聚合分析

### 决策 3：mastery_level 用简化 SM-2 算法

- 复习次数少 + 最近又错 → 掌握度低
- 复习次数多 + 长期没错 → 掌握度高
- 与 Anki 的 SM-2 简化版一致，但不搞完整 spaced repetition

### 决策 4：v1 → v2 迁移用双写

- v2 上线后同时写 v1 和 v2
- 观察 2 周确认 v2 稳定
- 切断 v1 写入、保留 v1 只读
- 全部迁移完成后下线 v1

## DDD 视角的分析

### 实体识别

| 概念 | 类型 | 理由 |
|:---|:---|:---|
| **error_book_v2** | 聚合根 | 有生命周期、有一致性边界 |
| **error_item** | 实体 | 有身份（id）、可修改 |
| **knowledge_tag** | 值对象 | 无身份、可替换 |
| **mastery_level** | 值对象 | 通过计算得出 |

### 聚合边界

- 错题本内部一致性：mastery_level 更新时 review_count 也要更新（原子）
- 与其他聚合的交互：**只通过 user_id 引用**、不直接嵌入其他聚合

### 领域事件

- `ErrorItemCreated`（面试完成后触发）
- `ErrorItemReviewed`（mock/复盘触发）
- `KnowledgeTagsUpdated`（LLM 打标后触发）

事件驱动 → 复盘/Master Profile 等消费者订阅事件更新自己的视图。

| 指标 | v1 | v2 |

| 查询"用户所有错题" | O(N session 扫描) | **O(1) 直接查错题本** |

| mock 面试"针对错题练" | 不支持 | **支持** |

## 方法论抽象与迁移

### 从"附属字段"到"一等公民"的判断标准

一个数据结构应升级为独立实体，如果它满足：
1. **有多个消费者**（>2 个业务场景要读）
2. **有独立的生命周期**（不随宿主消失）
3. **有跨聚合的查询需求**（如"用户所有..."）
4. **有独立的业务逻辑**（如 mastery_level 计算）

错题本四条全中。

### DDD 在 AI 系统中的应用

传统 DDD 多用于 CRUD 业务系统，但在 AI 系统中同样适用：
- LLM 生成的"结构化输出" ≈ 领域事件
- 用户画像/记忆库 ≈ 聚合根
- Prompt 中的角色/工具 ≈ 领域服务

### 可迁移场景

| 场景 | 迁移点 |
|:---|:---|
| **教育 App 的错题本** | 完全同构 |
| **健身 App 的训练记录** | 用户级持久记忆 |
| **代码 review 系统的 issue 库** | 一等公民 + 多消费者 |
| **CRM 的客户画像** | user_id 主分区 + LLM 打标 |

### 反例警示

- **反例 1**：一开始把错题当附属 → 后期跨场景需求出现要大重构
- **反例 2**：不做 v1/v2 双写迁移 → 数据丢失或不一致
- **反例 3**：knowledge_tag 用固定枚举 → 无法覆盖新知识点

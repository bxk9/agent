# 04 · 提示词工程实战：复盘 Skill 五大原创铁律

> **作者**：陈乾 · **场景**：面试复盘业务

---

## 一句话摘要

面对 LLM 复盘输出"漏题 / 编数字 / 越权评价 / 跳过 skill / ASR 误识"五类问题，我在同一份复盘 Skill 上迭代 15+ 次，抽象出**"数字铁律 / 硬闸 / 全覆盖 / 事实围栏 / 同音变体"五大原创约束**，配合**"Skill 软约束 + 交付前自检 + 工具入库拦截"三层拦截**，让复盘输出从"看运气"变成"看架构"。

## 背景与问题定义

### 业务场景

用户完成一场模拟面试后，系统调用 **面试复盘 Skill**，输出复盘报告（HTML），包含：
- 整体盘点（策略、节奏、致命问题）
- **逐题分析**（全覆盖所有题目）
- 亮点 & 改进建议
- 引导下一步（重练 / 错题本 / 下次注意）

### 五类痛点

| 类型 | 表现 | 治理前发生率 |
|:---|:---|:---:|
| **漏题** | 说 5 题只分析 3 题 | ~20% |
| **数字幻觉** | 编造"提升 30%"这类数字 | ~40% |
| **越权评价** | 用"优秀""良好"等主观档位词 | ~60% |
| **跳过 Skill** | 转写后直接输出复盘，绕过 Skill | 偶发 |
| **ASR 同音误识** | React → 日刻，K8s → 卡8s | 高频 |

## 方案演进与关键决策

### 五大原创铁律

#### 铁律 1：整体盘点前置

**问题**：模型倾向逐题输出，缺全局评估
**约束**：Skill 强制第一节输出整体盘点

**面试可讲**：
- 为什么把"整体"放前面？——引导 LLM 先"抽象再细节"，符合专业面试官思路
- Reasoning 模型天然做这个，但普通模型需要 skill 引导

#### 铁律 2：逐题全覆盖 + 交付前自检

**问题**：模型跳题、并题
**三层拦截**：
- Skill 层：硬约束"必须覆盖所有题目"
- 交付前：自检声明题数 vs 实际逐题分析块数
- 工具层：`save_review_report` 校验漏题 → 拒绝入库

**面试可讲**：
- 为什么单靠 Skill 不够？——LLM 会说"好的我会覆盖"然后还是漏
- 交付拦截 + 工具拒绝 = 硬保障

#### 铁律 3：数字铁律

**三段式规则**：
1. **无数字必占位**：`[数据待补]`（不许无中生有）
2. **有数字必对齐原话**（不许改动）
3. **背景/情景数字禁编造**（不许"看起来合理"）

**反例注入**：
```
【反例】用户没提到用户量，模型输出"服务了 1000 万用户"
【正例】用户没提到用户量，输出"服务了 [数据待补] 用户"
```

**面试可讲**：
- 数字幻觉是 LLM 最典型的"看似合理"幻觉
- **反例注入**是提示词工程的核心技巧（Few-shot 反例比正例更有效）

#### 铁律 4：硬闸机制

**问题**：转写后模型跳过复盘 skill 直接输出
**方案**：业务动作前置硬闸——检测到"复盘"场景**必须**走 skill
**收窄**：仅约束复盘场景，不干扰简历/mock 面试其它流程

**面试可讲**：
- 为什么要"硬闸"？——软约束不够时的兜底
- 为什么要"收窄"？——避免约束误伤其他场景（工程稳健性）

#### 铁律 5：同音变体处理

**问题**：ASR 误识（React → 日刻、K8s → 卡8s、Vue → 与）
**约束**：
- 专名同音变体按误识还原
- **原话保原样**、分析用标准术语
- 不提"转写误差/统一术语"（避免用户以为系统 bug）

**面试可讲**：
- ASR + LLM 联合链路的特有问题
- 如何**优雅**处理输入噪声（不修改用户输入，但在分析层做还原）

### 三层拦截总设计

```
┌──────────────────────────────────────┐
│ Layer 1: Skill 软约束                 │
│ - 五大铁律以约束条款形式写入 Skill      │
│ - LLM 尽量遵守（软）                   │
└───────────────┬──────────────────────┘
                ↓
┌──────────────────────────────────────┐
│ Layer 2: 交付前自检                    │
│ - 题数对齐                             │
│ - 关键字段完整性                        │
└───────────────┬──────────────────────┘
                ↓
┌──────────────────────────────────────┐
│ Layer 3: 工具层入库拦截                 │
│ - save_review_report 拒绝漏题产物      │
│ - 记录漏题原因供 skill 迭代             │
└──────────────────────────────────────┘
```

## 算法/工程实现细节

### Skill 结构示范

```markdown
# 复盘 Skill

## 硬约束（数字铁律）
- 用户原话没提及的数字，一律用 `[数据待补]` 占位
- 反例：❌ "服务了 1000 万用户"（编造）
- 正例：✅ "服务了 [数据待补] 用户"

## 硬约束（全覆盖）
- 逐题分析必须覆盖所有 {{N}} 道题
- 交付前对齐题数，缺失即失败

## 硬约束（同音变体）
- ASR 误识别（如 React 识为"日刻"）按标准术语还原
- 原话展示时保留原样，分析部分使用标准术语
- 禁止提及"转写误差"或建议"统一术语"

## 场景硬闸
- 本 Skill 仅在"面试复盘"场景使用
- 简历生成 / mock 面试进行中 → 禁用
```

### 交付前自检伪代码

```python
def pre_delivery_check(report_html, expected_n):
    per_question_blocks = extract_per_question(report_html)
    if len(per_question_blocks) != expected_n:
        return False, f"expected {expected_n} but got {len(per_question_blocks)}"
    if contains_fabricated_numbers(report_html):
        return False, "fabricated_numbers"
    if uses_forbidden_tier_words(report_html):
        return False, "forbidden_tier_words"
    return True, "ok"
```

### 工具层入库拦截（08-07）

```python
def save_review_report(html, questions, ...):
    ok, reason = pre_delivery_check(html, len(questions))
    if not ok:
        log_missing_reason(reason)  # 记录到监控
        raise DeliveryRejected(reason)  # 拒绝入库
    ...
```

## 方法论抽象与迁移

### Prompt 工程"三段式"

1. **业务约束**：从业务视角先提"该做什么、不该做什么"
2. **反例驱动**：踩过的坑写成反例注入 skill
3. **收窄边界**：一旦发现约束误伤其它场景，立即加"场景守卫"

### 通用治理原则

| 原则 | 说明 |
|:---|:---|
| **软 + 硬 双层** | Skill 软约束 + 工具硬拦截 |
| **不做猜测补全** | 拒绝比错误更重要（宁可占位不要编造） |
| **反例 > 正例** | Few-shot 反例比正例更有效（LLM 更善于模仿"避免哪些"） |
| **场景守卫** | 约束要精准，不要污染其他链路 |
| **拦截前置日志** | 拒绝时记录原因，形成迭代闭环 |

### 可迁移场景

| 场景 | 迁移点 |
|:---|:---|
| 简历生成的 AI 标记 | 11099826 的三层防御方法论一脉相承 |
| 代码 Agent 的产物校验 | 数字铁律 → 代码断言完整性 |
| 医疗 / 法律等专业领域 | 事实围栏 + 拒绝式补正 |

## 一、背景

局部简历优化场景（"把自我评价改成适合软件测试岗位"）在优化前实测总耗时 **154.5s**，用户体感极差。目标：在保证正确性的前提下，将端到端时长压至 100s 以内。

## 三、方案迭代（v1.0 → v1.7）

### v1.0 初版：Prompt 强化 + scoped_content 精简合并
- 效果：**部分失效**。Prompt 无法可靠约束 LLM 遵从率。
- 教训：单纯"引导 LLM 做对"不可靠。

### v1.1 评审修正
- **关键发现**：原 P0-1 "框架层自动降级" 预期收益 -30~38s 是**时序错误**。
  - 降级发生在 `_render_sync()` 入口，此时 LLM 思考 #5 已完成，无法追溯性省时间。
  - 实际收益仅 **-0.2~1s**（只省了兜底闸的 200ms）。
- **新增 P0-B**：JSON Schema 动态修改，在 LLM 生成阶段就限制它不生成非目标字段。
  - 这是**唯一**能真正减少生成耗时的路径。

### v1.2 落地实施
| 项 | 状态 | 收益 |
|----|------|------|
| P0-A 框架层自动降级（正确性兜底） | 现有代码已覆盖 | -0.2~1s |
| P0-C L1 Prompt 并行化引导 | 已实施 | 概率性 -14~34s |
| P0-C L3 框架层预调用兜底 | 已实施 | 确定性 -7~10s |
| P0-B 方案 C 描述层警告 | 已实施 | 隐式引导 |
| P1 精简回复模板 | 已实施 | -10~15s |

### v1.3 第二次实测：177.4s（反而增加！）
- 精简合并路径生效（`resume_content` 为空，`scoped_content` 已使用）
- 但发现**新瓶颈**：思考 #4 花 99.5s，其中 ~40s 用于从纯文本提取 `base_resume_json`
- 决策：新增 **P0-D**：让 `parse_resume_file` 直接返回结构化 JSON

### v1.4 P0-D 实施
- 修改 `_format_result`，同步执行 `_deferred_extract`，返回值内嵌 `resume_json`
- 预期收益：-35~40s

### v1.5 P0-D 回滚（教训）
- 第三次实测发现同步提取耗时 **70s** 且 JSON 解析失败
- `parse_resume_file` 从 0.3s 暴增到 70.6s，回退到异步
- 教训：**任何路径变更都必须实测验证，不能靠预期外推**

### v1.6 附带修复
- `extractor.py` 的 "Extra data" JSON 解析错误 → 用 `json.JSONDecoder().raw_decode()` 只取第一个 JSON
- `blueclaw_chat.py` / `vivo_chat.py` 的 "list index out of range" → 空 `choices` 防御
- 增加 LLM 原始返回内容前 500 字符日志

### v1.7 附带修复
- DOM 局部替换：`honors` 别名映射从单数 `honor` 改为复数 `honors`，与 LLM 的 scope 保持一致

## 五、方法论沉淀

### 5.1 时序识别
在推演任何优化收益前，先画时间轴：
- 该优化发生在**哪一步之前 / 之后**？
- 是否可能"追溯性"减少已发生的耗时？（答：不能）

### 5.2 事前约束 vs 事后兜底
| 类型 | 收益 | 可靠性 | 举例 |
|------|-----|-------|------|
| 事前约束（Schema） | 高（真正减耗时） | 中（依赖 LLM 适配） | P0-B |
| 事后兜底（代码降级） | 低（<1s） | 高（确定性） | P0-A |

**结论**：两者必须配合。事前约束负责提效，事后兜底负责保正确。

### 5.3 双区间预期
不再报"预期收益 -30s"，而是报 **"乐观 -34s / 悲观 -14s"**，明确说明差异来源（LLM 遵从概率）。

### 5.4 每一次实测都是学习
- 第一次实测 154.5s → 找到 3 大瓶颈
- 第二次实测 177.4s → 意外发现"精简后反而增加"，找到隐藏瓶颈（JSON 提取）
- 第三次实测触发 P0-D 回滚 → 学到"同步方案未必比异步快"

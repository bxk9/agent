## 二、战役 A：语音链路 `usage_tokens` 埋点（5 次迭代收敛）

**症状**：语音会话结束后 usage 上报为空或字段缺失，导致计费与配额统计异常。

**根因链**（分 3 层）：
1. **L1（协议层）**：vivo `/chat/stream` 的 usage 只在最后一个 chunk 出现，且可能为空
2. **L2（Python 兼容性）**：空 `choices` 列表触发 `list index out of range`
3. **L3（业务层）**：主 Agent 与语音 session 的 task_id 不一致，埋点被拆成两份

**修复序列**：
```
07-29 19:37  fix usage_tokens埋点bug            ← L1：定位到最后 chunk 才有 usage
07-30 21:45  fix usage-tokens bug               ← L1：修 None 判断
07-30 21:52  fix usage-tokens bug               ← L2：加空 choices 防御
07-30 21:58  fix usage-tokens bug               ← L2：路径切换后再触发
07-30 22:06  fix usage-tokens bug               ← L3：task_id 关联
08-05 09:52  fix usage 埋点                     ← 端到端复盘后收敛
```

**教训**：涉及第三方流式协议的埋点，必须在 `finally` 块统一 flush，而不是依赖某一帧的到达。

## 三、战役 B：JSON 解析 "Extra data"（涉及 3 个文件）

**症状**：LLM 返回结果被 `json.loads()` 抛出 `Extra data:line 1 column N`，导致简历结构化提取失败。

**根因**：
- 部分模型（尤其在思考模式）会返回多个 JSON 对象，或 JSON 后追加"以上就是..."的自然语言尾巴
- `json.loads()` 严格要求整个字符串是单一 JSON

**修复**（v1.6，见 `docs/design/20260729_LLM思考耗时优化...md`）：
```python
# 之前
data = json.loads(raw)

# 之后
decoder = json.JSONDecoder()
data, _ = decoder.raw_decode(raw.lstrip())
```

**附加动作**：在 `extractor.py` 加日志记录 LLM 原始返回前 500 字，方便复现。

**波及文件**：`extractor.py`、`blueclaw_chat.py`、`vivo_chat.py`（同一根因，三处修复）。

## 四、战役 C：DOM 局部替换 honors 模块失效

**症状**：局部优化 `scope=["honors"]` 时，简历"荣誉证书"模块的改写内容未被应用到最终 HTML。

**根因分析**（罕见的"命名映射不一致"）：
- 原始简历标题 "荣誉证书" 通过 `_TITLE_ALIAS_TO_KEY` 被映射为 `"honor"`（单数）
- 但 LLM 传入的 `scope=["honors"]`（复数，来自 skill 定义）
- 判断 `module_key not in scope` 为 True，跳过替换

**修复**（v1.7）：
```python
# app/tools/resume_sidebar/pipeline.py
_TITLE_ALIAS_TO_KEY = {
    "荣誉证书": "honors",   # 原为 "honor"
    "荣誉奖项": "honors",
    ...
}
```

**教训**：跨模块命名约定必须在文档中固化。参见 `../05_references/40_key_conventions.md`。

## 五、战役 D：语音"150 分钟无限输出"

**症状**：某次语音面试用户提到"面试 150 分钟"，LLM 后续把每道题的作答时间都描述为 150 分钟。

**根因**：
- LLM 未理解"150 分钟"是**整场面试预计时长**，误当成每题作答时长
- Prompt 未明确"面试预计时长"的语义边界

**修复**（08-06 `优化语音输出150分钟的问题；解决模型未遵循json的问题`）：
- Prompt 中明确"总时长 ≠ 单题时长"
- 单次输出配额约束
- 附带修复"模型未遵循 json"（在同一提交中一并处理）

## 六、战役 E：VLM 异常降级与缓存污染

来源：`docs/fix/20260806_VLM异常降级与缓存污染防护_根因分析与修复方案.md`

**症状**：VLM（视觉大模型）解析简历时偶发异常，且异常结果被写入缓存，后续所有请求都命中脏缓存。

**修复要点**：
1. VLM 调用增加 try-except，异常时不写缓存
2. 缓存 key 加入 VLM 响应 hash，避免脏数据穿透
3. 降级到 fitz 纯文本解析路径

## 七、战役 F：三层防御架构（08-01）

来源：`docs/fix/20260730_端测日志根因修复方案_三层防御架构.md`

针对"端测日志"暴露的多个数据一致性问题，我参与设计了**三层防御架构**：

```
┌─────────────────────────────────┐
│ L1 事前约束（Schema/Prompt 层）  │  → 引导 LLM 做正确的事
├─────────────────────────────────┤
│ L2 事中兜底（工具层校验）        │  → 校验参数、修正异常
├─────────────────────────────────┤
│ L3 事后修复（渲染层 diff 补标）  │  → 兜底闸 + DOM 局部替换
└─────────────────────────────────┘
```

任意一层失败，下一层继续保护正确性。这是本项目应对 LLM 不可靠性的核心方法论。

## 九、方法论沉淀

从 34 篇复盘文档中提炼的通用范式：

1. **症状 → 根因链**：不满足于"改一行代码通过"，一定追到底层协议或语义
2. **根因分层**：区分 L1/L2/L3，每层单独修复，避免"一刀切"
3. **修复必带回归**：每次修复必写验证清单
4. **归档到 docs/**：所有修复都有 markdown 文档，便于后来者复用

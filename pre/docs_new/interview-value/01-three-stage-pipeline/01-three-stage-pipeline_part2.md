1. **"早退是数据不是异常"**：将控制流从异常机制中剥离，用 `turn.stop()` 替代 `raise ExitException()`
2. **单一真值来源**：TurnState 收敛 14 个散落局部变量，杜绝"多处赋值 + 兜底覆盖"
3. **薄壳编排器**：HostAgent 只负责串联，业务逻辑集中在阶段函数
4. **引用共享的 ModelSession**：切换后各阶段读到即新模型，无需回传

### 4.2 难点攻克

| 难点 | 解决方案 |
|---|---|
| 8 处 raise 跨 3 个方法层级 | 逐处对照行号改造，每步验证行为等价 |
| 14 个局部变量的等价替换 | 纯机械替换不改控制流，逐字段对照 |
| try/finally 收口重构 | 明确划分：崩溃走 except，业务 error 走 turn.error，二者互斥 |
| 闭包 `_write_result` 迁移 | 阶段抽取时一并迁移，逐个 Task 验证 |

### 4.3 设计权衡

| 决策 | 选择 | 理由 |
|---|---|---|
| 阶段函数是否依赖 HostAgent | 否，纯函数 | 可独立测试和替换 |
| TurnState 是否包含请求体 | 是，body 引用 | 避免多处传递 |
| geocode 是否并行预取 | 否，串行 await | 高流量下并行对 QPS 无提升，简化复杂度 |
| 阶段函数是否 yield | prepare 不 yield，infer/finalize yield | 统一签名但按需使用 |

## 6. 面试要点

### 6.1 核心问题

**Q: 为什么选择三阶段而不是其他架构？**

A: 三阶段的划分基于业务语义的自然分界：
- prepare：准备输入（工具集、提示词、运营干预）
- infer：核心推理（模型调用、验证、重试）
- finalize：输出处理（去重、推荐位、SSE 下发）

每个阶段的输入输出明确，可独立测试和替换。相比更多阶段（如 5 阶段），三阶段在清晰度和复杂度之间取得了最佳平衡。

**Q: TurnState 的设计考虑了哪些因素？**

A: 
1. **单一真值来源**：所有阶段只写 TurnState，finalize 只读 TurnState
2. **控制信号**：should_stop/stop_reason/error 取代 ExitException
3. **可扩展性**：新增字段不影响已有阶段
4. **埋点内嵌**：StatCollector 作为字段，各阶段独立写入

**Q: 如何保证重构过程中的行为等价？**

A: 
1. **分步提交**：11 个 Task，每个 Task 保持行为等价
2. **两个 PR**：PR1 控制流改造，PR2 结构抽取
3. **冒烟测试**：每个 Task 后用场景 query 验证
4. **逐处对照**：8 处 raise 逐行改造，不遗漏

### 6.2 延伸问题

**Q: 如果要新增一个阶段（如 post_infer），怎么做？**

A: 在 infer 和 finalize 之间插入新的 `_stage_post_infer`，只需：
1. 创建 `stage_post_infer.py`
2. 在 `process()` 中 `if not turn.should_stop:` 后调用
3. 不碰其他阶段代码

**Q: TurnState 的线程安全性如何保证？**

A: Python 的 asyncio 是单线程事件循环，同一时刻只有一个协程在执行，不存在并发写入问题。TurnState 的生命周期是单轮请求，请求结束后即销毁。

**Q: 如果阶段函数之间需要共享临时数据怎么办？**

A: 两种方案：
1. 写入 TurnState（推荐，可追踪）
2. 通过函数返回值传递（仅限相邻阶段）

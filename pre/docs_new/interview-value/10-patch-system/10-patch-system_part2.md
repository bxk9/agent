5. **自定义触发器**：支持复杂业务逻辑的触发条件
6. **热更新支持**：通过配置中心实时下发规则

### 4.2 难点攻克

| 难点 | 解决方案 |
|---|---|
| 提示词过长 | 200 字硬校验，超限静默跳过 |
| 触发条件复杂 | 7 种触发器 + 自定义触发器 |
| 规则冲突 | 按注册顺序执行，后者覆盖前者 |
| 热更新风险 | validator 校验 + fallback 兜底 |

### 4.3 设计权衡

| 决策 | 选择 | 理由 |
|---|---|---|
| 提示词长度限制 | 200 字硬校验 | 防止注入过长内容影响性能 |
| 规则冲突处理 | 后者覆盖前者 | 简单明确，易于理解 |
| 自定义触发器 | 注册表模式 | 灵活扩展，不修改核心代码 |
| 白名单校验 | disable_prompt_modules | 防止禁用关键模块 |

## 6. 面试要点

### 6.1 核心问题

**Q: 为什么设置 200 字硬校验？**

A: 200 字硬校验的设计考量：
1. **性能保护**：过长的提示词会增加 system_prompt 长度，影响模型推理速度
2. **定位明确**：Patch 定位为"轻量引导"，长策略应投仲裁系统
3. **防止滥用**：硬校验防止运营人员无意中注入过长内容
4. **全局一致**：200 字限制对全部 74 个 Patch 生效，保证一致性

**Q: Patch 系统与仲裁系统的分工是什么？**

A: 明确分工，避免重叠：

| 维度 | Patch 系统 | 仲裁系统 |
|---|---|---|
| 定位 | 轻量引导 | 产品策略仲裁 |
| 策略长度 | 200 字以内 | 无限制（MD 文件） |
| 触发条件 | 7 种触发器 | 工具共现 + 请求特征 |
| 干预动作 | 7 种动作 | 仅注入提示词 |
| 适用场景 | 工具注入/剔除/模型切换 | 能力重叠工具的选择 |

**Q: 自定义触发器的设计思路是什么？**

A: 自定义触发器解决"声明式配置无法表达的复杂逻辑"：
1. **注册表模式**：通过装饰器注册，不修改核心代码
2. **统一接口**：所有触发器接收 (query, body, patch) 参数
3. **灵活扩展**：运营人员可以请求开发人员添加新的自定义触发器
4. **安全隔离**：触发器异常不影响其他 Patch 规则

### 6.2 延伸问题

**Q: 如果要新增一个 Patch 规则，怎么做？**

A: 两种方式：
1. **本地配置**：在 operations/patches/configs/ 下添加 JSON 文件，重启生效
2. **配置中心**：通过配置中心下发，实时生效（推荐）

**Q: Patch 规则的执行顺序如何确定？**

A: 按注册顺序执行，后者覆盖前者：
1. 本地配置先加载
2. 配置中心覆盖本地配置
3. 同一 patch_id 的规则，后者覆盖前者

**Q: 如何监控 Patch 规则的效果？**

A: 通过日志和埋点：
1. **命中日志**：记录每次命中的 Patch 规则
2. **干预日志**：记录每次干预的具体动作
3. **效果指标**：工具选择准确率、用户满意度

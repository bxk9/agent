
### 4.2 难点攻克

| 难点 | 解决方案 |
|---|---|
| 验证失败阻塞主流程 | 异常降级为 PASS，保证主流程不中断 |
| 无限重试 | 双闸门（全局 + per-tag）防止无限重试 |
| 流式已发射无法回退 | 流式安全约束：已 yield 文本 token 禁止回退 |
| LLM 验证器超时 | 5s 超时，超时降级为 PASS |
| 新规则风险 | Dry-run 模式，观察期只记录日志 |

### 4.3 设计权衡

| 决策 | 选择 | 理由 |
|---|---|---|
| 验证器异常处理 | 降级为 PASS | 验证是"锦上添花"，不能阻塞主流程 |
| LLM 验证器超时 | 5s | 平衡验证质量和响应速度 |
| 重试次数限制 | 默认 1 次 | 避免过度重试影响用户体验 |
| Dry-run 默认开启 | 是 | 新规则需要观察期，降低风险 |

## 6. 面试要点

### 6.1 核心问题

**Q: 为什么选择三阶段验证而不是单一验证？**

A: 单一验证无法覆盖不同粒度：
- **逐工具验证**：检测单个工具的参数错误
- **批量验证**：检测跨工具的一致性问题
- **配置驱动验证**：支持热更新，快速响应新需求

三阶段验证覆盖从细粒度到粗粒度的所有场景。

**Q: 验证器异常时为什么降级为 PASS 而不是 FAIL？**

A: 验证是"锦上添花"，不能阻塞主流程：
- **降级为 PASS**：验证器异常时继续执行工具，可能有问题但不会中断用户请求
- **降级为 FAIL**：验证器异常时中断请求，用户体验差

设计原则：宁可放过错误，也不中断用户请求。验证器异常会记录日志，便于事后排查。

**Q: 重试机制的双闸门如何工作？**

A: 双闸门防止无限重试：
1. **全局闸门**：`retry_count >= max_retry`（默认 1 次），限制总重试次数
2. **per-tag 闸门**：`tag in _seen_tags`，防止同一 tag 无限重试

例如：
- 第一次重试：`tag="flash_hallucination"`，通过
- 第二次重试：`tag="flash_hallucination"`，被 per-tag 闸门拦截
- 第二次重试：`tag="param_format_error"`，通过（不同 tag）

**Q: Dry-run 模式的作用是什么？**

A: Dry-run 模式是新规则的观察期：
- **只记录日志**：不实际执行 DROP，避免误杀
- **观察效果**：通过日志分析规则的准确率和误杀率
- **降低风险**：确认规则无误后再关闭 Dry-run

### 6.2 延伸问题

**Q: 如果要新增一个验证器，怎么做？**

A: 只需 3 步：
1. 实现 `Validator` 接口（或继承 `RuleValidator`）
2. 在 `register_validators()` 中注册
3. （可选）在 `tools/mcp/validators/configs/` 中添加 JSON 配置

无需修改主流程代码，验证器自动生效。

**Q: LLM 验证器的成本如何控制？**

A: 通过以下措施控制成本：
1. **使用轻量模型**：Doubao-Seed-2.0-lite，成本低
2. **超时控制**：5s 超时，避免长时间占用
3. **按需启用**：只对高风险工具启用 LLM 验证
4. **缓存结果**：相同参数缓存验证结果

**Q: 如何评估验证器的效果？**

A: 通过以下指标评估：
1. **拦截次数**：验证器拦截了多少次错误调用
2. **准确率提升**：拦截后工具调用准确率的提升
3. **误杀率**：验证器误杀了多少次正确调用
4. **重试成功率**：重试后工具调用的成功率

可以通过日志聚合系统（如 ELK）分析这些指标。

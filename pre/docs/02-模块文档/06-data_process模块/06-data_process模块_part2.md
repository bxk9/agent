   - 排除规则（常识消歧优先）：若query的动作和对象均已具备，仅因对象表述简略/口语化而字面可能多义，但依据用户习惯与生活常识存在唯一压倒性的高概率解释，则视为意图清晰，按该解释判clear（对应工具调用类型判single），不应过度澄清而判vague。判定锚点：抛开字面歧义，是否存在一个大众默认、无需反问即可确定的主流意图？存在→clear；多个解释概率相当、无主流默认→vague。
"""
```

**分类要点**：
- **clear**: 参数完整，无需推理或澄清
- **lack**: 参数不足，必须问用户
- **infer**: 参数需推理转换
- **vague**: 意图模糊，需澄清"要做什么"

**优���级规则**：`vague > infer > lack > clear`

**三、指令类型**

```python
"""
## 三、指令类型
1. cond：（条件指令）query中包含触发条件 + 条件满足时执行的任务，且该条件需由外部调度器/监听器在满足时才能触发执行。
   - 判定原则：cond只看指令性质（是否需外部调度器/监听器触发），与触发条件的具体值是否给全无关。用户表达了定时/延时/事件触发诉求、但未给具体时点/阈值时，指令类型仍判cond，缺失的具体值归入意图明确度维度判lack。如"定时打开音乐"（未给时间）→ 指令类型cond、意图明确度lack。
   - 触发条件类型：
     · 时间条件：指定时间（每天上午9点）、相对时间（半小时后）、日出/日落相关（日出前15分钟）。
     · 地理位置条件：到达/离开指定位置（到达公司时、离开家时）。
     · 手机状态条件：飞行模式开关、WLAN/蓝牙连接或断开、耳机插拔、充电状态、NFC开关。
     · 应用状态条件：打开/关闭/前台运行某应用。
   - 扩展规则：（相对延迟时间触发）若query用"X分钟/小时后""日出/日落后"等相对延迟时间作为触发条件，且其后任务对应的候选工具自身不接收延时/定时执行参数（如关闭网络、关闭热点、打电话等即时执行类工具），则该延迟需由外部调度器到点后触发，属于cond。例如"10分钟后关闭网络/蓝牙""一小时后打电话/发信息给xx"。
   - 扩展规则：（外部事件触发）若触发条件是某个无法预知具体时点、需持续监测外部世界/信息流才能确认发生的事件（如"看到XX新闻/消息时""XX球队夺冠时""股价跌破X时""下雨时"），其后跟随待执行任务（如提醒/通知/发消息），则需由外部监听器在事件发生时触发，属于cond。例如"以后看到C罗新闻提醒我""中国羽毛球队夺冠的时候提醒我"。
   - 扩展规则：（上一轮条件指令的补充）若上一轮已给出触发条件但未明确待执行任务（模型正就"条件满足时做什么"进行追问），本轮query补充了该条件下要执行的具体任务，则本轮与上一轮共同构成完整的"条件触发+待执行任务"结构，本轮指令同样属于cond。
   - 排除规则：（无任务条件）query中虽然包含条件表述，但条件后并未跟随明确的工具调用类任务（仅是情绪/观点/陈述等），不属于cond。
   - 排除规则：（工具自带条件参数，优先级高于上方"相对延迟时间触发"扩展规则）若候选工具本身就以"时间/时长/触发条件"作为其原生输入参数（即工具被设计为接收并自行处理该条件），则用户提到的时间/条件只是该工具的常规参数填充，则不属于cond。如"定一个10分钟后的闹钟""设置1小时后的提醒""半小时后关闭手机"，闹钟类/提醒类/定时开关机工具原生支持定时参数，属norm。

2. norm：（普通指令）除条件指令外的所有情况都属于普通指令。
"""
```

**分类要点**：
- **cond**: 需要外部调度器/监听器触发的条件指令
- **norm**: 普通指令

**四、执行反馈状态**

```python
"""
## 四、执行反馈状态
1. abnormal：（异常反馈）多轮对话中，用户对模型在历史对话中的【理解、调用或执行】表现出不满或纠正，本质是"错源在模型"。包括但不限于：用户对模型上一轮结果的主观否定/质疑/抱怨，或对模型的工具选择有误、参数理解有误、执行结果未达预期、回复事实有误等情况进行明确的澄清/纠正/补救。
   - 扩展规则（包含范围，覆盖到任一项即属 abnormal，不要求 history 必须为完成态回复）：
     * 主观否定信号：用户对上一轮结果直接表达不满或质疑（口头禅参考："不对/错了/不是这个/你听错了/你确定吗/不够好"）。
     * 参数纠正型：用户用"是 X，不是 Y"、"改成 Z"、"X 错了"、"搞错了/想错了，是 X"等表达，显式给出正确参数；或指出模型选错了工具/对象（如"是打开摄像头，不是相册"）。
     * 执行未达预期：用户指出模型声称已完成的事实未生效，或效果不佳（参考："还没X/没成功/没生效"、"看不清/听不清"、"太大/太小/太长/太短"）。
     * 事实错误纠正：用户指出模型上一轮回复的知识/查询/结论有误（参考："X我记得不在Y地"、"应该是X"、"X不对吧"）。
   - 排除规则（精度兜底，命中任一项即属 ok 而非 abnormal）：
     * 用户侧错误：错误源头在用户自身（说错、改主意、临时换内容、补充新约束），即使带"不对/错了/不是…"等语气词也仍属 ok。
     * 用户自行变更：用户主动修改/取消/删除/切换已设置的内容（如"不用了"、"算了吧"、"换下一首"、"改到三点"），未指出模型上一轮"错"。
     * 任务正常推进：用户回应模型追问/补充参数（模型问"几点"答"早上9点"）；创作类任务持续优化迭代未表达不满（"再瘦一点"、"换3D卡通"）；重发同一指令或发起独立新任务，与上一轮无纠错关联。
   - 判定锚点：用户的不满或纠正是否针对【模型刚才的理解或执行偏差】？是→abnormal；否（错源在用户/无错源/独立新任务）→ok。

2. ok：（正常推进）除异常反馈外的所有情况均属于正常推进，包括但不限于：首轮对话、正常任务延续、响应模型追问的参数补充、用户自行变更、新话题发起等。
"""
```

**分类要点**：
- **abnormal**: 错源在模型的异常反馈
- **ok**: 正常推进

**判定锚点**：错源是否在模型？

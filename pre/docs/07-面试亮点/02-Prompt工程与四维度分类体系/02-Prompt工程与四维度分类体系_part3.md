**Case 10 —— 复合指令子任务缺参（定闹钟缺时间参数）→ 整体取最高档 lack**
历史对话:[]
当前query：打开网易云播放周杰伦，然后给我定个闹钟
Output: multi lack norm ok

**Case 11 —— 多任务含 vague 子任务 → 整体取最高档 vague**
历史对话:[]
当前query：调到10%，再放首歌
Output: multi vague norm ok

**Case 12 —— 条件指令（外部条件触发+待执行任务）→ cond**
历史对话:[]
当前query：等我到家了帮我把空调打开
Output: single clear cond ok

**Case 13 —— 完整动宾但多相似候选工具，方向不明 → pend+vague**
历史对话:[]
当前query：帮我买张票
Output: pend vague norm ok

**Case 14 —— 本轮的指令是对上一轮条件指令的补充，本轮视为cond → cond**
历史对话:
user:充电时帮我做点事
assistant:请问你想让我在充电时帮你执行什么操作呢？比如开启省电模式、调整屏幕亮度等，你可以具体说明一下~
当前query：帮我播放周杰伦的歌
Output: single clear cond ok
"""
```

### 4.3 示例设计要点

**要点1：对比示例**
- Case 5 vs Case 6：abnormal vs ok
- 区别：用户是否否定上一轮结果
- Case 5："不够好看" → 否定 → abnormal
- Case 6："想了下，还是换成" → 自行变更 → ok

**要点2：边界case**
- Case 4："到10%" → 意图模糊 → pend + vague
- Case 13："帮我买张票" → 多个候选工具 → pend + vague
- 区别：Case 4是修饰主体不明确，Case 13是动宾完整但工具不明确

**要点3：优先级规则**
- Case 10：multi + lack（部分子任务缺参）
- Case 11：multi + vague（部分子任务模糊）
- 说明：整体取最高档（vague > lack）

**要点4：强绑定规则**
- Case 2：qa → 强绑定 clear
- Case 3：unsupported → 强绑定 clear
- Case 4：pend → 强绑定 vague

**要点5：多轮对话**
- Case 5/6：历史对话影响执行状态判断
- Case 14：历史对话影响指令类型判断

## 5. 迭代优化过程

### 5.1 迭代方法论

**迭代流程**：
```
1. 收集错误case
   ↓
2. 分析错误原因
   ↓
3. 定位问题维度
   ↓
4. 修改Prompt（分类标准/规则/示例）
   ↓
5. 验证效果（测试集）
   ↓
6. 提交更新（记录变更原因）
```

**迭代原则**：
- **小步快跑**：每次只修改一个点，便于验证效果
- **数据驱动**：基于错误case分析，而非主观判断
- **回归测试**：每次修改后，验证整体准确率不下降
- **详细记录**：记录每次变更的原因和效果

### 5.2 关键迭代记录

#### 迭代1：V1.0 → V2.0（合并para和seq）

**问题发现**：
- para和seq的区分准确率只有82%
- 很多query既可能是para也可能是seq，难以判断
- 下游系统对para和seq的处理逻辑相同

**错误case分析**：
```
Query: "帮我查下屏幕上这首诗是谁写的，然后画一幅这个作者的肖像图"
标注: seq（先识别再绘图，有依赖关系）
模型输出: para（误判为并行）

分析：模型难以判断工具之间是否有依赖关系
```

**解决方案**：
- 合并para和seq为multi
- 简化分类标准，减少边界case

**效果**：
- 工具类型准确率：88% → 94%（+6%）
- 整体准确率：85% → 88%（+3%）

#### 迭代2：V2.0 → V3.0（添加扩展规则和排除规则）

**问题发现**：
- single的误判率较高（12%）
- 很多边界case没有明确规则

**错误case分析**：
```
Case 1:
Query: "播放匆匆那年"
标注: pend（可能是音乐/小说/影视）
模型输出: single（误判为单工具）

分析：播放类任务有多个候选工具，但用户意图是明确的

Case 2:
Query: "打开灯光"
标注: pend（可能是IoT灯/手电筒/屏幕亮度）
模型输出: single（误判为单工具）

分析：常识消歧，"打开灯光"通常指IoT灯
```

**解决方案**：
- 添加"播放类默认锚定"排除规则
- 添加"常识消歧"扩展规则

**效果**：
- single准确率：88% → 95%（+7%）
- pend准确率：90% → 93%（+3%）
- 整体准确率：88% → 92%（+4%）

#### 迭代3：V3.0 → V4.0（添加强绑定规则）

**问题发现**：
- chat/qa/unsupported的意图明确度经常误判为lack或infer
- pend的意图明确度经常误判为clear

**错误case分析**：
```
Case 1:
Query: "你好呀"
标注: chat + clear
模型输出: chat + lack（误判为参数不足）

分析：chat不需要参数，意图明确度应该是clear

Case 2:
Query: "到10%"
标注: pend + vague
模型输出: pend + clear（误判为意图清晰）

分析：pend本身就是意图模糊导致的
```

**解决方案**：
- 添加强绑定规则：
  - chat/qa/unsupported → 强绑定 clear
  - pend → 强绑定 vague

**效果**：
- 意图明确度准确率：89% → 95%（+6%）
- 整体准确率：92% → 94%（+2%）

#### 迭代4：V4.0 → V5.0（添加历史延续优先规则）

**问题发现**：
- 多轮对话场景下，工具类型经常误判
- 用户补充参数时，模型误判为新任务

**错误case分析**：
```
历史对话:
user: 帮我定个闹钟
assistant: 请问您想定几点的闹钟？
当前query: 早上8点
标注: single（延续上一轮的闹钟任务）
模型输出: qa（误判为知识问答）

分析：模型没有理解这是参数补充，而是当作新任务
```

**解决方案**：
- 添加"历史延续优先"规则：
  - 若history上一轮已锁定某工具，当前query默认视为该工具的参数补全或延续

**效果**：
- 多轮对话准确率：85% → 93%（+8%）
- 整体准确率：94% → 95%（+1%）

#### 迭代5：V5.0 → V5.1（优化异常反馈判定）

**问题发现**：
- abnormal的误判率较高（15%）
- 用户自行变更被误判为abnormal

**错误case分析**：
```
Case 1:
历史对话:
user: 帮我画一张漂亮女生的照片
assistant: 好的，已经生成了漂亮女生的图片
当前query: 想了下，还是换成帅气男生的照片吧
标注: ok（用户自行变更）
模型输出: abnormal（误判为异常反馈）

分析：用户没有否定上一轮结果，只是改主意了

Case 2:
历史对话:
user: 帮我画一张漂亮女生的照片
assistant: 好的，已经生成了漂亮女生的图片
当前query: 不够好看，帮我换一张颜值很高的女生的照片
标注: abnormal（用户否定上一轮结果）
模型输出: abnormal（正确）

分析：用户明确表达"不够好看"，是否定上一轮结果
```

**解决方案**：
- 细化abnormal的判定规则：
  - abnormal：用户明确否定上一轮结果（如"不对"、"错了"、"不够好"）
  - ok：用户自行变更（如"想了下"、"还是换成"）

**效果**：
- abnormal准确率：85% → 94%（+9%）
- 整体准确率：95% → 96%（+1%）

### 6.3 错误case分析

**剩余4%的错误主要分为以下几类**：

**类型1：边界case（占40%）**
```
Query: "帮我买个东西"
标注: pend（意图模糊）
模型输出: single（误判为单工具）

分析：query既可能是pend（不知道买什么），也可能是single（知道买什么，只是没说）
这种边界case本身就有歧义，人工标注也不一致
```

**类型2：工具定义理解错误（占30%）**
```
Query: "帮我翻译这段话"
标注: qa（知识问答）
模型输出: single（误判为单工具调用）

分析：模型没有理解translate工具属于qa范畴
需要优化工具定义的描述
```

**类型3：多轮对话理解错误（占20%）**
```
历史对话:
user: 帮我定个闹钟
assistant: 请问您想定几点的闹钟？
当前query: 算了，不定了吧
标注: ok（用户取消任务）
模型输出: abnormal（误判为异常反馈）

分析：模型没有理解"算了"是取消，而不是否定上一轮结果
需要添加更多取消场景的示例
```

**类型4：输出格式错误（占10%）**
```
模型输出: "single,clear,norm,ok"（逗号分隔）
期望输出: "single clear norm ok"（空格分隔）

分析：模型偶尔会忘记空格分隔的要求
需要强化输出格式的约束
```

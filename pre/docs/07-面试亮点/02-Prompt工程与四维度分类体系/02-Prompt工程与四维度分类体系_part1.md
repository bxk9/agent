# Prompt工程与四维度分类体系 - 面试亮点

> **核心价值**：设计并实现了四维度正交分类体系，通过50次Prompt迭代将分类准确率从85%提升到96%，构建了完整的Prompt工程方法论。

---

## 1. 项目背景与问题定义

### 1.1 业务场景

Dynamic Router需要对用户query进行智能路由，判断任务复杂度（easy/complex），以便下游系统决定处理策略。

**初始需求**：
- 输入：用户query + 历史对话 + 候选工具列表
- 输出：任务复杂度（easy/complex）
- 准确率要求：> 95%
- 延迟要求：< 500ms

### 1.2 初始方案的局限性

**V1.0方案（单维度分类）**：
```
直接输出：easy 或 complex
```

**问题分析**：
1. **可解释性差**：无法知道为什么判定为complex
2. **调优困难**：准确率不达标时，无法定位是哪个环节出错
3. **扩展性差**：业务规则变化时，需要重新训练模型
4. **边界case多**：很多query处于easy和complex的边界，难以判断

**关键洞察**：
- 任务复杂度是由多个因素共同决定的
- 需要拆解为多个独立的维度，分别判断
- 通过规则组合，提高可解释性和可维护性

### 1.3 优化目标

**核心问题**：如何设计一个多维度分类体系，既能准确判断任务复杂度，又具有良好的可解释性和可维护性？

**量化目标**：
- 整体准确率 > 95%
- 每个维度准确率 > 90%
- 输出格式100%正确
- 支持业务规则灵活调整

## 2. 四维度分类体系设计

### 2.1 设计原则

**原则1：正交性**
- 每个维度应该独立，互不干扰
- 避免维度之间的耦合和冗余

**原则2：完备性**
- 所有维度组合起来，能覆盖所有可能的场景
- 不存在无法分类的query

**原则3：可判定性**
- 每个维度的标签应该有清晰的定义
- 边界case有明确的判定规则

**原则4：业务相关性**
- 维度选择应该与业务决策强相关
- 能够直接指导下游系统的处理策略

### 2.2 维度选择与定义

经过多轮讨论和验证，最终确定了四个维度：

#### 维度1：工具调用类型（is_use_tool）

**定义**：判断用户query需要调用多少个工具，以及工具之间的关系

**标签设计**：
```
single      - 单工具调用（只需调用1个工具）
multi       - 多工具调用（需要调用多个工具）
qa          - 知识问答（无需调用工具，直接回答）
chat        - 闲聊（无需调用工具，情感交流）
pend        - 工具待确定（意图模糊，无法确定调用哪个工具）
unsupported - 工具不支持（当前工具列表无法支持）
```

**设计理由**：
- **single vs multi**：直接影响任务复杂度，multi需要任务编排
- **qa/chat**：无需工具调用，处理逻辑简单
- **pend**：需要澄清意图，增加交互轮次
- **unsupported**：需要特殊处理（如引导用户使用其他功能）

**演进历史**：
```
V1.0: single / multi / qa / chat / pend / unsupported
V2.0: 合并 para（并行）和 seq（串行）为 multi
V3.0: 新增 special（特殊工具，如美团、支付宝）
V4.0: special 重命名为 specific
```

**合并理由**：
- para和seq对下游系统来说都是multi，处理逻辑相同
- 区分para和seq需要更复杂的推理，准确率难以保证
- 合并后准确率提升3%

#### 维度2：意图明确度（is_intent_specific）

**定义**：判断用户query的意图是否清晰，参数是否完整

**标签设计**：
```
clear - 意图清晰（参数完整，无需推理或澄清）
lack  - 参数不足（缺少关键参数，需要用户补充）
infer - 参数需推理（参数不完整，但可以通过推理得到）
vague - 意图模糊（无法确定用户想要做什么）
```

**设计理由**：
- **clear**：可以直接执行，无需额外处理
- **lack**：需要向用户追问，增加交互轮次
- **infer**：需要调用推理模块，增加处理时间
- **vague**：需要澄清意图，可能需要多轮对话

**优先级规则**：
```
vague > infer > lack > clear
```

**设计理由**：
- vague最严重，需要澄清意图
- infer次之，需要推理但可能出错
- lack较轻，只需补充参数
- clear最理想，可以直接执行

#### 维度3：指令类型（is_special_instruction）

**定义**：判断用户query是否包含特殊的指令类型

**标签设计**：
```
norm - 普通指令（直接执行）
cond - 条件指令（需要满足条件后才执行）
```

**设计理由**：
- **cond**：需要条件判断和任务调度，增加复杂度
- **norm**：直接执行，处理逻辑简单

**演进历史**：
```
V1.0: norm / short（快捷指令）/ cond
V2.0: 移除 short（业务调整，不再支持快捷指令）
```

**移除理由**：
- 业务调整，不再支持快捷指令功能
- short的识别准确率较低（85%）
- 移除后整体准确率提升2%

#### 维度4：执行反馈状态（is_exe_success）

**定义**：判断用户query是否包含对上一轮执行的反馈

**标签设计**：
```
ok       - 正常推进（无反馈或正面反馈）
abnormal - 异常反馈（对上一轮执行结果不满意）
```

**设计理由**：
- **abnormal**：需要特殊处理（如道歉、重新执行、澄清）
- **ok**：正常处理流程

**判定规则**：
```
abnormal的判定条件（满足任一即可）：
1. 用户明确表达不满（如"不对"、"错了"、"不是这个"）
2. 用户纠正上一轮的参数（如"改成9点"、"不要这个"）
3. 用户重复相同的query（上一轮可能执行失败）

ok的判定条件：
1. 首轮对话
2. 用户正常推进任务
3. 用户表达满意（如"好的"、"谢谢"）
```

### 2.3 维度组合与任务复杂度

**复杂度判定规则**：
```python
is_complex = (
    is_intent_specific in ["infer", "vague"]           # 意图不明确
    or is_use_tool in ["multi", "chat", "pend", "specific"]  # 工具调用复杂
    or is_special_instruction in ["cond"]              # 条件指令
    or is_exe_success in ["abnormal"]                  # 异常反馈
)

task_type = "complex" if is_complex else "easy"
```

**设计理由**：
- 任一维度为"复杂"，整体判定为complex
- 所有维度都为"简单"，才判定为easy
- 这种"或"逻辑保证了高召回率（不会漏判complex）

**典型组合示例**：

| 工具类型 | 意图明确度 | 指令类型 | 执行状态 | 任务复杂度 | 说明 |
|---------|-----------|---------|---------|-----------|------|
| single | clear | norm | ok | **easy** | 最简单的场景 |
| multi | clear | norm | ok | **complex** | 多工具调用 |
| single | vague | norm | ok | **complex** | 意图模糊 |
| single | clear | cond | ok | **complex** | 条件指令 |
| single | clear | norm | abnormal | **complex** | 异常反馈 |
| qa | clear | norm | ok | **easy** | 知识问答 |
| chat | clear | norm | ok | **complex** | 闲聊（业务规则） |

## 3. Prompt工程方法论

### 3.1 Prompt结构设计

**整体结构**：
```
System Prompt = 角色定义 + 分类标准 + 处理规则 + 输出格式 + 典型示例
User Prompt = 工具定义 + 用户输入
```

**设计理由**：
- **角色定义**：明确模型的身份和任务
- **分类标准**：详细描述每个维度的标签定义
- **处理规则**：处理边界case和优先级规则
- **输出格式**：严格控制输出格式，便于解析
- **典型示例**：通过示例帮助模型理解分类标准

### 3.2 角色定义

```python
role_definition = """
你是一个手机用户的query意图拆解专家。你的任务是根据手机用户的当前query和历史对话，
结合候选工具定义，从下面四个维度对用户当前query的意图进行分类。
"""
```

**设计要点**：
- 明确身份：意图拆解专家
- 明确任务：四维度分类
- 明确输入：query + 历史对话 + 工具定义

### 3.3 分类标准描述

**描述模板**：
```
## 维度名称
1. 标签1：（中文名称）详细描述
   - 扩展规则：补充说明
   - 排除规则：明确不属于该标签的情况
2. 标签2：（中文名称）详细描述
   - 扩展规则：补充说明
   - 排除规则：明确不属于该标签的情况
...
```

**示例（工具调用类型）**：
```
## 一、工具调用类型
1. multi：（多工具调用）用户任务包含多个子任务，需要调用多个不同工具才能完成任务。
   - 扩展规则：必须先调用额外的工具完成隐含的前置操作（如要先调用图片问答/问屏截图等）的情况，也属于multi。
   - 扩展规则：对于含single子任务+任意非single子任务（qa/unsupported/pend）的混合query，则整体归为multi。

2. pend：（工具待确定）用户诉求方向本身不明确，或该指令有多个相似候选工具可以选择，导致无法判断要执行什么任务、应调用哪个工具，需要先跟用户澄清"要做什么"。
   - 排除规则：若能明确该调用哪个候选工具，只是参数问题（参数不足或需要推理），则不属于pend。
   - 排除规则（播放类默认锚定）：仅针对播放类任务，"播放XX"（如"播放匆匆那年""播放活着"，同名内容可能是音乐/小说/影视等），虽然play_music/play_broadcast/play_video等多个工具字面均可承接，但用户的诉求对象（作品名XX）本身是明确的，"选哪个媒介/app"只是下游路由问题，不属于"要做什么"层面的歧义，无需向用户澄清，应默认锚定播放类工具，判single而非pend。

3. unsupported：（工具不支持）用户query是明确的任务指令，但当前候选工具中没有能够支持该任务的工具（无工具匹配）。或者能匹配到相关工具，但该任务的具体要求超出了工具的功能定义和参数支持范围（超出工具能力）。
   - 扩展规则：任务内容严重违反道德习俗、社会价值观或社会秩序，也属于unsupported。
   - 排除规则：若明确可匹配对应的候选工具，且未超出工具能力范围，仅参数不足/需要推理，则不属于unsupported。

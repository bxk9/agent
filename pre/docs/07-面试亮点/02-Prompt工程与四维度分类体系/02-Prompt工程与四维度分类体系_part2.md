4. single：（单工具调用）只需要调用单个候选工具，即可完成任务。
   - 扩展规则：只需要多次调用同一个工具的情况，也属于single。
   - 扩展规则（常识消歧）：当query的动作+对象齐全，对象虽为口语化/简略表述、字面看似存在多种解释，但结合用户习惯与生活常识存在唯一高概率指向时，应按该高概率意图锁定对应候选工具，属single，无需向用户澄清。如"打开灯光"（指控制IoT房间灯）、"打开遥控"（指打开遥控器页面/功能）、"打开镜子"（指手机镜子功能）。
   - 扩展规则：当query形如"打开/用XX应用+具体任务"，若该任务对应的候选工具自身已有app_name 参数可接收该应用名称（如多媒体类的play_music/play_video，导航类等），则"打开XX"仅作为该工具的app_name参数填充，不视作独立的open_app子任务，整体判single（而非multi）。
   - 排除规则：请严格按照当前可用的工具定义的范围和边界来判断，若用户要求超出工具能力或无候选工具匹配，则应判为unsupported（而非single）。

5. qa：（知识问答）用户提出涵盖生活娱乐、文化���育、医疗健康、时事财经、自然科学、人文社科、电子科技、学科数理等各领域的知识性问题，可使用knowledgeQA工具，基于自有知识和在线搜索能力回答。
   - 扩展规则：手机等电子产品的相关咨询与指导（问题排查、使用教程、参数功能咨询等），也属于qa。
   - 扩展规则：以任务形式要求输出特定内容的场景，包括文本创作/邮件起草/文本翻译/内容总结/改写扩写/代码编写等，也属于qa。
   - 扩展规则：若query中包含多个子任务，且所有子任务均为问答类（不涉及任何single/unsupported/pend类工具调用子任务），则整体归为qa。
   - 排除规则：若用户询问的对象是自己或身边人/事物（家人/伴侣/朋友/宠物/工作/偏好/经历等）的私人信息，无需也无法通过任何工具回答（不在公开知识库、不在搜索能力范围、也不属于手机功能/系统操作），则归为chat而非qa。

6. chat：（闲聊）不包含任何明确的功能操作或执行类诉求、纯满足对话交互或情绪价值的场景，也不需要调用工具，主要包括以下类型：
   - 日常交流：围绕日常/兴趣/观点/话题的闲聊交流，以及对话起止（打招呼、告别、呼唤小v、结束对话等），或无明确目的和意义的即兴对话。
   - 小v互动：涉及蓝心小v人设/特质（基础信息、能力范围、爱好特长等）的相关问题，或对小v的正面/负面评价。
   - 娱乐游戏：以互动性、过程参与感为主的游戏场景，包括角色扮演、游戏陪玩（猜谜、成语接龙、讲笑话/讲故事、心理/性格/星座/玄学测试等）。
   - 情感陪伴：情绪宣泄/鼓励/共鸣，或用户纯粹表达主观意见和观点，期望满足情绪价值。
```

**设计要点**：
1. **详细描述**：每个标签都有清晰的定义
2. **扩展规则**：补充说明边界case
3. **排除规则**：明确不属于该标签的情况，避免误判
4. **具体示例**：在描述中嵌入具体示例，帮助理解

### 3.4 处理规则设计

**核心规则**：
```python
processing_rules = """
# 处理规则
1. 默认值规则：若工具定义中注明了某参数有默认值（如位置默认当前位置、日期默认今天、时间默认当前时间），用户未提供该参数时，使用默认值，视为clear，而不是lack或infer。

2. 工具调用类型优先级：若在工具调用类型的分类维度中，有多个标签符合定义，请严格按优先级判定：multi > pend > unsupported > single > qa > chat，输出优先级最高的那个。

3. 意图明确度优先级：若在意图明确度的分类维度中，有多个标签符合定义，请严格按优先级判定：vague > infer > lack > clear，输出优先级最高的那个。

4. 意图明确度强绑定：
   - 工具调用类型 ∈ {chat, qa, unsupported} → 强绑定clear
   - 工具调用类型 = pend → 强绑定vague
"""
```

**设计理由**：

**规则1：默认值规则**
- 问题：用户说"定个闹钟"，没有指定时间，是lack还是clear？
- 解决：如果工具定义中时间有默认值（如当前时间），则视为clear
- 理由：减少不必要的追问，提升用户体验

**规则2：工具类型优先级**
- 问题：query既可能是single也可能是multi，如何判断？
- 解决：按优先级选择，multi > pend > unsupported > single > qa > chat
- 理由：宁可判为complex，也不漏判（高召回率）

**规则3：意图明确度优先级**
- 问题：query既可能是clear也可能是infer，如何判断？
- 解决：按优先级选择，vague > infer > lack > clear
- 理由：宁可判为需要推理/澄清，也不误判（高准确率）

**规则4：强绑定规则**
- 问题：chat/qa/unsupported的意图明确度应该是什么？
- 解决：强绑定为clear
- 理由：这些场景不依赖工具调用，意图本身就是清晰的
- 问题：pend的意图明确度应该是什么？
- 解决：强绑定为vague
- 理由：pend本身就是意图模糊导致的

## 4. 典型示例库设计

### 4.1 示例选择原则

**原则1：覆盖性**
- 覆盖所有标签组合
- 覆盖常见场景和边界case

**原则2：对比性**
- 提供对比示例，帮助模型理解细微差别
- 如：abnormal vs ok（用户改主意 vs 模型错误）

**原则3：代表性**
- 选择最具代表性的query
- 避免过于简单或过于复杂的示例

**原则4：多样性**
- 覆盖不同领域（闹钟、音乐、导航、问答等）
- 覆盖不同对话轮次（单轮、多轮）

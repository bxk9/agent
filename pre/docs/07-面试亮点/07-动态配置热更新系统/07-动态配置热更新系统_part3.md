## 6. 面试问答准备

### Q1: 为什么选择30秒的同步间隔，而不是更短或更长？

**A**: 
1. **业务需求**：配置变更不需要实时生效，30秒延迟可接受
2. **性能考虑**：更短的间隔（如5秒）会增加配置中心的压力
3. **网络开销**：更短的间隔会增加网络传输次数
4. **平衡点**：30秒是业务需求和性能的平衡点
5. **可配置**：同步间隔可以通过参数调整，适应不同场景

### Q2: 如何保证配置更新的原子性？

**A**:
1. **锁保护**：使用RLock保护配置的读写，确保原子性
2. **批量更新**：使用`dict.update()`批量更新配置，避免部分更新
3. **回调触发**：配置更新完成后才触发回调，避免回调看到中间状态
4. **事务语义**：配置更新要么全部成功，要么全部失败（不会部分成功）

### Q3: 如果配置中心宕机怎么办？

**A**:
1. **继续使用旧配置**：同步失败时继续使用旧配置，不影响服务
2. **自动重试**：下次同步时自动重试，配置中心恢复后自动同步
3. **本地默认配置**：启动时加载本地默认配置，即使配置中心一直不可用也能启动
4. **告警通知**：配置同步连续失败时发送告警，及时发现问题

### Q4: 如何处理配置冲突（多个客户端同时修改）？

**A**:
1. **配置中心保证**：配置中心使用版本号或时间戳，保证最终一致性
2. **最后写入胜出**：多个客户端同时修改时，最后写入的配置生效
3. **变更检测**：每个客户端独立检测变更，避免覆盖其他客户端的修改
4. **业务层面避免**：通过流程和权限控制，避免多个客户端同时修改同一配置

### Q5: 如何测试配置热更新系统？

**A**:
1. **单元测试**：测试配置管理器的各个方法（get、register、sync等）
2. **并发测试**：100个线程并发读写，验证线程安全
3. **集成测试**：模拟配置中心，测试完整的同步流程
4. **压力测试**：高频同步（如1秒一次），验证系统稳定性
5. **故障注入**：模拟配置中心宕机、超时、返回错误，验证容错机制

### Q6: 这个方案有什么局限性？

**A**:
1. **延迟**：配置生效有30秒延迟，不适合需要实时生效的场景
2. **一致性**：多个实例之间可能有短暂的不一致（最多30秒）
3. **依赖配置中心**：配置中心不可用时，无法更新配置
4. **复杂度**：相比硬编码，增加了系统复杂度
5. **调试困难**：配置动态变化，调试时需要查看配置历史

### Q7: 如何进一步优化？

**A**:
1. **推送机制**：配置中心主动推送变更，减少延迟（从30秒降到<1秒）
2. **配置版本管理**：支持配置版本管理和回滚
3. **配置审计**：记录配置变更历史，便于排查问题

## 6. 面试问答准备

### Q1: 为什么需要四层容错，一层不够吗？

**A**: 
1. **职责分离**：每层有不同的职责，参数验证负责输入校验，异常捕获负责错误处理，降级策略负责备选方案，兜底返回负责最终保障
2. **层层递进**：如果一层失败，还有下一层保障，提高整体可靠性
3. **可维护性**：每层逻辑清晰，便于理解和维护
4. **可测试性**：可以单独测试每层的逻辑

### Q2: 如何决定哪些组件可以降级，哪些不能？

**A**:
1. **组件重要性**：核心组件（如模型推理）不能降级，辅助组件（如向量检索）可以降级
2. **降级影响**：评估降级对准确率、延迟、用户体验的影响
3. **降级成本**：实现降级策略的开发和维护成本
4. **业务需求**：根据业务需求决定可接受的准确率下降

**本项目的决策**：
- 向量检索：辅助功能，失败时准确率下降1-2%，可接受 → 可以降级
- 模型推理：核心功能，失败时准确率降为0%，不可接受 → 不能降级
- 配置同步：后台任务，失败时使用旧配置，影响可控 → 可以降级
- 正则匹配：快速路径，失败时不影响准确性 → 可以降级

### Q3: 熔断机制的阈值如何设置？

**A**:
1. **failure_threshold（失败阈值）**：
   - 太小：容易误触发熔断
   - 太大：不能及时保护系统
   - 经验值：5-10次连续失败

2. **recovery_timeout（恢复超时）**：
   - 太短：外部服务可能还没恢复
   - 太长：影响系统可用性
   - 经验值：30-120秒

**本项目的设置**：
- failure_threshold = 5（连续5次失败触发熔断）
- recovery_timeout = 60（60秒后尝试恢复）

**调优方法**：
1. 监控熔断触发频率
2. 如果频繁触发，增加failure_threshold
3. 如果恢复后仍然失败，增加recovery_timeout

### Q4: 如何测试容错机制？

**A**:
1. **单元测试**：
   - Mock外部服务，模拟各种异常（超时、网络错误、5xx错误）
   - 验证降级策略是否正确执行
   - 验证错误日志是否记录

2. **集成测试**：
   - 使用真实的测试环境
   - 人为制造故障（如停止VSearch服务）
   - 验证系统是否能正确降级

3. **压力测试**：
   - 高并发场景下验证容错机制
   - 监控系统可用性、错误率、延迟

4. **混沌工程**：
   - 在生产环境随机注入故障
   - 验证系统的自愈能力

### Q5: 如果所有降级策略都失败怎么办？

**A**:
1. **兜底返回**：返回统一的错误格式（task_type="complex", 所有字段="err"）
2. **详细日志**：记录完整的错误信息和堆栈
3. **告警通知**：发送告警给运维人员
4. **自动重试**：下游系统可以选择重试
5. **人工介入**：如果持续失败，需要人工排查和修复

### Q6: 这个方案有什么局限性？

**A**:
1. **降级影响准确率**：向量检索失败时，准确率下降1-2%
2. **复杂度增加**：四层容错增加了代码复杂度
3. **维护成本**：需要维护熔断、重试、健康检查等机制
4. **不能完全避免故障**：只能减少故障影响，不能消除故障

### Q7: 如何进一步优化？

**A**:
1. **智能降级**：根据历史数据动态调整降级策略
2. **预测性熔断**：通过监控指标预测故障，提前熔断
3. **自动恢复**：故障恢复后自动重试失败的请求
4. **多活部署**：部署多个实例，一个实例故障时自动切换
5. **服务网格**：使用Istio等服务网格，统一管理容错策略

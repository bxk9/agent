## 7. 面试问答准备

### Q1: 为什么选择asyncio而不是多线程？

**A**: 
1. **IO密集型**：向量检索和模型推理都是IO操作（HTTP请求），不是CPU密集型，asyncio更适合
2. **无GIL限制**：Python的GIL会限制多线程的CPU利用率，但对asyncio无影响
3. **代码简洁**：asyncio.gather一行代码实现并发，多线程需要处理线程安全、锁等问题
4. **性能更优**：asyncio无线程切换开销，延迟更低
5. **框架契合**：FastAPI本身就是异步框架，使用asyncio最自然

### Q2: 如何保证并发执行的正确性？

**A**:
1. **任务独立性**：向量检索和模型推理没有数据依赖，可以安全并发
2. **异常处理**：使用return_exceptions=True，一个任务失败不影响其他任务
3. **超时控制**：为每个任务设置独立的超时时间，避免长时间阻塞
4. **降级策略**：向量检索失败时降级使用模型结果，保证系统可用性
5. **充分测试**：通过压力测试验证并发执行的稳定性

### Q3: 如果向量检索很慢怎么办？

**A**:
1. **超时控制**：设置2秒超时，超时后返回空结果
2. **降级处理**：向量检索失败时，使用模型推理结果（向量检索是辅助）
3. **性能监控**：记录向量检索耗时，发现慢查询及时优化
4. **缓存机制**：对高频query进行结果缓存，减少向量检索调用
5. **异步执行**：向量检索和模型推理并发执行，总延迟取最大值而非累加

### Q4: 并发执行有什么风险？

**A**:
1. **资源竞争**：如果多个任务访问共享资源，可能出现竞争条件
   - 解决：确保任务独立性，避免共享状态
2. **异常处理复杂**：一个任务失败可能影响其他任务
   - 解决：使用return_exceptions=True，独立处理每个任务的异常
3. **调试困难**：并发执行的时序不确定，难以复现问题
   - 解决：详细的日志记录，记录每个任务的耗时和结果
4. **性能不一定提升**：如果任务是CPU密集型，并发可能更慢
   - 解决：分析任务类型，IO密集型用asyncio，CPU密集型用多进程

### Q5: 如何进一步优化性能？

**A**:
1. **SGLang早停优化**：已经实现，延迟降低80%
2. **结果缓存**：对高频query进行结果缓存，避免重复推理
3. **模型蒸馏**：训练专门的小模型用于路由分类，进一步降低延迟
4. **批处理**：将多个请求合并为一个batch，提高GPU利用率
5. **异步IO优化**：使用uvloop替代默认的asyncio事件循环，性能提升20-30%

### Q6: 这个方案有什么局限性？

**A**:
1. **依赖异步框架**：需要所有依赖的库都支持异步（如httpx、aiohttp）
2. **不能利用多核CPU**：asyncio是单线程的，不能利用多核CPU（但对于IO密集型任务不是问题）
3. **调试复杂**：并发执行的时序不确定，调试比串行执行复杂
4. **学习曲线**：asyncio的概念和API比多线程复杂，需要学习成本

### Q7: 如何监控并发执行的性能？

**A**:
1. **耗时统计**：为每个任务记录耗时（向量检索、模型推理、总耗时）
2. **日志记录**：详细记录每个任务的执行过程和结果
3. **性能指标**：监控QPS、延迟（P50、P99）、成功率、错误率
4. **压力测试**：定期进行压力测试，验证系统在高并发下的表现
5. **A/B测试**：对比串行执行和并发执行的性能差异

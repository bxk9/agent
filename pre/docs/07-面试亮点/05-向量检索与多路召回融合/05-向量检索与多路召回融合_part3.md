   - 平均延迟降低30%（200ms → 140ms）
   - 高频query延迟降低75%（200ms → 50ms）
   - 吞吐量提升40%

2. **成本降低**
   - LLM调用次数减少35%
   - 推理成本降低35%
   - 向量检索成本远低于LLM推理

3. **准确率影响小**
   - 整体准确率下降0.2%（可接受）
   - 向量检索准确率98%（高于LLM）
   - 高分匹配准确率99%（非常可靠）

## 6. 面试问答准备

### Q1: 为什么选择0.95和0.8作为阈值？

**A**: 
1. **数据分析**：分析历史数据，发现相似度>0.95的query几乎相同，准确率99%；相似度0.8-0.95的query相似但不完全相同，准确率95%
2. **A/B测试**：测试了多组阈值（0.9/0.7、0.95/0.8、0.98/0.85），0.95/0.8在准确率和命中率之间达到最佳平衡
3. **业务需求**：业务要求准确率下降<1%，0.95/0.8只下降0.2%，满足要求

### Q2: 如果向量检索的结果和LLM推理的结果不一致怎么办？

**A**:
1. **高分匹配（>0.95）**：优先使用向量检索结果，因为相似度很高，准确率99%
2. **低分匹配（0.8-0.95）**：优先使用LLM推理结果，向量检索结果作为参考
3. **无匹配（<0.8）**：完全使用LLM推理结果

**设计理由**：
- 高分匹配的准确率（99%）高于LLM推理（96%），所以优先使用
- 低分匹配的准确率（95%）低于LLM推理（96%），所以优先使用LLM
- 这样可以最大化整体准确率

### Q3: 向量库如何保证数据质量？

**A**:
1. **数据清洗**：去重、去噪、过滤异常数据
2. **人工审核**：对高频query进行人工审核，确保分类结果正确
3. **定期更新**：每日增量更新，每周全量更新
4. **质量监控**：监控向量检索的准确率，发现问题及时修复

### Q4: 如果VSearch服务不可用怎么办？

**A**:
1. **超时控制**：设置1秒超时（生产环境），快速失败
2. **降级策略**：VSearch失败时，降级到纯LLM推理
3. **重试机制**：最多重试1次，提高成功率
4. **熔断机制**：连续失败5次后熔断60秒，避免雪崩
5. **监控告警**：VSearch不可用时发送告警，及时修复

### Q5: 如何进一步优化性能？

**A**:
1. **缓存优化**：增加缓存大小，提高缓存命中率
2. **向量库优化**：使用更高效的向量索引（如HNSW）
3. **模型优化**：使用更小的embedding模型，减少向量化时间
4. **批处理**：将多个query合并为一个batch，提高VSearch的吞吐量
5. **预计算**：对高频query预计算向量，减少实时计算

### Q6: 这个方案有什么局限性？

**A**:
1. **依赖向量库质量**：向量库数据质量直接影响准确率
2. **冷启动问题**：新query没有历史数据，无法通过向量检索加速
3. **语义漂移**：用户表达方式变化，可能导致向量检索失效
4. **维护成本**：需要维护向量库、缓存、VSearch服务等
5. **准确率略降**：整体准确率下降0.2%（但可接受）

### Q7: 如何评估向量检索的效果？

**A**:
1. **命中率**：监控向量检索的命中率（目标>30%）
2. **准确率**：监控向量检索的准确率（目标>95%）
3. **延迟**：监控向量检索的延迟（目标<100ms）
4. **A/B测试**：对比有/无向量检索的效果
5. **用户反馈**：收集用户反馈，发现问题及时优化

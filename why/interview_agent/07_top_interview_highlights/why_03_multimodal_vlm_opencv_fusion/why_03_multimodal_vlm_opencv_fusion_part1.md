# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

双路方案不是"锦上添花"，而是**单一 VLM 路线在真实简历上连续翻车后的被迫升级**：头像误检、头像失效、异常产物缓存污染三类事故在 08-04 至 08-06 集中爆发，团队用三天时间走出了"VLM 语义判断 + OpenCV 几何定位 + 缓存治理"的组合拳。

## 1.3 为什么是"VLM + OpenCV"这个组合？

### 两个模型的失败模式互补

| 维度 | VLM（视觉语言模型） | OpenCV 人脸检测 |
|:---|:---|:---|
| **擅长** | 语义理解（"这是证件照还是公司 logo"） | 几何定位（人脸框坐标精确） |
| **失败模式** | 误检（`1ebfb3f`）、输出不稳定 | 侧脸/低清/艺术照漏检 |
| **成本** | 高（一次 LLM 调用） | 极低（本地毫秒级） |
| **确定性** | 概率性 | 确定性算法 |

**组合逻辑**：
- **OpenCV 先筛**：本地快速给出候选人脸框，零成本
- **VLM 后判**：对候选区域做语义确认（是不是真头像、质量够不够）
- **互相兜底**：OpenCV 漏检时 VLM 还能凭语义找；VLM 误检时 OpenCV 的几何证据能否决

### 淘汰方案对比

**方案 A：只用 VLM**
- 已被证伪：`1ebfb3f`（误检）、`86a54a7`（失效）就是纯 VLM 时期的事故
- VLM 对"头像"这种需要像素级定位的任务天然不擅长（它擅长描述而非定位）

**方案 B：只用 OpenCV**
- 简历头像风格多变（证件照、生活照、插画风头像、圆形裁剪），传统 Haar/DNN 检测器对非标准头像漏检率高
- 且 OpenCV 无法判断"这块人脸是不是用户本人头像"还是"简历里某张合影"

**方案 C：让 LLM 直接输出头像坐标**
- VLM 输出坐标的精度与格式稳定性都差，且与本项目"三层防御"（01 号文档）面对的 LLM 输出不可靠问题同源——团队已经用实践证明了不能信任 LLM 的精确结构化输出

## 1.4 为什么缓存治理必须同步做？

提取算法修好了，但如果脏结果还在缓存里，**修复等于没修**——用户请求命中旧缓存，依旧拿到坏头像。这解释了为什么 08-06 当天两位开发者同时在动缓存：

- 11197109：治理 VLM 异常产物不进缓存（`9639b4f`）
- 11099826：调整头像缓存策略 + 加校验降级（`5288ccf`）

**教训**：**任何"修复提取逻辑"的 PR，必须同时回答"历史脏缓存怎么办"**——要么失效旧缓存，要么加版本键。

## 1.5 反事实推理：如果坚持单路方案？

1. **误检率无法收敛**：调参（`d9249b1`）已经证明收敛不了，误检会把公司 logo 当头像放进简历——这是用户可直接感知的严重事故
2. **缓存污染放大事故**：一次误检结果进缓存 → 该简历后续所有渲染全部带错头像
3. **纯文字简历无兜底**：无头像简历产出低质量产物（`9639b4f` 已点名）

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 单一 VLM 路线收敛失败（真实原因）

**来源**：git 提交记录 - 08-04 至 08-06 头像事故链

**提交信息原文**：
```
929a58a | 2026-08-04 | 11197109 | 修复图像版式提取
bd63628 | 2026-08-05 | 11099826 | 解决电话/头像问题
86a54a7 | 2026-08-06 | 11099826 | 修复头像失效的问题
1ebfb3f | 2026-08-06 | 11099826 | 解决头像误检的问题
d9249b1 | 2026-08-06 | 11099826 | 头像提取修改参数
```

**详细解释**：
- 三天内五起头像类 bug，横跨两位开发者——是链路级问题而非单点 bug
- `d9249b1`（修改参数）出现在事故链中段：团队**先尝试过调参救场**
- 调参之后误检（`1ebfb3f`）和失效（`86a54a7`）仍接连出现——证明单路方案收敛不了

**事故演进还原**：
```
08-04：图像版式提取不准 → 修复（929a58a）
08-05：头像定位错 → 修复（bd63628）
08-06：调参救场（d9249b1）→ 当天仍出现头像失效（86a54a7）
08-06：继续修复 → 又冒出头像误检（1ebfb3f）
结论：修一个冒一个 → 必须换架构（引入 OpenCV 双路）
```

### 2.1.2 OpenCV 引入的直接动机（真实原因）

**来源**：git 提交记录 - `a867570`

**提交信息原文**：
```
a867570 | 2026-08-04 | 11197109 | OpenCV 人脸检测库
929a58a | 2026-08-04 | 11197109 | 修复图像版式提取
```

**详细解释**：
- `a867570`（引入 OpenCV）与 `929a58a`（修复图像版式提取）**同日提交**
- 说明 OpenCV 是在图像版式提取翻车的当天被引入的
- 动机直接：VLM 对"这块区域是不是头像"的判断不稳定，需要 OpenCV 人脸检测器给出**几何层面的硬证据**

**技术对比**：
```
VLM 判断"是不是头像"：
- 概率性输出，同一张图多次调用结果可能不同
- 擅长语义描述，不擅长像素级定位
- 误检实例：1ebfb3f（非头像区域当头像）

OpenCV 人脸检测：
- 确定性算法，结果可复现
- 输出精确人脸框坐标
- 本地执行，毫秒级，零 LLM 成本
- 弱点：侧脸/低清/艺术照漏检（需要 VLM 兜底）
```

### 2.1.3 双路融合而非二选一（合理推断）

**详细解释**：
- 两个模型的失败模式正交：VLM 误检 vs OpenCV 漏检
- 组合逻辑：OpenCV 先筛（零成本候选）→ VLM 后判（语义确认）→ 互相兜底
- 只保留一路都会留下另一路的失败模式

**融合决策表**：
```
OpenCV 检出 + VLM 确认 → 高置信头像（采纳）
OpenCV 检出 + VLM 否决 → 排除（可能是合影/插图/logo）
OpenCV 漏检 + VLM 找到 → 语义兜底（非标准头像，采纳）
双路都无           → 无头像兜底路径
```

## 2.2 技术实现原因

### 2.2.1 为什么淘汰"纯 VLM"方案（真实原因）

**来源**：git 提交记录 - `1ebfb3f`、`86a54a7`

**提交信息原文**：
```
1ebfb3f | 2026-08-06 | 11099826 | 解决头像误检的问题
86a54a7 | 2026-08-06 | 11099826 | 修复头像失效的问题
```

**详细解释**：
- 这两起事故都发生在纯 VLM 时期——是被证伪的直接证据
- 误检：把非头像区域当头像（用户可直接感知的严重事故——公司 logo 出现在头像位）
- 失效：提取出的头像不可用（链接失效/图像损坏）
- VLM 对"头像"这种需要像素级定位的任务天然不擅长（擅长描述而非定位，合理推断）

### 2.2.2 为什么淘汰"纯 OpenCV"方案（合理推断）

**详细解释**：
- 简历头像风格多变：证件照、生活照、插画风头像、圆形裁剪、低清扫描
- 传统 Haar/DNN 检测器对非标准头像漏检率高
- OpenCV 无法回答语义问题："这块人脸是用户本人头像，还是简历里某张合影？"
- 必须保留 VLM 的语义判断能力

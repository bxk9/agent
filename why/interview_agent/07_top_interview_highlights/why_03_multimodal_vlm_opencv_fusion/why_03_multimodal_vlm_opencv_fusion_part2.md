### 2.2.3 为什么淘汰"VLM 直接输出坐标"方案（合理推断）

**详细解释**：
- VLM 输出坐标的精度与格式稳定性差
- 与本项目"三层防御"（01 号文档）面对的 LLM 输出不可靠问题同源
- 团队已经用实践证明了不能信任 LLM 的精确结构化输出（`7291bf3` LLM 自创键名事故）
- 坐标应该由确定性算法（OpenCV）产生，VLM 只做语义判断

## 2.3 性能优化原因

### 2.3.1 为什么 OpenCV 在前、VLM 在后（合理推断）

**详细解释**：
- 成本差异巨大：OpenCV 本地毫秒级 vs VLM 一次 LLM 调用
- OpenCV 先筛出候选框，VLM 只需确认少量候选，而非全图判断
- 若 VLM 在前，每次都要完整调用一次 LLM，成本不可接受

**成本分析**：
```
方案A（VLM 在前）：
- 每个简历页 1 次完整 VLM 调用（全图语义分析）
- 成本高，且无法利用几何信息缩小范围

方案B（OpenCV 在前，最终方案）：
- OpenCV 本地检测：~毫秒级，0 成本
- VLM 只确认候选区域：调用次数 = 候选数（通常 0-2 个）
- 无候选时甚至不需要 VLM 调用
```

### 2.3.2 为什么头像要缓存（合理推断）

**详细解释**：
- 简历生成是多次渲染的过程（预览、导出 PDF、导出 Word 都要头像）
- 每次渲染都重新提取头像 = 重复的 OpenCV + VLM 开销
- 缓存提取结果，一次提取多次复用
- 但缓存引入了污染风险——这正是缓存治理要解决的问题

## 2.4 工程实现原因

### 2.4.1 为什么必须治理缓存污染（真实原因）

**来源**：git 提交记录 - `9639b4f`

**提交信息原文**：
```
9639b4f | 2026-08-06 | 11197109 | VLM 异常产物缓存污染与纯文字兜底质量低下
```

**详细解释**：
- 提交标题直接点名"缓存污染"——这是真实发生的问题类别
- 污染机制：一次 VLM 异常产物（错误头像/空结果）被缓存后，后续所有请求都命中脏缓存
- 后果：提取算法修好了，但用户请求命中旧缓存，依旧拿到坏头像——**修复等于没修**

**治理方案**（真实，commit `5288ccf`）：
```
5288ccf | 2026-08-06 | 11099826 | 1、调整头像缓存策略；2、rebuilt html 评分，
                                   增加校验降级策略；3、debug 用的日志
```
- 调整缓存策略：合格产物才进缓存
- rebuilt html 评分：渲染产物也要评分校验
- 校验降级：不合格时降级，不阻塞交付
- debug 日志：全链路可追溯

**关键教训**：
```
任何"修复提取逻辑"的 PR，必须同时回答"历史脏缓存怎么办"
——要么失效旧缓存，要么加版本键
只修算法不清缓存 = 修复无效
```

### 2.4.2 为什么缓存要处理链接时效（真实原因）

**来源**：git 提交记录 - `f13d71e`

**提交信息原文**：
```
f13d71e | 2026-08-04 | 11197109 | 修复缓存命中过期链接透传导致文档 Agent 空转
```

**详细解释**：
- 缓存里存的不只是"值"，还有"VFS 链接的时效性"
- VFS 链接会过期，过期链接被透传给下游 → 文档 Agent 拿到打不开的链接 → 空转
- 缓存命中时必须校验链接时效，过期则视为未命中重新提取

### 2.4.3 为什么要治理"纯文字兜底质量低下"（真实原因）

**来源**：git 提交记录 - `9639b4f`

**提交信息原文**：
```
9639b4f | 2026-08-06 | 11197109 | VLM 异常产物缓存污染与纯文字兜底质量低下
```

**详细解释**：
- 部分简历根本没有头像图片（纯文字 PDF/DOCX）
- 早期方案对无头像简历走"纯文字兜底"，但兜底产物质量差（提交标题直接点名）
- 兜底路径也是产品体验的一部分，必须专门优化（无头像版式）

## 2.5 业务价值原因

### 2.5.1 为什么头像正确性优先级最高（合理推断）

**详细解释**：
- 头像是简历上**最显眼的视觉元素**——用户第一眼就看它
- 头像错误（logo 当头像、头像失效）是用户可直接感知的严重事故
- 相比字段级错误（可以解释为"提取不准"），头像错误直接摧毁产品信任
- 因此头像链路值得投入双路融合 + 缓存治理的重型方案

**用户感知对比**：
```
字段错误（如时间格式不对）：
- 用户感知："这个小地方没弄好"
- 容忍度：中

头像错误（logo 出现在头像位）：
- 用户感知："这个产品连头像都能搞错"
- 容忍度：极低 → 直接质疑整个产品的可靠性
```

### 2.5.2 为什么"宁可漏检不可误检"（合理推断）

**详细解释**：
- 头像缺失：简历没有头像，可以接受（很多正式简历本来就没头像）
- 头像错误：错误图像出现在头像位，不可接受
- 因此融合决策中 VLM 的否决权优先：OpenCV 检出但 VLM 否决 → 排除
- 这是由两种错误的业务代价不对称决定的

## 3. 总结

### 3.1 核心原因总结

1. **单路收敛失败**（真实）：三天五起事故，调参救场无效，必须换架构
2. **OpenCV 当天引入**（真实）：版式提取翻车当日落地，动机是几何硬证据
3. **失败模式正交**（合理推断）：VLM 误检 vs OpenCV 漏检，互补融合
4. **缓存污染必须治理**（真实）：一次异常污染所有后续请求

### 3.2 技术原因总结

1. **OpenCV 在前**（合理推断）：成本差异决定检测顺序
2. **VLM 只做语义判断**（合理推断）：坐标由确定性算法产生，不信任 LLM 结构化输出
3. **链接时效校验**（真实）：过期链接透传导致下游空转（`f13d71e`）
4. **兜底质量门槛**（真实）：纯文字兜底质量低下被点名治理

### 3.3 业务价值总结

1. **视觉可信度**（合理推断）：头像错误直接摧毁产品信任
2. **宁可漏检不可误检**（合理推断）：两种错误代价不对称
3. **错误不扩散**（真实）：缓存治理保证一次异常不演变为持续事故

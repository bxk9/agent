4. **有独立的业务逻辑**（如 mastery_level 计算）

错题本四条全中。

**DDD 在 AI 系统中的应用**：

- LLM 生成的"结构化输出" ≈ 领域事件
- 用户画像/记忆库 ≈ 聚合根
- Prompt 中的角色/工具 ≈ 领域服务

**可迁移场景**：

| 场景 | 迁移点 |
|:---|:---|
| **教育 App 的错题本** | 完全同构 |
| **健身 App 的训练记录** | 用户级持久记忆 |
| **代码 review 系统的 issue 库** | 一等公民 + 多消费者 |
| **CRM 的客户画像** | user_id 主分区 + LLM 打标 |

**反例警示**：

- **反例 1**：一开始把错题当附属 → 后期跨场景需求出现要大重构（limit 事故就是代价）
- **反例 2**：逐条操作在数据量增长后必撞 limit → 批量能力要随实体一起设计
- **反例 3**：错题识别不可靠时硬写入 → 错题本可信度崩塌，宁可漏记不可错记

## 7. 面试问答准备

### Q1: 错题本为什么要独立成实体？

**A**：
1. 直接推手：limit 事故（`67317ed`）——大量单题删除撞接口限制，逐条操作附属数据不可持续
2. 四个判断标准全中：多消费者（复盘/语音/mock/前端）、独立生命周期（删除/恢复）、跨聚合查询（"我所有错题"）、独立业务逻辑（识别/重试）
3. 附属式的代价：跨会话查询 O(N) 扫描、批量操作受限、排序逻辑重复

### Q2: 四方闭环怎么形成的？

**A**：
1. 生产：语音面试 LLM 自动识别错题写入（`7a9a540` 重试保可靠）
2. 消费 1：复盘按时间序展示错题素材（`1df495b`）
3. 消费 2：mock 面试针对错题出题（`551de3b`）
4. 再生产：mock 答错的题回写错题本——闭环成立

### Q3: DDD 视角怎么分析这个模型？

**A**：
1. error_book_v2 是聚合根：有生命周期、有一致性边界
2. error_item 是实体：有身份（id）、可修改
3. knowledge_tag、mastery_level 是值对象：无身份、通过计算得出
4. 聚合间只通过 user_id 引用，不直接嵌入

### Q4: 错题识别不可靠怎么办？

**A**：
1. 重试机制（`7a9a540`）：提高识别可靠性
2. 不确定时不误判：宁可漏记不可错记——错题本可信度比完整度重要
3. 用户可删除/恢复（`67317ed`）：人工纠错通道兜底

### Q5: 这个建模的迁移价值？

**A**：
1. 判断标准四条：多消费者、独立生命周期、跨聚合查询、独立业务逻辑
2. 同构场景：教育错题本、健身记录、issue 库、客户画像
3. 核心认知：数据量增长和多消费方出现是"附属字段"的丧钟——早点独立化

## 9. 总结

错题本领域建模是一个典型的**事故驱动的 DDD 实践案例**，展示了：

1. **领域嗅觉**：从 limit 事故识别出"附属字段"模式的根本缺陷
2. **闭环设计**：一个实体支撑练→错→复→再练完整循环
3. **长期主义**：两个月持续投入，把错题本做成产品的记忆中枢

**一句话总结**：以 limit 事故为转折，把错题从面试附属字段升级为独立领域实体，用统一数据模型贯穿语音面试、复盘、错题本、mock 面试四方业务，形成"练→错→复→再练"的产品闭环。

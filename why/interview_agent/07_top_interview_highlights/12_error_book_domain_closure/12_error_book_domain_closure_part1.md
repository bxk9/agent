## 4. 核心实现细节

### 4.1 limit 事故与批量操作（`67317ed`）

**提交原文**：`增加批量删除和恢复错题本功能，解决大量单题删除引起的limit限制`

```python
# 事故模式（v1）：
for item in selected_items:       # 逐条删除
    api.delete_error_item(item.id)  # 条数一多 → 撞接口 limit

# 修复（v2）：批量操作
def batch_delete(user_id, item_ids):
    """批量删除——前提是错题有统一的集合身份"""
    error_book.bulk_delete(user_id, item_ids)  # 一次调用

def batch_restore(user_id, item_ids):
    """恢复功能同步落地——独立实体才能支持软删除/恢复"""
    error_book.restore(user_id, item_ids)
```

**本质**：批量操作的前提是**错题数据有统一的集合身份**（能按 user/批次选中）——这天然要求错题本是独立实体而非散落字段。

### 4.5 边界 case 处理

**Case 1：大量错题删除**
```
场景：用户积累几十条错题后清空
处理：批量删除接口（67317ed），不逐条调用
教训：单条操作在数据量增长后必撞 limit
```

**Case 2：错题音频链接失效**
```
场景：query_error_book 返回的 VFS 链接错误
处理：链接解析校验（09f1f05）
关联：与 08 号文档 VFS URL 治理同源
```

**Case 3：错题识别不确定**
```
场景：语音转写噪声导致 LLM 判定不确定
处理：重试机制（7a9a540）+ 不确定时不误判
原则：错题本的可信度比完整度更重要
```

**Case 4：跨会话查询**
```
场景：用户问"我常错什么知识点"
处理：按 user_id 查询全部错题 + 知识点聚合
前提：错题本独立于 session 存在
```

## 6. 技术亮点总结

### 6.1 创新性

1. **事故驱动的领域建模**：limit 事故直接推出独立实体
2. **四方闭环**：一个实体支撑练→错→复→再练完整循环
3. **软删除/恢复**：独立实体才能支持的完整生命周期

### 6.2 技术深度

1. **DDD 实践**：聚合根、实体、值对象的完整识别
2. **多消费方数据组织**：统一查询接口 + 数据层排序
3. **外部引用管理**：实体字段 + VFS 引用的聚合根职责

### 6.3 业务价值

1. **产品闭环**：从"一次性面试工具"升级为"持续练习系统"
2. **个性化**：针对错题练习，练习效率提升
3. **数据资产**：错题本成为用户长期积累的能力画像

### 6.4 方法论抽象与迁移（原文档保留部分）

**从"附属字段"到"一等公民"的判断标准**——一个数据结构应升级为独立实体，如果它满足：

1. **有多个消费者**（>2 个业务场景要读）
2. **有独立的生命周期**（不随宿主消失）
3. **有跨聚合的查询需求**（如"用户所有..."）

## 2. 项目背景与问题定义

### 2.1 业务场景

语音模拟面试的完整链路（06-09 首建，`3682da6`"新增语音模拟面试功能"）：

```
用户音频流
    ↓
【VAD 检测】────────触发打断──┐
    ↓                          │
【STT 流式转文本】               │
    ↓（partial → final）        │
【LLM 流式生成】←───────────────┤
    ↓（token 流）               │
【TTS 流式合成】←───────────────┤
    ↓（音频 chunk）              │
【前端播放队列】←───flush 指令───┘
```

### 2.2 面试场景对语音的四项要求

1. **首字节延迟 < 1s**：用户说完一句话到听见 AI 首字，超过 1s 就"面试感"崩塌
2. **打断自然**：用户想打断 AI 时能立刻停
3. **角色稳定**：AI 面试官不能随机变成"AI 助手"口吻
4. **多轮上下文**：一场面试 20+ 轮不出戏

### 2.3 天真实现的问题

**方案 A：非流式全链路**
```
STT 转完整文本 → LLM 生成完整回答 → TTS 合成完整音频 → 播放
延迟 = STT (1s) + LLM (3-5s) + TTS (2s) = 6-8s → 不可接受
```

**方案 B：只 LLM 流式，其他串行**
```
STT → LLM 流式 → 等 LLM 结束 → TTS
延迟仍 = STT + LLM 首字 + 等 LLM 结束 + TTS = 仍然 4-5s
```

## 3. 技术方案设计

### 3.1 核心思路

## 4. 核心实现细节

### 4.1 流式改造纲领（`bd40e51`）

**提交原文**：`voice: 单一 prompt 源 + 流式 LLM + FALLBACK 兜底 + 面经正文透传`

```python
# 全链路流式
async def voice_turn(user_audio):
    # 1. STT 流式：边说边转（partial results）
    async for partial in stt.stream(user_audio):
        if is_stable(partial):
            prewarm_llm(partial)      # 稳定 partial 预调用
    
    final_text = await stt.final()
    
    # 2. LLM 流式：拿到 final 立刻流式生成
    first_sentence = True
    async for chunk in llm.stream(final_text):
        # 3. TTS 流式：首个短句就开始合成播放
        await tts.stream_synthesize(chunk)
        if first_sentence:
            first_sentence = False    # 首字节延迟 = 首 token + 短句合成
```

**延迟效果**：
```
非流式：6-8s（不可接受）
全流式：首字节 ~600-900ms（自然对话区间）
```

### 4.2 首句短策略（prompt 设计）

```
策略：让 LLM 先出一个短句（如"嗯，你的意思是..."）
  - 短句 TTS 快、缓冲后续长内容
  - 用户感知延迟极短
落地：陈妮的对话 prompt 中实现
配合：出题数量槽位（6750181）——"开场白及延伸不计入数量"
```

### 4.3 打断闭环

```python
async def on_vad_speech_start(session):
    """用户开始说话（VAD 触发）"""
    # 1. 立刻 flush TTS 队列
    await tts.flush()
    # 2. 清空前端播放队列
    session.player.clear()
    # 3. 记录"AI 说到哪被打断"到上下文
    session.context.mark_interrupted_at(tts.played_position())
    # 4. 新 STT 流开始
    session.stt.restart()
```

**关键**：打断时**上下文要记录 AI 实际"说到哪"**，而不是记录 LLM 完整回答。否则用户以为打断了、AI 以为自己讲完了——上下文永久错位。

### 4.4 每次只出一题的行为约束

**真实提交链**：

```
a490baa（07-31）：每次只出一题，点评话术约束
2d0aecc（07-31）：仅改变配置不增加题号
25c2b95（08-05）：强化语音内部不能点评，文字逐题出
6750181（08-05，陈妮）：添加出题数量槽位，约束开场白及延伸不计入数量
422609b（07-28）：取消输出题号，避免跟主agent的题号冲突
```

**为什么必须一题一题出**：
```
1. 语音场景无法回看：一次报 3 题，用户只记住最后一题
2. 追问依赖上一题的回答：批量出题 = 放弃追问
   （08-10 7607626 最终把默认策略定为"深度追问"，与批量出题根本冲突）
3. 题号管理：多题并发导致题号混乱（2d0aecc、422609b 治理）
```

**约束手段升级**：prompt 约束（`a490baa`）→ 持续强化（`25c2b95`）→ 结构化参数（`6750181` 出题数量槽位）。

### 4.5 点评后置决策（`ff5f834`）

**提交原文节选**（这条提交信息本身就是决策文档）：

```
1. 语音面试点评策略调整：从不提供反馈改为面试结束后通过复盘完成点评，
   点评能力不缺失，只是时机不同
2. 路由规则加固：用户要求点评/逐题反馈不改……道题，不提前列出全部题目
11. 语音链接：每次下发语音入口必须重新输出占位符，禁止引用历史链接
12. 面试结束不直接给总结：无论正常结束还是主动终止，
    都先询问用户是否需要整体点评，确认后才输出评估
```

**为什么后置**：
```
1. 语音里听点评体验极差：300 字点评 TTS 念 1 分钟+，用户只能干听
2. 打断面试节奏：真实面试官不会每题答完就长篇点评
3. 把选择权交给用户：结束后先询问是否需要点评（第 12 条）
```

### 4.7 边界 case 处理

**Case 1：用户抢话打断**
```
处理：VAD 触发 → flush TTS → 记录"说到哪" → 新 STT 流
关键：上下文记录实际播放位置，不是 LLM 完整回答
```

**Case 2：LLM 想批量出题**
```
处理：prompt 约束 + 出题数量槽位（结构化参数）
演进：07-31 约束 → 08-05 强化 → 槽位参数化
```

**Case 3：用户要求中途点评**
```
处理：路由规则加固（ff5f834 第 2 条）——不改变出题流程
       告知用户点评在面试结束后通过复盘完成
```

**Case 4：语音链接时效**
```
处理：每次下发语音入口必须重新输出占位符，禁止引用历史链接
      （ff5f834 第 11 条——历史链接会过期）
```

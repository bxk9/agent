# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

错题本从"面试附属数据"升级为独立领域实体，是被三个真实压力逼出来的：① **单题删除触发 limit 限制**（07-31 `67317ed`，直接证据）；② **多个业务方都要消费错题数据**（复盘要、语音要、mock 要）；③ **跨会话查询需求**（用户要看"我所有的错题"而不只是"这场的错题"）。git 历史显示错题本是 yitong 持续投入时间最长的单一模块（06-08 至 08-07，横跨两个月）。

## 1.2 真实原因（git 证据链）

### 起点：错题本很早就是一等公民（06-08）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 06-08 | `a9fd2ea` | feat: **前端错题本展示优化** |

- 项目启动第 4 天（仓库 06-04 首次提交）就有错题本前端展示——说明错题本**从产品立项起就是核心功能**，不是后期附加
- 这决定了后续所有架构决策的基调：错题本的数据模型必须按"长期核心资产"设计，而不是"临时附属字段"

### limit 事故：附属式操作的直接代价（07-31）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-31 | `67317ed` / `44ef32d` | **增加批量删除和恢复错题本功能，解决大量单题删除引起的limit限制** |

**这是错题本独立化最直接的证据**：

- "大量单题删除引起的 limit 限制"——当错题本只是零散的附属记录时，删除操作只能逐条调用接口，条数一多就撞上接口的调用频率/数量限制
- 解决方案是"**批量删除和恢复**"——批量操作的前提是**错题数据有统一的集合身份**（能按 user/批次选中），这天然要求错题本是独立实体而非散落字段
- "恢复"功能同步落地——独立实体才能支持软删除/恢复，附属字段删了就没了
- 这次事故的本质：**当数据量增长后，"逐条操作附属数据"的模式在 API 层和性能层同时崩溃**

### 排序治理：多消费方对数据组织的不同要求（07-28 至 07-29）

| 日期 | Commit | 作者 | 提交信息 |
|:---:|:---|:---:|:---|

| 07-29 | `0494938` / `67a58e6` | yitong | 语音add-dialogue增加**按时间排序**，错题本同样增加排序 |
| 07-29 | `ed50dd1` / `6b4ae20` | yitong | get_session_error_book**对答案进行升序排列** |

**两天内三条排序提交揭示了"多消费方"的现实**：

- 复盘模块（陈乾）消费错题本时要求**按时间顺序**——错题本必须提供稳定的排序能力
- 语音侧（yitong）和 session 查询接口各有各的排序需求（时间序 / 答案升序）
- 如果错题数据散落在各场面试里，每个消费方都要自己扫描、收集、排序——**排序逻辑重复 N 份且容易不一致**。独立实体 + 统一查询接口（get_session_error_book / query_error_book）让排序在数据层一次解决

### 数据完整性治理：错题本与 VFS 的耦合（07-29）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-29 | `09f1f05` / `9dc7aed` | 解决**query_error_book返回错误vfs链接**问题 |

- 错题本的查询接口会返回 VFS 链接（错题的音频/详情文件），链接错了用户就打不开
- 这说明错题本实体**不只存文本，还引用外部产物**（面试录音片段、标准答案文档）——实体必须管理"自身字段 + 外部引用"两类数据，这是典型的聚合根职责
- 与 08 号文档的 VFS URL 治理同源：凡是引用 VFS 链接的业务，都要面对链接过期/错误的问题

### 闭环成型：错题本反哺面试（08-04 至 08-07）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 08-04 | `551de3b` / `d33788c` | **强化错题本的调用**和追问只问一题 |
| 08-07 | `7a9a540` | **语音错题本识别增加重试机制** |

- "强化错题本的调用"——面试过程中主动调用错题本，即**用历史错题指导当前出题**，闭环的"消费"端成型
- "语音错题本识别"说明语音面试中用户答错的判定是自动的（LLM 识别），且需要重试机制保证识别可靠性——闭环的"生产"端也在加固
- 至此四方闭环完整：面试生产错题 → 复盘消费错题 → 下次面试调用错题本针对性出题 → 新错题回写

## 1.3 为什么必须是"独立实体"而不是"面试附属"？

### 四个判断标准全部命中

| 标准 | 错题本的表现 | 证据 |
|:---|:---|:---|
| **多个消费者** | 复盘、语音、mock、前端展示四方消费 | `1df495b` `551de3b` `a9fd2ea` |
| **独立生命周期** | 错题跨会话长期存在，支持删除/恢复 | `67317ed` |
| **跨聚合查询** | "我的所有错题"按时间/答案排序 | `0494938` `ed50dd1` |
| **独立业务逻辑** | 错题识别、重试、VFS 引用管理 | `7a9a540` `09f1f05` |

### 淘汰方案对比

**方案 A：错题作为面试 session 的附属字段**
- 已被 limit 事故证伪（`67317ed`）：逐条操作附属数据会撞 API 限制
- 且跨会话查询（"我所有的错题"）需要扫描全部 session，O(N) 不可接受

**方案 B：错题存纯文本日志，按需解析**
- 无法支持排序、批量删除、恢复等结构化操作；复盘的"按时间展示"（`1df495b`）无法高效实现

**方案 C：每个业务方各自维护一份错题视图**
- 排序逻辑重复（07-29 的三条排序提交就是统一前的混乱状态），数据不一致风险高

## 1.4 反事实推理：如果不独立化？

1. **limit 事故常态化**：用户错题积累到几十条后，任何批量操作都会撞限制（`67317ed` 的根因未除）
2. **闭环断裂**：面试无法调用历史错题（`551de3b` 无从实现），产品退化为"一次性面试工具"
3. **排序各自为政**：复盘、语音、前端各扫各的数据，展示顺序互相矛盾

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 为什么 limit 事故是独立化的直接推手（真实原因）

**来源**：git 提交记录 - `67317ed`

**提交信息原文**：
```
67317ed | 2026-07-31 | yitong | 增加批量删除和恢复错题本功能，解决大量单题删除引起的limit限制
```

**详细解释**：
- 提交原文直接给出因果："大量单题删除引起的 limit 限制"
- 附属式数据没有集合身份，删除只能逐条调用接口 → 条数一多撞 API 的频率/数量限制
- 批量操作的前提是数据有统一的集合身份——这天然要求独立实体
- "恢复"同步落地：独立实体才能支持软删除，附属字段删了就没了

**业务场景**：
```
用户练习了一个月，积累 50 条错题
用户想清空重来：
  附属式：逐条删除 50 次接口调用 → 撞 limit → 删除失败
  独立实体：一次批量删除调用 → 完成
数据量增长后，附属式模式在 API 层和性能层同时崩溃
```

### 2.1.2 为什么错题本立项就是核心资产（真实原因）

**来源**：git 提交记录 - `a9fd2ea`

**提交信息原文**：
```
a9fd2ea | 2026-06-08 | yitong | feat: 前端错题本展示优化
```

**详细解释**：
- 仓库 06-04 首次提交，06-08（第 4 天）就有错题本前端展示
- 错题本从产品立项起就是核心功能，不是后期附加
- 这决定了架构基调：必须按"长期核心资产"设计数据模型
- 若当初按"临时附属"设计，两个月后的独立化重构代价会更大

### 2.1.3 为什么多消费方要求统一数据组织（真实原因）

**来源**：git 提交记录 - `1df495b`、`0494938`、`ed50dd1`

**提交信息原文**：
```
1df495b | 2026-07-28 | 陈乾  | 复盘素材来自错题本时，按照时间顺序展示题目
0494938 | 2026-07-29 | yitong | 语音add-dialogue增加按时间排序，错题本同样增加排序
ed50dd1 | 2026-07-29 | yitong | get_session_error_book对答案进行升序排列
```

**详细解释**：
- 两天三条排序提交揭示多消费方现实：复盘要时间序、语音要时间序、session 查询要答案升序
- 数据散落时每个消费方自己扫描、收集、排序——逻辑重复 N 份且容易不一致
- 独立实体 + 统一查询接口：排序在数据层一次解决，消费方只声明需求

**技术对比**：
```
数据散落（v1）：
  复盘：扫描所有 session → 收集错题 → 自己排序
  语音：扫描所有 session → 收集错题 → 自己排序
  前端：扫描所有 session → 收集错题 → 自己排序
  → 三份排序逻辑，容易不一致，O(N) 扫描

独立实体（v2）：
  error_book.query(user_id, order_by=...)
  → 一份逻辑，O(1) 查询，消费方只声明排序需求
```

- 语音面试中"用户答错"的判定是自动的（LLM 识别转写文本）
- 识别不可靠 → 错题记录错误 → 错题本可信度崩塌
- 重试机制提高识别可靠性
- 隐含原则：不确定时不误判——错题本可信度比完整度重要（配合删除/恢复的人工纠错通道）

### 2.2.3 为什么按 user_id 组织（合理推断）

**详细解释**：
- 跨会话查询（"我所有的错题"）的入口是 user
- 多租户隔离：A 用户不能看到 B 用户的错题
- 与司棋侧 user 中心化架构（VFS user_id 治理，08 号文档）对齐
- user_id 主分区 + session 二级索引：既支持跨会话查询，又支持按场查询

## 2.3 性能与质量原因

### 2.3.1 为什么批量和恢复要一起做（真实原因）

**来源**：git 提交记录 - `67317ed`

**提交信息原文**：
```
67317ed | 2026-07-31 | yitong | 增加批量删除和恢复错题本功能……
```

**详细解释**：
- 批量删除解决了 limit，但也引入了新风险：误删一大片怎么办？
- 恢复功能是批量删除的必要配套——删除能力越强，恢复能力越必要
- 软删除（标记而非物理删）让恢复成为可能——这只有独立实体才支持

### 2.3.2 为什么跨会话查询必须 O(1)（合理推断）

**详细解释**：
- "我常错什么"是高频查询（复盘、mock 出题、能力画像都要）
- 附属式 O(N session 扫描) 随面试次数增长线性恶化
- 独立实体按 user_id 直接查询 O(1)
- 这是"用户级持久记忆"的性能基础

## 2.4 工程实现原因

### 2.4.1 为什么闭环消费端要"强化调用"（真实原因）

**来源**：git 提交记录 - `551de3b`

**提交信息原文**：
```
551de3b | 2026-08-04 | yitong | 强化错题本的调用和追问只问一题
```

**详细解释**：
- "强化"说明错题本调用此前不够主动——LLM 不会自发去查错题本
- 面试过程中主动调用错题本 = 用历史错题指导当前出题
- 这是闭环从"数据存在"到"数据被使用"的关键一步
- 与"追问只问一题"同提交——针对性出题与深度追问配套

### 2.4.2 为什么排序要在数据层而不是消费层（真实原因）

**来源**：git 提交记录 - 07-29 两条排序提交

**详细解释**：
- 消费层排序 = 每个消费方重复实现（07-29 的三条提交就是混乱期）
- 数据层排序 = 一份逻辑、一致行为、O(1) 查询
- 统一查询接口（get_session_error_book / query_error_book）是数据层排序的载体

## 2.5 业务价值原因

### 2.5.1 为什么闭环让产品从"工具"变"系统"（合理推断）

**详细解释**：
- 无闭环：每次面试是孤立事件，练完就忘——"一次性面试工具"
- 有闭环：练→错→复→再练，错题积累成能力画像——"持续练习系统"
- 用户留存逻辑改变：从"每次重新练"到"越练越有针对性"
- 错题本是这个转变的数据中枢

### 2.5.2 为什么"针对错题练"是差异化卖点（合理推断）

**详细解释**：
- 题库产品人人能做，"针对你的错题出题"需要完整的错题数据模型
- mock 面试消费错题本（`551de3b`）= 个性化练习
- 这是数据模型投资转化为产品差异化的直接例子

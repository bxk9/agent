- 第一版用 contextvar 存 token 累计值 → 跨线程失效（提交原文点名）→ 统计结果为 0（`124a5b1`）
- 本项目大量使用 run_in_executor（线程池），contextvar 在线程切换处丢失
- 最终方案：模块级 FIFO 字典，以 request_id 为 key，FIFO 限制容量防内存泄漏

**技术对比**：
```
contextvar：
- 纯 asyncio 内可用
- 跨线程（run_in_executor）丢失 → 统计为 0
- 本项目线程池使用多 → 断点太多

显式传参：
- 所有函数签名带统计参数 → 侵入性大
- 漏一个调用点就断链

模块级 FIFO 字典（最终方案）：
- 以 request_id 显式存取 → 可控
- FIFO 容量限制 → 无泄漏
- 低侵入 → 调用点只需两处（写入/汇总）
```

### 2.2.2 为什么 token 汇总要合并为单条日志（真实原因）

**来源**：git 提交记录 - `124a5b1`

**提交信息原文**：
```
124a5b1 | 2026-08-05 | 司棋 | fix: token 汇总合并为单条日志 + 修复 token 为 0 的问题
```

**详细解释**：
- 分散的多条日志在高并发下会交错，无法阅读
- 一次请求的 LLM 调用、工具调用 token 必须聚合成单条汇总日志
- 这样才能回答"这次请求总共吃了多少 token"——裁剪决策的基础数据

## 2.3 性能优化原因

### 2.3.1 为什么淘汰"全量摘要��缩"方案（合理推断）

**详细解释**：
- 摘要方案：用一次 LLM 调用把历史对话压缩成摘要
- 问题 1：摘要本身要调 LLM → 语音实时场景延迟不可接受（参见 11 号文档首字节延迟约束）
- 问题 2：摘要丢细节 → 面试追问需要精确历史原文（"你刚才说……"）
- 定位：摘要是兜底手段（配对裁完仍超限时），不是主策略

**方案对比**：
```
全量摘要：
- 延迟：+1 次 LLM 调用（秒级）
- 信息保真：低（细节丢失）
- 适用：离线批处理

配对裁剪（最终方案）：
- 延迟：纯本地计算（毫秒级）
- 信息保真：保留原文（只移除低价值配对）
- 适用：实时对话
```

### 2.3.2 为什么淘汰"换大窗口模型"方案（真实原因 + 合理推断）

**来源**：git 提交记录 - `874b360`

**提交信息原文**：
```
874b360 | 2026-08-04 | yitong | 增加兜底v4 pro模型
```

**详细解释**：
- 团队确实用模型切换做兜底（`874b360`），但那是**可用性兜底**（主模型挂了切备用），不是容量方案
- 大窗口模型成本高、延迟大——语音场景对首字节延迟敏感（合理推断）
- 上下文越长注意力越稀释（lost in the middle 效应），裁剪反而提升回答质量（合理推断，行业共识）

## 2.4 工程实现原因

### 2.4.1 为什么裁剪必须带日志（真实原因）

**来源**：git 提交记录 - `1d3a318`

**提交信息原文**：
```
1d3a318 | 2026-08-04 | yitong | blueclaw_chat增加裁剪和日志
```

**详细解释**：
- "裁剪"和"日志"出现在同一个提交标题——开发者明确把两者视为一体
- 裁剪是有损操作：裁错了的表现是"AI 忘了用户刚才说的"，这类问题没有日志根本无法归因
- 日志内容应包含：裁了哪些配对、token 前后值、trace_id（合理推断，与 06 号文档的可观测规范一致）

**业务场景**：
```
用户报障："面试官忘了我上一题的回答"
无日志：不知道是裁剪裁掉了，还是 LLM 注意力问题，还是 STT 转写丢了
有日志：按 trace_id 查裁剪记录 → 确认是否裁掉了该轮 → 调整保留策略
```

### 2.4.2 为什么裁剪策略要与"产物引用"联动（合理推断）

**来源**：git 提交记录 - `f13d71e`（反面教训）

**提交信息原文**：
```
f13d71e | 2026-08-04 | 11197109 | 修复缓存命中过期链接透传导致文档 Agent 空转
```

**详细解释**：
- 裁剪不能只看"这条消息旧不旧"，还要看"有没有被后续引用"
- 被引用的产物（如简历内容被后续点评引用）必须保留
- 反过来，引用已失效的数据（过期链接）必须清除——`f13d71e` 证明失效引用透传会导致 Agent 空转
- 裁剪与引用治理是同一问题的两面

## 2.5 业务价值原因

### 2.5.1 为什么长对话稳定性是语音产品的生命线（合理推断）

**详细解释**：
- 语音面试一场 20+ 轮，进行到第 15 轮中断 = 用户损失全部练习时间
- 文字聊天中断可以重发，语音中断的恢复成本高得多（要重新进入状态）
- 上下文超限是"确定性会发生的事故"（轮次够多必然触发），不是概率性风险
- 因此裁剪是语音功能的**必备项**而非优化项

**用户影响分析**：
```
无裁剪：
- 20 轮后 token 超限 → 请求失败 → 面试中断
- 用户感知："这个产品练不久就坏"
- 影响：核心场景不可用

有裁剪：
- 长对话稳定运行
- 用户感知：无感（最好的基础设施就是不被感知）
- 价值：支撑"完整模拟面试"的产品承诺
```

### 2.5.2 为什么这套策略可推广（合理推断）

**详细解释**：
- 任何多轮 Agent 系统都面临上下文膨胀：客服机器人、代码助手、教育陪练
- 配对约束是 OpenAI 兼容协议的通用要求，配对裁剪算法可直接复用
- 观测先行的方法论（先建 token 统计再定策略）适用于所有性能优化场景

## 3. 总结

### 3.1 核心原因总结

1. **语音场景最先爆**（真实）：轮次多 + 工具产物大 + 实时性高，同日两提交紧急落地
2. **配对是协议硬约束**（行业事实 + 真实旁证）：孤儿 tool_call/response 导致 API 报错或空转
3. **观测先行**（真实）：token 统计三连修建成后，裁剪决策才有数据支撑
4. **裁剪必带日志**（真实）：有损操作必须可追溯

### 3.2 技术原因总结

1. **FIFO 字典替代 contextvar**（真实）：跨线程失效是实测出来的，不是预知的
2. **单条汇总日志**（真实）：高并发下分散日志不可读
3. **淘汰摘要方案**（合理推断）：延迟与信息保真双重不达标
4. **淘汰大窗口模型**（真实+推断）：模型切换是可用性兜底，不是容量方案

### 3.3 业务价值总结

1. **长对话稳定**：20+ 轮语音面试不中断
2. **成本可见**：请求级 token 汇总支撑成本核算与预算调优
3. **方法论沉淀**：观测 → 剖分 → 优化的闭环可复用

# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

配对裁剪策略的成因是**两次真实压力叠加**：① 语音面试多轮对话把上下文撑爆（08-04 连续两次"语音上下文裁剪"提交）；② token 观测体系刚在 08-05 建成，让"到底吃了多少 token"第一次可量化。而"必须配对"这条铁律，来自 LLM API 的硬约束——**孤儿 tool_call 或孤儿 tool_response 会直接导致 API 报错或模型行为错乱**。

### 为什么语音场景最先爆？

【推断，业务场景支撑】语音面试的上下文构成与文字聊天完全不同：
1. **轮次多**：一场面试 20+ 轮问答，每轮还有追问（`01baa6a` "强化追问"）
2. **工具产物大**：面试中会拉取简历、错题本（`551de3b` "强化错题本的调用"），这些 tool_response 动辄数千 token
3. **实时性要求高**：不能像离线任务那样慢慢等，token 超限 = 请求直接失败 = 面试中断

三者叠加，语音链路是全系统最先触碰上下文上限的场景——所以裁剪先在语音落地（`93a0dd7`），再沉淀为通用策略。

## 1.3 为什么必须"配对保留"？

### LLM API 的硬约束

主流 LLM API（OpenAI 兼容协议）要求消息序列满足：

```
assistant: tool_calls=[{id: "call_1", ...}]
tool: {tool_call_id: "call_1", content: "..."}   ← 必须紧跟且 id 对应
```

**违反后果**：
- 孤儿 tool_call（有调用无响应）→ API 直接 400 报错，或模型"以为工具还在执行"而空转
- 孤儿 tool_response（有响应无调用）→ API 报错 `tool_call_id not found`

这不是设计选择，是**协议层的强制约束**。任何裁剪策略如果破坏配对，裁剪本身就成为新的故障源。

### 项目内的旁证：孤儿数据确实会引发空转

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 08-04 | `f13d71e` | 11197109 · **修复缓存命中过期链接透传导致文档 Agent 空转** |
| 08-07 | `1018c6a` | 司棋 · fix: format_document pdf_tip **由 executor 直接拼接，不走 LLM 转发** |

- `f13d71e` 证明"上下文里残留过期/无效的引用数据"会让下游 Agent 空转——裁剪时留下孤儿工具数据，危害同源
- `1018c6a` 证明团队有"**能不过 LLM 就不让 LLM 转发**"的共识——减少上下文中的无效工具往返，与裁剪目标一致

### 裁剪优先级的取舍

配对约束下，裁剪只能按"整对"为单位操作。合理策略是：
1. **保留最近 N 轮完整配对**（对话连贯性）
2. **保留产物被后续引用的配对**（如简历内容被后续点评引用）
3. **优先裁"大而无用"的配对**（如早期的文件上传响应，内容已被摘要替代）

## 1.4 淘汰方案对比

**方案 A：按 token 数从头部硬截断**
- 硬截断大概率切在配对中间 → 产生孤儿 → API 报错
- `93a0dd7` 同日两提交说明第一版裁剪上线后立刻打了补丁——很可能就是踩了"裁坏配对"或"裁掉关键上下文"的坑

**方案 B：全量摘要压缩（LLM 总结历史）**
- 摘要本身要调一次 LLM → 语音实时场景延迟不可接受（参见 11 号文档首字节延迟约束）
- 摘要会丢细节，面试追问场景需要**精确的历史问答原文**（"你刚才说……"）

**方案 C：换更大上下文窗口的模型**
- `874b360`（08-04 yitong "增加兜底v4 pro模型"）说明团队确实会用模型切换做兜底，但那是**可用性兜底**不是容量方案
- 大窗口模型成本高、延迟大；上下文越长注意力越稀释（lost in the middle），裁剪反而提升质量

## 1.5 反事实推理：如果不做配对裁剪？

1. **语音面试 20 轮后必崩**：token 超限 → 请求失败 → 用户面试中途中断，这是最严重的体验事故
2. **若裁了但不配对**：API 400 错误率上升，且这类错误**只在长对话复现**，排查极其困难
3. **若不观测只裁剪**：裁多裁少全凭感觉，无法验证效果——这正是"裁剪和日志"必须在同一提交（`1d3a318`）的原因

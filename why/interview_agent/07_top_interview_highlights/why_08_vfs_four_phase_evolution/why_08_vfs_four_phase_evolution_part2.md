7bbbcb5 | 2026-08-05 | 司棋 | fix(vfs): _upload_with_path 和 _vfs_json 修复 user_id 漏传，加请求日志
fe5939b | 2026-08-05 | 司棋 | fix: 所有 VFSClient/build_vfs_headers 调用补充 user_id 参数
```

**详细解释**：
- 两条同日提交，第二条是"所有调用补充"——漏传不是个别笔误，是接口设计缺陷
- 根因：接口早期没把 user_id 设为必填参数，调用点传不传全靠自觉
- 根治：接口签名强制 user_id（不传就报错）+ 全量调用点补齐
- 教训：**多租户标识必须接口强制，靠约定必漏**

**业务场景**：
```
user_id 漏传的后果：
1. 归属混乱：文件不知道属于谁
   → 跨用户查询可能拿到别人的文件（安全问题）
2. 配额审计失效：无法按用户统计存储用量
3. 用户中心化受阻：
   错题本按 user 分区、"我的文件空间"等能力全部无从谈起
   （12 号文档的错题本 user_id 主分区依赖此基础）
```

### 2.2.2 为什么 URL 要用三层兜底而不是统一格式（真实原因）

**来源**：git 提交记录 - `c291394`

**提交信息原文**：
```
c291394 | 2026-08-07 | 11099826 | feat: vclaw-fs URL三层兜底读取 + rebuilt质量评分 + AI标记提醒
```

**详细解释**：
- URL 经过多环节（VFS 返回、LLM 产出、前端展示、域名替换），完全统一需要改造所有环节
- 三层兜底在读取端收敛：原样读 → 规范化读 → 变体读，不动上游
- 渐进式治理：先保可用性，再逐步收敛源头（双重前缀 `9ddcfbb` 同时根治）

**技术对比**：
```
统一 URL 格式：
- 需要改造所有产生/改写 URL 的环节
- 改造期间新旧形态并存，风险高
- 周期长，期间用户持续遇到链接问题

三层兜底读取（最终方案）：
- 只改读取端，上游不动
- 立即生效，可用性立即恢复
- 后续再逐步收敛源头（双前缀修复等）
```

**来源**：git 提交记录 - 08-04 一天三条

**提交信息原文**：

**详细解释**：
- 一天三条 URL 类修复——不是巧合，是系统性缺陷的集中暴露
- 根因：多个环节都在给 URL 加前缀/做转换，叠加后产生双重前缀、重复、异常
- URL 的经手环节越少越安全——陈乾侧 `92bc8e6`（移除复盘报告链接域名替换流程）是同一教训的另一侧

## 2.3 性能与质量原因

### 2.3.1 为什么指数退避而不是固定间隔（真实原因 + 合理推断）

**来源**：git 提交记录 - `a05d7c2`（"3次指数退避"原文）

**详细解释**：
- 固定间隔重试在服务过载时会雪上加霜（所有客户端同时重试）
- 指数退避（1s→2s→4s）给服务恢复时间，且各客户端重试时刻错开
- 3 次是平衡点：覆盖偶发抖动，又不过度延长失败路径的总耗时

### 2.3.2 为什么要独立的 download 测试脚本（真实原因）

**来源**：git 提交记录 - `f89bedf`

**提交信息原文**：
```
f89bedf | 2026-08-06 | 司棋 | 增加测试脚本，从vfs download 文件脚本
```

**详细解释**：
- URL 问题的复现不依赖完整业务流程——直接 download 就能验证
- 独立测试脚本把"复现成本"从"跑完整业务"降为"一条命令"
- 治理 URL 这类形态问题，快速验证手段与修复本身同样重要

## 2.5 业务价值原因

### 2.5.1 为什么 VFS 治理值得持续投入（合理推断）

**详细解释**：
- VFS 是全局依赖：简历、复盘、错题本、语音全部依赖文件存取
- VFS 的任何问题都会扇出到所有业务模块——杠杆效应极大
- 四个阶段的投入换来全局文件访问的可靠、可追踪、可归属、可用

### 2.5.2 为什么 user_id 治理是用户中心化的地基（真实原因 + 合理推断）

**来源**：git 提交时序 - `fe5939b`（08-05）→ 后续用户中心化能力

**详细解释**：
- 没有 user_id 归属，就没有"用户的文件空间"概念
- 错题本按 user 分区（12 号文档）、跨会话记忆等能力全部依赖文件归属
- user_id 治理是后续一切用户中心化能力的地基

## 3. 总结

### 3.1 核心原因总结

1. **超时拆分与重试**（真实）：单一总超时两难，偶发抖动需兜住
2. **日志三次扩大**（真实）：调用入口被低估，覆盖面必须穷举
3. **user_id 接口强制**（真实）：靠约定必漏，签名强制才根治
4. **URL 三层兜底**（真实）：形态无法速统一，兜底先保可用性

### 3.2 技术原因总结

1. **指数退避**（真实+推断）：防重试风暴，给服务恢复时间
2. **独立测试脚本**（真实）：降低复现成本，加速治理
3. **环境配置化**（真实）：硬编码连错环境的教训
4. **日志防崩溃**（真实）：观测组件不能成为故障源

### 3.3 业务价值总结

1. **全局依赖稳定**：四业务模块的文件访问可靠
2. **用户中心化地基**：user_id 归属支撑后续能力
3. **链接可用**：三层兜底保证用户拿到的链接能打开

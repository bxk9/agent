# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

VFS 的四阶段演进（首建 → 可靠性治理 → URL 治理 → 用户中心化）**不是预先设计的路线图，而是被四类依次出现的真实问题倒逼出来的**：① 早期超时与重试缺失（07-07）；② 多租户日志不可追踪（08-04）；③ user_id 漏传导致的越权/归属混乱（08-05 三连修）；④ URL 链接异常与过期（08-04 至 08-07 密集修复）。

## 1.2 逐阶段真实成因

### 阶段 1：可靠性基础——超时拆分与重试（07-07）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-07 | `a05d7c2` | fix: VFS json store **加重试(3次指数退避) + 拆分超时(connect 10s/read 30s)** |

**为什么这么做**：
- "拆分超时"说明最初用的是**单一总超时**——connect 慢和 read 慢无法区分对待。连接建立应该快（10s 足够），而大文件读取天然慢（需要 30s）
- "3次指数退避"说明此前 VFS 调用**失败即抛错**，而 VFS 作为存储服务偶发抖动是常态——没有重试，偶发抖动就会变成用户可见的失败
- 这是 VFS 从"能用"到"可靠"的第一课：**对远程存储的调用必须有超时拆分 + 重试退避**，这是分布式调用的基本卫生

- 触发点大概率是某次"文件找不到/读不到"的用户报障，而日志里根本查不到对应的 VFS 调用记录

### 阶段 3：user_id 漏传三连修——多租户归属治理（08-05）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 08-05 | `7bbbcb5` | fix(vfs): _upload_with_path 和 _vfs_json **修复 user_id 漏传**，加请求日志 |
| 08-05 | `fe5939b` | fix: **所有 VFSClient/build_vfs_headers 调用补充 user_id 参数** |

**这是四阶段中最关键的一步**：
- 两条提交同日出现，且第二条是"**所有**调用补充 user_id"——说明 user_id 漏传不是个别调用点的笔误，而是**接口设计早期没有强制要求 user_id**，导致大量调用点都没传
- user_id 漏传的后果极其严重：
  1. **归属混乱**：文件不知道属于谁，跨用户查询时可能拿到别人的文件
  2. **配额与审计失效**：无法按用户统计存储用量
  3. **后续用户中心化无从谈起**：没有 user_id 就没有"用户的文件空间"
- 修复方式大概率是：接口签名强制 user_id 参数 + 全量调用点排查补齐——这正是"所有调用补充"的含义

## 1.3 为什么是"演进"而不是"一步到位"？

### 认知是随事故递进的

四个阶段的触发点各不相同：
1. 07-07 才发现超时/重试缺失 → 说明早期 VFS 调用是"理想环境假设"
2. 08-04 才补日志 → 说明此前 VFS 问题靠猜
3. 08-05 才发现 user_id 漏传 → 说明多租户意识是在用户量上来之后才建立的
4. 08-04~08-07 才治理 URL → 说明 URL 的经手环节是逐渐增多的

**每一步都是"上一步的修复暴露了下一步的问题"**——这是真实系统演进的常态，不是规划失误。

### 为什么不推倒重写？

1. **VFS 是全局依赖**：简历、复盘、错题本、语音全部依赖它，重写期间的兼容成本极高
2. **每阶段修复都独立有价值**：重试、日志、user_id、URL 兜底，任何一步都可以单独上线见效
3. **渐进式演进风险可控**：`c291394` 的"三层兜底"就是典型的渐进策略——不改上游，只在读取端增加容错

## 1.4 反事实推理：如果跳过某个阶段？

| 跳过的阶段 | 后果 |
|:---|:---|
| **跳过重试/超时** | VFS 偶发抖动直接变成用户可见失败，且 connect 慢会拖死整个请求 |
| **跳过日志** | user_id 漏传问题永远不会被发现——因为根本看不到调用记录 |
| **跳过 user_id 治理** | 多租户数据归属混乱，用户中心化（错题本按 user 分区等）全部无从谈起 |
| **跳过 URL 治理** | 链接打不开/重复/双重前缀持续发生，用户拿到的文件链接随机失效 |

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 为什么第一阶段是超时拆分与重试（真实原因）

**来源**：git 提交记录 - `a05d7c2`

**提交信息原文**：
```
a05d7c2 | 2026-07-07 | 司棋 | fix: VFS json store 加重试(3次指数退避) + 拆分超时(connect 10s/read 30s)
```

**详细解释**：
- "拆分超时"反证了此前是单一总超时——connect 慢与 read 慢无法区分对待
- "3次指数退避"反证了此前失败即抛错——VFS 偶发抖动直接穿透为用户可见失败
- 这是分布式调用的基本卫生：远程存储调用必须有超时拆分 + 重试退避

**业务场景**：
```
无重试时：
  VFS 偶发抖动（网络闪断、服务重启）→ 调用失败 → 用户上传简历失败
  用户感知："这个产品不稳定"
  实际：只是偶发抖动，重试一次就能成功

有重试后：
  偶发抖动 → 指数退避重试（1s→2s→4s）→ 大概率成功
  用户感知：无感（最好的可靠性就是不被感知）
```

### 2.1.2 为什么 connect 和 read 超时值差 3 倍（真实原因 + 合理推断）

**来源**：git 提交记录 - `a05d7c2`（参数原文）

**提交信息原文**：
```
拆分超时(connect 10s/read 30s)
```

**详细解释**：
- connect 10s：连接建立是轻量操作，10s 足够；超过说明网络/服务有问题，应快速失败
- read 30s：大文件（简历 PDF、面试录音）读取天然慢，需要给足时间
- 单一总超时的两难：设短误杀大文件，设长拖死卡死连接——拆分是唯一解

**技术对比**：
```
单一总超时 20s：
- 大文件读取 25s → 被误杀
- connect 卡死 → 拖到 20s 才失败

拆分（connect 10s / read 30s）：
- 大文件读取 25s → 正常完成 ✓
- connect 卡死 → 10s 快速失败 ✓
```

### 2.1.3 为什么日志覆盖面要三次扩大（真实原因）

**来源**：git 提交记录 - `b215510` → `c669057` → `f3e2204`

**提交信息原文**：
```
b215510 | 2026-08-04 | 司棋 | feat(vfs): VFS 调用加请求日志，包含 url/trace_id/tenant/user/path 等参数
c669057 | 2026-08-04 | 司棋 | feat(vfs): 所有 VFS 接口加请求日志，包含 url/trace_id/tenant/user/body

```

**详细解释**：
- 覆盖面递进："VFS 调用" → "所有 VFS 接口" → "所有直连 VFS 的 HTTP 调用"
- 第一次加日志时低估了调用入口数量：除了 VFSClient 封装的调用，还有绕过客户端直连 HTTP 的调用点
- 可观测的覆盖面必须穷举——漏一个入口，那段链路就是排查黑洞

## 2.2 技术实现原因

### 2.2.1 为什么 user_id 要接口强制而不是约定（真实原因）

**来源**：git 提交记录 - `7bbbcb5`、`fe5939b`

**提交信息原文**：
```

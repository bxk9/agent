# 三层防御方法论 - 原因说明

# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

三层防御不是"设计出来的"，而是**被连续一周的字段丢失事故逼出来的**。git 历史清晰显示：08-02 至 08-04 期间出现了密集的"字段丢失"单点修复，直到 **08-04 提交 `555285d`** 才首次出现"三层防御对齐"的完整表述——这标志着从"逐 bug 打补丁"转向"分层体系化防御"。

## 1.2 真实原因（git 证据链）

### 事故驱动：一周内至少 6 起字段丢失类 bug

| 日期 | Commit | 提交信息 | 暴露的问题层 |
|:---:|:---|:---|:---|
| 08-02 | `035c00b` | fix: 简历个人信息字段丢失/映射错误 + warn() 调用参数错误 | **Schema 层**（字段映射错） |
| 08-02 | `aa29906` | fix: 修复项目经历技术栈字段丢失和排版分散问题 | **Schema 层**（字段缺失） |
| 08-05 | `2e782b2` | 修复一下个人信息的英文字段 | **归一化层**（键名不一致） |
| 08-05 | `ba6d575` | 修复校园活动和项目经历混淆的问题 | **Schema 层**（语义归类错） |
| 08-06 | `08d7027` | 小时匹配不分离 | **正则层**（时间正则切错） |
| 08-07 | `7291bf3` | fix: LLM自创self_assessment英文键名导致补充信息模块异常 | **归一化层**（LLM 自创键名） |

**关键观察**：这些 bug 分布在**三个不同的失败层**——
1. LLM 根本没输出这个字段（Schema 缺失）
2. LLM 输出了但格式/切分不对（正则兜底精度）
3. LLM 输出了但键名漂移（归一化缺失）

**任何单层修复都只能挡住一类**，这就是为什么单点 fix 修了一周还在冒新 bug。

### 体系化时刻：`555285d`（08-04）

提交信息原文（节选）：

> 改动汇总 Fix 1 — resume_sidebar_constants.py（LLM Schema 补字段）新增 portfolio 字段……ize_for_sidebar 和 _normalize_jinja2_data 两个入口均调用，覆盖所有模板路径 **根因修复路径：LLM Schema → 正则兜底精度 → 归一化清洗，三层防御对齐。**

这条提交是三层防御的"出生证明"，它同时说明了三个关键决策：

1. **修复从根因开始**（Schema 补字段），而不是在渲染端打补丁
2. **两个入口都要覆盖**（`customize_for_sidebar` 和 `_normalize_jinja2_data`）——防御必须在**所有消费路径**上生效，漏一个入口等于没防
3. **明确命名为"三层防御"**——说明此时作者已经形成了方法论自觉

### 体系化之后的验证：降级而非拒绝

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 08-08 | `fb29509` | fix(scope): **拒绝渲染改为降级全量渲染** + basicInfo 嵌套容错 + 英文关键字中文化 |
| 08-11 | `b636f11` | fix: extra_sections字段提取增强 + bullet缩进修正 |

`fb29509` 揭示了一个重要的二次决策：**当三层防御仍判定数据异常时，不拒绝渲染，而是降级全量渲染**。原因：

- 【真实】此前"拒绝渲染"策略导致用户拿不到任何产物，体验比"渲染得不够精准"更差
- 【真实】`basicInfo 嵌套容错`说明 LLM 有时把 basic 包一层嵌套、有时不包——归一化层必须兼容两种形态
- 【推断】简历生成是付费转化关键路径，"宁可粗糙不可没有"是产品铁律

## 1.3 为什么是这三层，而不是其他方案？

**淘汰方案 A：只靠 Prompt 约束 LLM 输出**

git 历史中 `7291bf3`（LLM 自创 self_assessment 键名）直接证明——**即使 prompt 明确要求键名，LLM 仍会自创英文键名**。Prompt 是概率性约束，不是确定性契约。团队早期大概率尝试过"把 prompt 写得更严"，但 08-02 至 08-07 持续冒出的键名/字段 bug 说明这条路收敛不了。

**淘汰方案 B：只靠后处理正则清洗**

正则只能处理"输出了但格式不对"，处理不了"根本没输出"（`aa29906` 技术栈字段丢失）。缺字段时正则无米下锅。

**淘汰方案 C：换用 function calling / structured output 强约束**

- 【推断】本项目 LLM 调用走统一网关（blueclaw infra，见 `00fdb1b`），并非所有模型都支持严格 JSON schema 模式
- 【推断】简历提取场景输入是**自由格式简历原文**，字段本身高度可变，刚性 schema 反而会把合法内容拒掉
- 【真实佐证】`4cbdbb4`（08-07 "暂时阉割掉版式提取能力"）说明团队对"能力不稳定就先砍掉"有共识

**三层各自的不可替代性**：

| 层 | 挡什么 | 被哪类 bug 证明必要 |
|:---|:---|:---|
| **Schema 层** | 字段缺失、语义归类错 | `035c00b` `aa29906` `ba6d575` |
| **正则层** | 格式切分错（时间/电话/链接） | `08d7027` `13fff83`（优化时间提取） |
| **归一化层** | 键名漂移、嵌套形态不一、中英文混用 | `7291bf3` `2e782b2` `fb29509` |

三层失败的**交集为空**——没有任何一层能覆盖另外两层的失败模式，这是三层架构的根本理由。

## 1.4 为什么"两个入口都要调用"？

`555285d` 特别强调 `customize_for_sidebar` 和 `_normalize_jinja2_data` 两个入口均调用。

系统存在**两条渲染路径**（侧边栏实时预览 与 Jinja 模板最终渲染），如果只在一个入口做归一化：
- 预览正常、导出异常（或反之）→ 用户看到"预览是好的，下载下来字段没了"
- 这类"薛定谔的 bug"排查成本极高，因为复现取决于走哪条路径

**教训**：防御逻辑必须放在**所有消费路径的公共上游**，或确保每个入口都显式调用。后来 `9b1066c`（08-08 "scope检测逻辑迁移到工具层，修复agent_executor层注入无效问题"）再次验证了同一教训——**逻辑放错层，就会在某个入口失效**。

## 1.5 反事实推理：如果不做三层防御会怎样？

1. **字段丢失率不可收敛**：按 08-02~08-04 的 bug 密度（3 天 4 起字段类 bug），没有体系化防御，每周都会有新字段丢失事故
2. **修复成本线性增长**：每个新模板、新字段都要重新踩一遍坑（15+ 模板 × 15+ 字段）
3. **无法降级**：没有分层判定，就不知道"坏在哪一层"，只能整体拒绝或整体放行，做不出 `fb29509` 那种"降级全量渲染"的精细策略

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 三层防御的提出与命名（真实原因）

**来源**：git 提交记录 - `555285d`

**提交信息原文**：
```
555285d | 2026-08-04 | 11099826 | 改动汇总 Fix 1 — resume_sidebar_constants.py（LLM Schema 补字段）
新增 portfolio 字段……ize_for_sidebar 和 _normalize_jinja2_data 两个入口均调用，覆盖所有模板路径
根因修复路径：LLM Schema → 正则兜底精度 → 归一化清洗，三层防御对齐。
```

**详细解释**：
- 这是"三层防御"概念的出生证明——提交者明确把修复路径命名为"三层防御对齐"
- 三层分别是：LLM Schema（字段补全）→ 正则兜底精度（格式切分）→ 归一化清洗（键名/形态统一）
- 修复从根因（Schema 补字段）开始，而不是在渲染端打补丁

**业务场景**：
```
修复前：用户简历的 portfolio（作品集）字段 LLM 输出了，但 Schema 没声明
       → 渲染层不认识这个字段 → 静默丢弃 → 用户作品集凭空消失
修复后：Schema 补上 portfolio 字段 → 两个渲染入口都能正确消费
```

### 2.1.2 三层划分对应三类正交失败模式（真实原因）

**来源**：git 提交记录 - 08-02 至 08-07 的字段类 bug 序列

**提交信息原文**：
```
035c00b | 2026-08-02 | 11099826 | fix: 简历个人信息字段丢失/映射错误 + warn() 调用参数错误
aa29906 | 2026-08-02 | 11099826 | fix: 修复项目经历技术栈字段丢失和排版分散问题
08d7027 | 2026-08-06 | 11099826 | 小时匹配不分离
7291bf3 | 2026-08-07 | 11099826 | fix: LLM自创self_assessment英文键名导致补充信息模块异常
```

**详细解释**：
- 这些 bug 均匀分布在三类失败层，且**任何单层修复都只能挡住一类**
- 这就是为什么单点 fix 修了一周还在冒新 bug——直到三层体系建立

**失败模式对照**：
```
失败模式 1（Schema 层）：字段没输出 / 映射错
  例：035c00b 个人信息字段丢失、aa29906 技术栈字段丢失
  单层方案"只加正则"无法解决——正则无米下锅

失败模式 2（正则层）：输出了但切分错
  例：08d7027 "8小时"被当成时间区间切开
  单层方案"只补Schema"无法解决——字段在但值是坏的

失败模式 3（归一化层）：输出了但键名漂移
  例：7291bf3 LLM 自创 self_assessment 英文键名
  单层方案"Schema+正则"无法解决——键名都不认识，内容再好也进不了模块
```

### 2.1.3 双入口全覆盖（真实原因）

**来源**：git 提交记录 - `555285d`

**提交信息原文**：
```
ize_for_sidebar 和 _normalize_jinja2_data 两个入口均调用，覆盖所有模板路径
```

**详细解释**：
- 系统有两条渲染路径：侧边栏实时预览（customize_for_sidebar）、Jinja 模板最终渲染（_normalize_jinja2_data）
- 防御逻辑必须在**两个入口都生效**，漏一个入口等于没防

**业务场景**：
```
只防侧边栏入口的后果：
- 用户在预览页看到一切正常
- 点"导出PDF" → 走 Jinja 入口 → 字段丢失
- 用户报障："预览是好的，下载下来没了"
- 这类 bug 复现取决于走哪条路径，排查成本极高
```

——逻辑放错层就会在某个入口失效，这是同一教训的第二次验证。

## 2.2 技术实现原因

### 2.2.1 为什么 Schema 层要"补字段"而不是"删字段"（真实原因）

**来源**：git 提交记录 - `555285d`、`b2384eb`

**提交信息原文**：
```
555285d | 2026-08-04 | 11099826 | …（LLM Schema 补字段）新增 portfolio 字段
b2384eb | 2026-08-10 | 11099826 | feat: 新增学术CV字段 (research_interests, teaching_experience,
          academic_service, grants, citation_metrics, invited_talks, advising, professional_memberships)
```

**详细解释**：
- LLM 可能输出 Schema 未声明的合法字段（如作品集、学术服务）
- 如果 Schema 采取"白名单删除"策略，这些合法内容会被丢弃
- 采取"补字段"策略：发现合法新字段就补进 Schema，内容永不丢失

**量化示例**：
```
b2384eb 一次性新增 8 个学术 CV 字段
若走"模板直接消费 LLM 输出"的旧路：8 字段 × 15 模板 × 3 格式 = 360 个改动点
走契约+Schema 新路：Schema 加 8 字段 + 归一化适配 + 学术模板渲染 ≈ 数十个改动点
```

### 2.2.2 为什么归一化层要"翻译键名"而不是"拒绝未知键"（真实原因）

**来源**：git 提交记录 - `7291bf3`

**提交信息原文**：
```
7291bf3 | 2026-08-07 | 11099826 | fix: LLM自创self_assessment英文键名导致补充信息模块异常
```

**详细解释**：
- LLM 会自创键名（self_assessment、awards、hobbies 的英文变体），这是概率性必然，无法靠 prompt 根治
- 拒绝未知键 = 内容丢失；翻译未知键 = 内容保留
- 实现：`_sanitize_extra_fields` 中的 `_translate_key`（app/tools/resume_sidebar/normalize.py 第 1073 行）

**处理逻辑**：
```
输入: {"self_assessment": "认真负责"}
翻译: self_assessment → 自我评价（已知映射）
输入: {"some_unknown_key": "..."}
兜底: 保留原文进入 extra_sections，绝不丢弃
```

### 2.2.3 为什么需要嵌套容错（真实原因）

**来源**：git 提交记录 - `fb29509`

**提交信息原文**：
```
fb29509 | 2026-08-08 | 11099826 | fix(scope): 拒绝渲染改为降级全量渲染 + basicInfo 嵌套容错 + 英文关键字中文化
```

**详细解释**：
- LLM 有时输出 `{"basicInfo": {...}}`，有时输出 `{"basic": {...}}`，有时多包一层嵌套
- 归一化层必须兼容所有形态，统一展平
- 实现：`_pre_normalize_raw_data`（normalize.py 第 1942 行）

### 2.2.4 为什么语义归类要结合毕业年份（真实原因）

**来源**：git 提交记录 - `ba6d575`、`0141ea9`、`ec8d913`

**提交信息原文**：
```
ba6d575 | 2026-08-05 | 11099826 | 修复校园活动和项目经历混淆的问题
0141ea9 | 2026-08-05 | 11099826 | 修复'美团'分到校园活动中
ec8d913 | 2026-08-04 | 11099826 | 优化学习部长的提取效果
```

**详细解释**：
- "学生会部长""学习部长"这类经历既可能是校园活动也可能是工作，纯关键词判定必错
- 解法：`_is_campus_activity(item, grad_year)` 结合毕业年份判断 + 公司白名单强制纠正
- `_AMBIGUOUS_CAMPUS_KEYWORDS`（resume_sidebar_constants.py 第 59 行）专门维护歧义词表

**判定逻辑**：

```

## 2.3 性能与质量原因

### 2.3.1 为什么"拒绝渲染"改为"降级全量渲染"（真实原因）

**来源**：git 提交记录 - `fb29509`

**提交信息原文**：
```
fb29509 | 2026-08-08 | 11099826 | fix(scope): 拒绝渲染改为降级全量渲染 + basicInfo 嵌套容错 + 英文关键字中文化
```

**详细解释**：
- 旧策略：三层防御判定数据异常 → 拒绝渲染 → 用户拿不到任何产物
- 新策略：分级降级，永远有产物交付
- 简历生成是核心转化路径，"宁可粗糙不可没有"（合理推断，业务常识）

**降级分级**（合理推断，基于提交信息的策略展开）：
```
异常等级 1（字段缺失）  → 补默认值，正常渲染
异常等级 2（局部格式错）→ 跳过该字段，其余正常渲染
异常等级 3（整体不可用）→ 降级全量渲染（原文直出），绝不拒绝
```

### 2.3.2 为什么去重要保护 AI 标记内容（真实原因）

**来源**：git 提交记录 - `5f3a3e0`、`01245da`

**提交信息原文**：
```
5f3a3e0 | 2026-08-06 | 11099826 | 解决教育背景中获奖情况提取问题 简历中已有内容不做红色AI标记
01245da | 2026-08-06 | 11099826 | 发生过的修改，都要标记出来
```

**详细解释**：
- AI 修改过的内容会打标记（供用户识别哪些是 AI 改的）
- 去重逻辑如果粗暴丢弃重复条目，可能把带标记的内容丢掉 → 用户看不到 AI 的修改
- 实现：`_dedup_work_experience` 内部的 `_has_ai_mark` 判定（normalize.py 第 751 行），带标记内容优先保留；重复条目用 `_merge_bullets` 合并而非丢弃

## 2.5 业务价值原因

- 体系化后：bug 上升到"策略层"——说明基础防御已生效，剩余问题都是防御策略本身的打磨
- 15+ 模板 × 15+ 字段的规模下，没有体系化防御，每个组合都是潜在事故点（合理推断）

### 2.5.2 为什么这套方法论可复用（合理推断）

**详细解释**：
- 任何"LLM 输出 → 结构化消费"的链路都有同样的三类失败模式
- 迁移要点：先枚举失败模式 → 按正交性分层 → 保证所有消费入口过防御层
- 本项目内已有第二个应用实例：scope 检测的"规则 + LLM 意图分类兜底"（`772a2ee`）同样是多层防御思路

## 3. 总结

### 3.1 核心原因总结

1. **三层对应三类正交失败模式**（真实）：缺失/格式/键名，交集为空，单层必漏
2. **双入口全覆盖**（真实）：预览与导出两条路径都要防御，否则出现"薛定谔的 bug"
3. **补字段而非删字段**（真实）：LLM 会输出合法新字段，内容永不丢失
4. **降级而非拒绝**（真实）：核心转化路径永远要有产物交付

### 3.2 技术原因总结

1. **键名翻译**（真实）：LLM 自创键名是概率性必然，只能翻译不能拒绝
2. **嵌套容错**（真实）：LLM 输出形态不一，归一化层统一展平
3. **毕业年份归类**（真实）：歧义经历纯关键词判定必错，需结合时间维度
4. **集中实现**（真实）：4008 行单一文件 = 单一真理源，避免各模板各自实现

### 3.3 业务价值总结

1. **bug 收敛**（真实）：从每周多发的数据层 bug 收敛为策略层打磨
2. **交付可靠**（真实）：降级策略保证用户永远拿得到产物
3. **可扩展**（真实）：新增 8 个学术字段不动 15+ 模板

# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

INPUT_REQUIRED 状态位承担"隐式锁"职责，根源是本项目与主 Claw 之间**基于状态驱动的会话协议**：git 历史显示，input_required 状态的进入/退出直接影响主 Claw 的超时判定与心跳行为（08-11 至 08-13 的三次修复）。在这个协议下，"状态位即锁"是**协议语义的自然延伸**，而不是额外发明一套锁机制。

## 1.2 真实原因（git 证据链）

### input_required 状态是会话协议的一等公民

| 日期 | Commit | 提交信息 |

- 主 Claw 有 **180s 超时断连**机制——180 秒收不到有效消息就断开。这意味着任何"等待用户输入"的状态都面临被超时误杀的风险

- 这直接解释了为什么 INPUT_REQUIRED 状态必须有完整的生命周期管理：
  1. 进入等待 → 必须有心跳保活（否则 180s 被断）
  2. 用户响应 → 必须及时转回 running/complete
  3. 重新部署 → 状态必须正确恢复（`391ca79` 的事故场景）

## 1.3 为什么用状态位做隐式锁，而不是显式锁？

### 协议语义已经提供了锁的全部要素

对照锁的三个要求：

| 锁的要求 | 显式锁方案 | INPUT_REQUIRED 状态位 |
|:---|:---|:---|
| **互斥标记** | 独立的 lock 字段 | 状态位本身（协议已有） |
| **释放路径** | 需手动 unlock + 超时保护 | 状态机转换天然覆盖（complete/超时/取消） |
| **可观测性** | 需额外暴露锁状态 | 状态位本身就在日志/协议中可见 |

状态位方案**零新增组件**，且释放路径由状态机保证——这是选择它的根本原因。

### 显式锁在本场景的三个劣势

1. **锁泄漏风险**：显式锁如果持有者崩溃，锁会残留，需要额外的超时回收机制。而状态位随会话生命周期自然清零
2. **双真相源**：引入独立锁字段后，"锁状态"和"任务状态"可能不一致（锁着但任务已完成），产生新的 bug 类别
3. **协议穿透**：主 Claw 需要知道会话处于 input_required（心跳策略依赖它，见 `391ca79`）——状态位是协议的一部分，独立锁字段则无法穿透协议

### 180s 超时约束对锁设计的反向要求

主 Claw 的 180s 超时意味着：**锁（等待状态）不能无限期持有**。这要求：
- 等待期间必须有心跳保活（`76e5f37` 的空文本心跳）
- 锁的持有者（等待中的任务）必须能被超时机制强制释放
- 状态位方案天然满足：超时 → 状态转换 → 锁自动释放

## 1.4 配套治理的"为什么"

### 为什么 namespace 要单一真理源？

INPUT_REQUIRED 检查需要精确定位"哪个 session 的哪个 task 在等待"。如果 task_store、VFS、ctx_log 三处的 namespace 定义不一致，锁检查可能查错位置——查不到等待中的任务 → 误开新任务 → 状态撕裂。

### 为什么 task_store 按 user_id 分区？

锁的粒度是 session，但查询的入口往往是 user：
- 用户重连时（新 session）要能看到自己等待中的任务
- 多租户隔离要求 A 用户绝不能看到 B 用户的任务状态
- user_id 主分区 + session 二级索引同时满足两者

### 为什么重新部署是高危时刻？

"重新部署后主Claw超时"说明：部署重启会丢失内存中的状态，如果重启后没有正确恢复/清理 input_required 状态，心跳策略就会错乱。**有状态的锁机制必须回答"进程重启后锁怎么办"**——这是状态位方案必须配套持久化或清理策略的原因。

## 1.5 反事实推理：如果用显式锁会怎样？

1. **锁泄漏事故**：服务崩溃/重启后锁残留，用户的会话永远"等待中"，需要人工清理
2. **双真相源 bug**：锁状态与任务状态不一致时，排查需要同时看两处数据
3. **协议不兼容**：主 Claw 的心跳策略依赖 input_required 状态（`391ca79`），独立锁无法替代这个协议语义——最终还是得维护状态位，显式锁变成冗余

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 为什么 input_required 是"锁"的天然载体（真实原因）

**来源**：git 提交记录 - `a9de03d`、`391ca79`

**提交信息原文**：
```
a9de03d | 2026-07-08 | yitong | fix(executor): relay 指令拼入 input_required 的 message text 兜底
391ca79 | 2026-08-11 | 司棋   | fix: input_required → complete，停止心跳避免重新部署后主Claw超时
```

**详细解释**：
- input_required 不是普通状态，是协议的一等公民：它承载跨 Agent 通信（relay 指令挂载）、驱动心跳策略、影响主 Claw 超时判定
- 既然协议已经围绕这个状态构建了完整行为，用它做锁是"顺势而为"
- 另起一套锁机制 = 与协议语义平行的一套新概念 = 维护两套真相

**业务场景**：
```
用户："帮我生成简历"
Agent："请上传原稿" → 进入 input_required
此时协议行为自动切换：
  - 心跳启动（保活）
  - 主 Claw 知道会话在等待
  - 新消息被识别为"应答"而非"新请求"
这些行为都绑定在状态位上——锁的语义已经存在，只需明确使用
```

### 2.1.2 为什么心跳要"识别 + 无感"双满足（真实原因）

**来源**：git 提交记录 - `ab4416e`、`76e5f37`

**提交信息原文**：
```
ab4416e | 2026-08-13 | 司棋 | fix: 恢复心跳 message 字段，修复主Claw 180s 超时断连
76e5f37 | 2026-08-13 | 司棋 | fix: 心跳 message 用空文本，主Claw 能识别心跳且用户无感
```

**详细解释**：
- 主 Claw 180s 收不到有效消息就断连——等待用户的会话必须有活性证明
- 第一次修复恢复心跳字段，解决了断连，但心跳消息用户可见 → 污染对话
- 第二次修复用空文本：主 Claw 能识别（协议层），用户看不到（展示层）
- 一天两修说明这两个约束都是硬性的，缺一不可

**技术对比**：
```
无心跳：
- 等待超过 180s → 主 Claw 断连 → 会话丢失
- 用户回来发现"面试没了"

心跳用户可见（第一次修复后）：
- 不断连 ✓
- 但对话里出现心跳消息 → 用户困惑 ✗

空文本心跳（最终方案）：
- 不断连 ✓
- 用户无感 ✓
```

### 2.1.3 为什么并发任务必须显式清理（真实原因）

**来源**：git 提交记录 - `871a28d`

**提交信息原文**：
```
871a28d | 2026-08-11 | 11099826 | fix: WebSocket连接关闭时取消所有运行中任务 + 发送异常保护
```

**详细解释**：
- "取消所有运行中任务"（复数）证明并发任务是真实存在的
- 连接关闭不清理 → 任务继续跑 → 资源浪费 + 状态残留
- "发送异常保护"：关闭过程中还要发消息（如告别/状态上报），发送失败不能抛异常
- 这是锁的"异常释放路径"：连接断开也要能正确释放

## 2.2 技术实现原因

### 2.2.1 为什么淘汰显式锁（Redis Lock/Mutex）（合理推断）

**详细解释**：
- 锁泄漏：持有者崩溃后锁残留，需要额外的超时回收机制
- 双真相源：锁状态与任务状态可能不一致（锁着但任务已完成）
- 协议不穿透：主 Claw 的心跳策略依赖 input_required 状态本身，独立锁字段无法替代
- 结论：显式锁在本场景是冗余——协议状态已提供锁的全部要素

**方案对比**：
```
显式锁（Redis Lock）：
+ 通用、成熟
- 锁泄漏需回收机制
- 与任务状态双真相源
- 主 Claw 不认识，无法驱动心跳
- 新增组件与依赖

状态位锁（最终方案）：
+ 零新增组件
+ 释放路径由状态机保证
+ 协议原生，驱动心跳
+ 可观测（状态在日志/协议中）

- 要求状态机简单清晰（本场景满足）
```

### 2.2.2 为什么锁粒度是 session 不是 user（合理推断）

**详细解释**：
- session 级：同一用户可开多个会话并发做不同事（一个改简历、一个做面试）
- user 级：粒度太粗，多会话场景被误伤——用户在 A 会话等待时，B 会话被锁住
- 但查询入口是 user：用户重连（新 session）要能找回等待中的任务
- 解法：锁粒度 session + 存储分区 user_id（task_store 主分区）

### 2.2.3 为什么部署重启要专门治理（真实原因）

**来源**：git 提交记录 - `391ca79`

**提交信息原文**：
```
391ca79 | 2026-08-11 | 司棋 | fix: input_required → complete，停止心跳避免重新部署后主Claw超时
```

**详细解释**：
- 部署重启丢失内存状态，但主 Claw 侧的连接/状态可能残留
- 残留的 input_required + 持续心跳 → 主 Claw 超时异常
- 治理：部署时把 input_required 转 complete + 停止心跳
- 教训：**有状态的锁必须回答"进程重启后锁怎么办"**——这是状态机设计的必答题

## 2.3 性能与质量原因

### 2.3.1 为什么等待状态不能无限期持有（真实原因）

**来源**：git 提交记录 - `ab4416e`（180s 超时机制）

**详细解释**：
- 主 Claw 的 180s 超时是硬约束——这是"锁不���无限持有"的外部强制
- 心跳保活解决"不被误杀"，但业务层仍需处理"用户永远不回来"
- 完整方案：心跳保活（协议层）+ 业务定期检查（应用层）+ 状态机超时转换（释放路径）

### 2.3.2 为什么"连发消息"要注入而不是拒绝（合理推断）

**详细解释**：
- 拒绝等待中的消息：用户体验极差——"我说话 AI 不理"
- 每条消息开新 task：state 撕裂——两个 task 改同一份状态
- 注入原 task：消息作为"应答"进入等待中的任务——符合对话语义
- 这是"追问场景"的自然要求：用户的补充信息应该进入正在等待的任务

## 2.4 工程实现原因

### 2.4.1 为什么 namespace 要单一真理源（合理推断）

**详细解释**：
- INPUT_REQUIRED 检查要精确定位"哪个 session 的哪个 task 在等待"
- task_store / VFS / ctx_log 三处 namespace 不一致 → 查错位置 → 查不到等待任务 → 误开新 task
- 单一真理源：一处定义、多处引用，锁定位永远准确

### 2.4.2 为什么 task_store 要 user_id 主分区（合理推断）

**详细解释**：
- 多租户隔离：A 用户绝不能看到 B 用户的任务（安全底线）
- 跨会话查询：用户重连后按 user_id 找回等待中的任务
- session 二级索引：锁的粒度是 session，查询要快
- 主分区 + 二级索引同时满足隔离与查询

## 2.5 业务价值原因

### 2.5.1 为什么"等待"是 Agent 产品的核心状态（合理推断）

**详细解释**：
- Agent 与工具的本质区别：Agent 会主动向用户要信息（追问、补充）
- "等待用户输入"是 Agent 交互的高频状态，不是边缘场景
- 这个状态的任何 bug（撕裂、误杀、残留）都直接破坏对话体验
- 因此值得用协议级的完整方案治理

### 2.5.2 为什么这套方案可复用（合理推断）

**详细解释**：
- 任何有状态交互系统都有"等待-应答"模式：对话 AI、表单、审批流、回合制游戏
- 迁移要点：状态机简单 + 释放路径完整（含重启）+ 可观测
- 核心认知：并发控制不一定要引入锁组件——协议状态本身就是最好的锁

## 3. 总结

### 3.1 核心原因总结

1. **状态位是协议一等公民**（真实）：承载通信、驱动心跳、影响超时，锁语义已存在
2. **180s 超时是硬约束**（真实）：等待状态必须心跳保活
3. **心跳要双满足**（真实）：系统可识别 + 用户无感，空文本是解
4. **并发任务真实存在**（真实）：连接关闭必须显式清理

### 3.2 技术原因总结

1. **淘汰显式锁**（合理推断）：锁泄漏、双真相源、协议不穿透
2. **session 粒度 + user 分区**（合理推断）：锁粒度与查询入口分离
3. **部署治理**（真实）：重启后状态必须明确清理
4. **namespace 单一真理源**（合理推断）：锁定位准确的前提

### 3.3 业务价值总结

1. **交互自然**：连发消息、追问、等待都符合直觉
2. **连接稳定**：180s 断连根治
3. **数据安全**：多租户任务严格隔离

## 2. 项目背景与问题定义

### 2.1 业务场景

AI 简历生成的渲染体系：

```
LLM 结构化输出（15+ 字段，持续增长）
    ↓
AI 标记契约（稳定的中间层）
    ↓
15+ 模板 × 3 格式（HTML/DOCX/PDF）渲染
```

### 2.2 M × N × K 组合爆炸

**不加治理的耦合点**：

```
M：LLM 输出字段 ~15+（且持续增长，b2384eb 一次加 8 个学术字段）
N：15+ 套模板（技术型/学术型/通用型/创意型/Master Profile）
K：3 种输出格式（HTML / DOCX / PDF）

无契约时的影响面：任何字段变更 = N × K = 45+ 个渲染点
```

**真实事故证据**：

|:---:|:---|:---|

| 08-07 | `f60a9ba` | jpdf 和 word 渲染的内容保持一致 |
| 08-07 | `9609b3a` | 模块顺序重排算法修复 + Word 模板损坏兜底 + 字段去重增强 |

### 2.3 优化目标

**核心问题**：如何让字段变更、模板新增、格式扩展互不牵连？

**量化目标**：
- 字段变更不波及全部模板（契约隔离）
- 新模板成本 = 一份 CSS + Jinja（不动 LLM 与渲染核心）
- 导出零内容丢失（契约校验 + 降级兜底）

## 3. 技术方案设计

### 3.1 核心思路

**契约层解耦**：

```
LLM 输出（M 变化） ──▶ AI 契约（稳定） ──▶ 模板渲染（N × K）

契约特点：
- 字段名固定、语义明确、版本化
- 主字段（教育/工作/项目）所有模板必渲染
- extra_sections（奖项/语言/爱好）模板可选渲染
```

### 3.2 契约设计规则表

| 规则 | 内容 | 防御的问题 |
|:---|:---|:---|
| **主字段必填** | 教育/工作/项目的核心字段必填 | 内容丢失（`135c21d`） |
| **弱字段可选** | extra_sections 模板选择性渲染 | 模板差异 |
| **日期 canonical** | 存储层只有一种形态（YYYY-MM / 至今） | 格式混乱 |
| **向后兼容** | 新增字段默认值兼容，禁止删字段/改语义 | 版本演进 |

### 3.3 渲染分层

```
AI 契约（稳定）
    ↓
渲染适配层（契约 → 中间 IR）
    ↓
────────────────────────────
HTML 渲染   DOCX 渲染   PDF 渲染
    ↓          ↓          ↓
resume_html  python-docx  weasyprint
```

**IR（中间表示）**：把契约映射为"通用文档结构"（章节、段落、列表、表格），各格式各自渲染——15 模板 × 3 格式的 45 个组合共享上层逻辑。

## 4. 核心实现细节

### 4.1 契约示范

```yaml
# AI Contract
basic:
  name: str                    # 必填
  gender: str | null           # 可选
  avatar_url: str | null       # 可选，claw:// 协议
education:
  - school: str                # 必填
    degree: str                # 必填
    major: str | null
    start_date: str            # 必填，YYYY-MM 格式
    end_date: str | "至今"     # 必填
    courses: list[str] | null  # 可选
work_experience:
  - company: str
    position: str
    start_date: str
    end_date: str | "至今"
    bullets: list[str]         # 每条 40-80 字
project_experience: [...]
extra_sections:                # 弱字段
  awards: list[str] | null
  languages: list[str] | null
  hobbies: list[str] | null
```

### 4.2 模板矩阵组织

```
resume_templates/
├── shared/            ← 共享组件（教育块、工作块）
├── modern_dark/
│   ├── template.html  ← Jinja 结构
│   └── styles.css     ← 差异化样式
├── academic_cv/
│   └── ...
└── ...（15+ 套）
```

| 类别 | 模板数 | 特点 |
|:---|:---:|:---|
| **技术型** | 3-4 套 | 突出技术栈、GitHub / 项目链接 |
| **学术型** | 2-3 套 | 论文、导师、Academic CV |
| **通用型** | 5-6 套 | 标准商务、时间线、双栏 |
| **创意型** | 2-3 套 | 配色、图标、非标准布局 |
| **Master Profile** | 1 套特殊 | 学生个人档案（不同于简历） |

**核心不变量**：所有模板都从**同一个 AI 契约**渲染。新模板成本 = 一份 CSS + Jinja（约 100-300 行），不动 LLM Prompt、不改数据结构、不修 DOCX/PDF 核心代码。

### 4.3 scope 治理：局部修改的三层方案

**scope（"只改简历的某一部分"）是契约层最复杂的应用场景**：

```
第 1 层：scope 检测放在工具层（9b1066c）
  教训：放在 agent_executor 层"注入无效"——逻辑放错层就不生效
  
第 2 层：规则判不了时 LLM 意图分类兜底（772a2ee）
  scope 判定本身不可靠 → 规则 + LLM 双层
  
第 3 层：判错时降级全量渲染（fb29509）
  宁可全量重渲，不拒绝交付
```

**配套约束**（真实，commit `20722c6`"对压缩和部分内容修改进行约束"）：
```
- 局部修改不得破坏整体一致性
- auto_compress 默认 False（e4117a9）：宁可一页放不下，不擅自删内容
```

### 4.4 AI 标记的可视化层

**AI 标记色演进**（真实）：

```
5428713（08-08）：AI标记色红色→紫色
09c6655（08-08）：AI标记色改为紫色系(#8b5cf6)
原因：红色在简历语境中有"错误/警告"的负面联想，紫色更中性
5f3a3e0（08-06）：简历中已有内容不做红色AI标记
01245da（08-06）：发生过的修改，都要标记出来
```

AI 标记是契约的可视化层：用户能看到"哪些是 AI 改的"，标记数据随契约流转，去重时受保护（01 号文档的 `_has_ai_mark`）。

### 4.5 边界 case 处理

**Case 1：字段扩展（`b2384eb` 一次加 8 个学术字段）**
```
research_interests / teaching_experience / academic_service / grants
citation_metrics / invited_talks / advising / professional_memberships
处理：契约加字段 + 归一化适配 + 学术模板渲染
不动：其余 15+ 模板（无学术字段的模板直接忽略）
```

**Case 2：Word 模板损坏（`9609b3a`）**
```
处理：Word 模板损坏兜底——降级到其他渲染路径，不阻塞交付
```

**Case 3：PDF/Word 内容不一致（`f60a9ba`）**
```
根因：两种格式各读各的字段、各走各逻辑
处理：统一从契约渲染，内容一致性由契约保证
```

**Case 4：一页压缩（`e4117a9`）**
```
"压缩到一页精准控制 + auto_compress默认False"
原则：压缩是用户显式选择，绝不自动删内容
```

## 5. 效果评估与优化

### 5.1 耦合点对比

| 指标 | 无契约 | 有契约 |
|:---|:---|:---|
| 新增一个模板成本 | 改 LLM prompt + 数据结构 + 3 种渲染代码（~周） | **一份 CSS + Jinja（~小时）** |
| LLM prompt 修改影响面 | 所有模板都可能挂 | **契约层拦住** |
| 15 模板×3 格式的耦合点 | 675 处（15×15×3） | **~50 处**（分层收敛） |
| 新增 8 个学术字段 | 360 个改动点 | **Schema + 归一化 + 学术模板** |

### 5.2 事故收敛验证

```
契约前（07-16 ~ 08-07）：
  135c21d 导出内容丢失 → 22e8097 bullet 不统一 → f60a9ba PDF/Word 不一致
  事故在"渲染层"反复出现

契约 + scope 治理后（08-08 起）：
  修复上升到策略层（降级、入口迁移、压缩约束）
  基础渲染事故收敛
```

## 6. 技术亮点总结

### 6.1 创新性

1. **中间契约解耦**：M×N×K 组合爆炸收敛为分层结构
2. **scope 三层方案**：层迁移 + LLM 兜底 + 降级，治理最复杂的局部修改
3. **AI 标记可视化**：契约的修改痕迹层，用户可感知 AI 贡献

### 6.2 技术深度

1. **数据契约设计**：字段稳定性、版本化、向后兼容策略
2. **渲染分层**：契约 → IR → 多格式渲染
3. **降级工程**：拒绝渲染 → 降级全量渲染的产品决策

### 6.3 业务价值

1. **扩展性**：新模板小时级交付，新字段不波及全模板
2. **交付可靠**：导出零内容丢失，模板损坏有兜底
3. **用户信任**：AI 标记透明，压缩不擅自删内容

### 6.4 方法论抽象与迁移（原文档保留部分）

**中间契约的三个价值**：

1. **解耦上下游**：LLM 侧和渲染侧独立演进
2. **稳定的 API**：契约是团队协作的"公共接口"
3. **可测试性**：契约层可以独立造样本、测试

**与"数据契约"运动的关系**：现代数据工程的 Data Contract（Data Mesh 相关）概念，本设计是其在 LLM 应用中的实践。

**可迁移场景**：

| 场景 | 迁移点 |
|:---|:---|
| **AI 应用 + 多渲染** | 完全适用 |
| **多前端复用同一后端** | 契约 = 前后端合约 |
| **数据仓库表设计** | 稳定契约 + 多下游消费 |
| **微服务 API** | Interface segregation |

**反例警示**：

- **反例 1**：不建契约，LLM 输出直接进模板 → 改一次 prompt 45 个模板全挂
- **反例 2**：契约字段过多细节 → 变成"模板专属字段"，失去解耦价值
- **反例 3**：不做版本化 → 无法向前兼容
- **反例 4**：横切逻辑放错层（`9b1066c` scope 注入无效）→ 形同虚设

## 7. 面试问答准备

### Q1: 为什么需要契约层，直接渲染不行吗？

**A**：
1. 实证：契约前的事故链——导出内容丢失（`135c21d`）、bullet 不统一（`22e8097`）、PDF/Word 不一致（`f60a9ba`）
2. 根因：渲染直接消费 LLM 原始输出，LLM 形态一变，所有模板同时受影响
3. 契约层把"LLM 的多变"隔离在契约之前，渲染侧只面对稳定结构

### Q2: 契约的版本兼容怎么做？

**A**：
1. 新增字段：默认值兼容，老模板忽略新字段（`b2384eb` 加 8 个学术字段不动其他模板）
2. 删除字段：禁止，只能标记 deprecated
3. 改字段语义：禁止，必须新字段 + 迁移

### Q3: scope（局部修改）为什么难？

**A**：
1. 要精确知道"哪些字段属于哪个模块"——依赖契约的模块映射
2. 检测逻辑放错层会失效（`9b1066c` 从 agent_executor 迁到工具层）
3. 判定不可靠要 LLM 兜底（`772a2ee`），判错要降级（`fb29509`）
4. 三层方案：工具层检测 + LLM 意图兜底 + 降级全量渲染

### Q4: 为什么 auto_compress 默认关闭？

**A**：
1. 自动压缩曾误删用户内容（与 `20722c6` 的约束相呼应）
2. 简历内容对用户是资产——宁可一页放不下，不能擅自删
3. 压缩是用户显式选择（`e4117a9`"压缩到一页精准控制"）

### Q5: 这个架构的迁移价值？

**A**：
1. 任何"LLM 输出 + 多消费端"的系统：契约隔离多变性
2. 迁移要点：契约字段稳定 + 版本化 + 所有消费端过契约层
3. 与 Data Mesh 的 Data Contract 同构，可对标讲述

## 9. 总结

AI 标记契约与模板矩阵是一个典型的**架构解耦案例**，展示了：

1. **组合爆炸收敛**：M×N×K 耦合点通过契约层分层收敛
2. **扩展性设计**：新模板小时级、新字段零波及
3. **复杂场景治理**：scope 三层方案 + 降级工程

**一句话总结**：以稳定的 AI 标记契约隔离 LLM 输出与 15+ 模板 × 3 格式的渲染，把 M×N×K 组合爆炸收敛为分层架构，新模板只需一份 CSS、新字段不波及全模板，是 LLM 应用数据契约的完整实践。

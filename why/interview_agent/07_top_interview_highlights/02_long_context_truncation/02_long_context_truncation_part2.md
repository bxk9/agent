            f"tokens {before} -> {after}, trace_id={trace_id}")
# 否则裁错了无从排查：用户反馈"AI 忘了我刚才说的"，必须能回查裁掉了什么
```

### 4.4 边界 case 处理

**Case 1：tool_call 在预算边界上**
```
场景：移除某配对后仍超预算 100 token
处理：继续移除下一个 P3/P4 配对，绝不移除 P1 最近对话
原则：宁可多裁一对低优先级，不动最近对话
```

**Case 2：历史配对已被引用**
```
场景：第 3 轮的简历 tool_response 在第 15 轮被追问引用
处理：引用检测——被后续消息引用的配对升级为 P2 保留
反例：f13d71e 的"过期链接透传导致空转"——引用失效比保留更危险
```

**Case 3：裁剪后仍超限**
```
场景：P3/P4 裁完仍超预算
处理：对 P1 之外的对话轮次做摘要压缩（保留最近 N 轮原文）
兜底：极端情况下结束当前任务并提示用户（绝不带着残缺上下文硬跑）
```

## 6. 技术亮点总结

### 6.1 创新性

1. **配对感知裁剪**：把 LLM API 的协议约束（tool_call/response 配对）内化为裁剪算法的原子性约束
2. **观测驱动决策**：先建 token 统计，再定裁剪策略——数据先行
3. **裁剪与日志绑定**：每次裁剪留痕，可追溯可回查

### 6.2 技术深度

1. **协议层理解**：理解 OpenAI 兼容协议的 tool_call_id 配对要求
2. **异步工程**：token 统计在 run_in_executor 场景下的 contextvar 失效问题及 FIFO 字典解法
3. **优先级建模**：P0-P4 裁剪优先级的信息价值建模

### 6.3 业务价值

1. **语音面试稳定性**：20+ 轮长对话不中断
2. **成本可见**：请求级 token 汇总支撑成本核算
3. **方法论可迁移**：任何多轮 Agent 系统的上下文治理

### 6.4 方法论抽象与迁移（原文档保留部分）

**抽象出的通用方法论——"观测 → 剖分 → 治理"三步**：

1. **观测先行**：任何优化前先建度量。没有 token 统计，裁剪阈值只能靠猜（本项目观测本身就修了三个 bug：为 0、跨线程失效、日志分散）
2. **约束内化**：把外部协议的硬约束（配对要求）变成算法的原子性约束，而不是事后校验
3. **有损操作必留痕**：裁剪/压缩/摘要都是有损的，必须记录"损了什么"，否则问题无法归因

**可迁移场景**：

| 场景 | 迁移点 |
|:---|:---|
| 客服机器人多轮对话 | 同样的配对裁剪 + 优先级保留 |
| 代码助手长会话 | 工具调用产物（文件内容）的裁剪策略 |
| RAG 多轮检索 | 检索结果的优先级保留与过期清理 |
| 任何 token 成本敏感系统 | 请求级 token 观测体系 |

**反例警示**：
- **反例 1**：无观测直接裁 → 裁多裁少全凭感觉，效果无法验证
- **反例 2**：硬截断不配对 → 孤儿消息导致 API 报错，裁剪本身成为故障源
- **反例 3**：裁剪不留日志 → 用户反馈"AI 失忆"时无从排查

## 7. 面试问答准备

### Q1: 为什么裁剪必须以配对为原子单位？

**A**：
1. LLM API 协议要求 tool_call 与 tool_response 按 tool_call_id 严格配对
2. 孤儿 tool_call → API 400 或模型空转；孤儿 tool_response → tool_call_id not found
3. 裁剪本身不能成为新故障源——这是配对约束的根本理由
4. 项目内旁证：`f13d71e` 证明上下文中的无效引用会让下游 Agent 空转

### Q2: 裁剪优先级怎么定？

**A**：
1. P0 系统 prompt 永不裁（人设根基）
2. P1 最近 N 轮完整对话保留（追问场景需要精确历史）
3. P2 被后续引用的产物保留（引用检测）
4. P3/P4 大而无用的历史配对优先裁（信息密度低）
5. 本质：按"对后续对话的信息价值"排序

### Q3: 为什么不用摘要压缩？

**A**：
1. 摘要要额外调一次 LLM，语音实时场景延迟不可接受
2. 摘要丢细节，面试追问需要原文（"你刚才说……"）
3. 摘要是兜底手段（P3/P4 裁完仍超限时才用），不是主策略

### Q4: 如何验证裁剪没裁错？

**A**：
1. 裁剪与日志绑定（`1d3a318` 同一提交）：记录裁了哪些配对、token 前后值、trace_id
2. token 统计体系（`ed1c3b8`）提供请求级成本视图
3. 用户反馈"AI 忘了刚才说的"时可凭 trace_id 回查裁剪记录

### Q5: 这个方案的局限与演进方向？

**A**：
1. 局限：引用检测是启发式的，复杂引用链可能漏检
2. 演进：语义级裁剪（按信息熵保留）、分层缓存（产物外置 + 按需拉取）
3. 与 RAG 的结合：把大产物从上下文移到检索层，从根上减少裁剪需求

1. **协议理解**：把 LLM API 的配对约束转化为算法原子性约束
2. **数据驱动**：观测先行，裁剪决策有 token 数据支撑

- 与司棋侧 `1018c6a`（"pdf_tip 由 executor 直接拼接，不走 LLM 转发"）是同一思路

### 2.2.3 为什么重试必须有预算（真实原因）

**来源**：git 提交记录 - `08bcac0`、`7a9a540`

**提交信息原文**：
```
08bcac0 | 2026-08-06 | yitong | 优化语音输出150分钟的问题；解决模型未遵循json的问题
7a9a540 | 2026-08-07 | yitong | 语音错题本识别增加重试机制
```

**详细解释**：
- `08bcac0` 证明无约束重试 = 耗时炸弹：JSON 持续不合规时循环累积到 150 分钟
- 但重试本身有价值（`7a9a540` 主动给错题本识别加重试）——提高成功率
- 正确姿势：**有预算的重试**——次数上限 + 退避 + 超预算降级
- 重试次数 × 单次超时 ≤ 用户可接受的等待阈值

**技术对比**：
```
无约束重试（事故模式）：
  while not success: retry()
  → 失败模式持续时无限循环 → 150 分钟

有预算重试（最终方案）：
  for i in range(MAX_RETRIES): retry_with_backoff()
  超预算 → 降级处理
  → 成功率与尾部延迟双可控
```

## 2.3 性能优化原因

### 2.3.1 为什么模型切换只是兜底不是主手段（真实原因）

**来源**：git 提交记录 - `874b360`

**提交��息原文**：
```
874b360 | 2026-08-04 | yitong | 增加兜底v4 pro模型
```

**详细解释**：
- "兜底"二字明确了定位：主模型慢/挂时保可用性，不是日常延迟优化
- 换快模型牺牲质量（面试追问深度），不能作为主手段
- 150 分钟问题换什么模型都解决不了——应用层循环逻辑与模型无关

### 2.3.2 为什么用"断开时长"做目标函数（真实原因）

**来源**：git 提交记录 - `83f0849`

**提交信息原文**：
```
83f0849 | 2026-08-04 | yitong | 增加断开时长
```

**详细解释**：
- 延迟优化的终点不是技术指标（P99 多少 ms），而是业务后果（用户流失）
- 断开时长直接度量"用户能忍多久"——这是 SLA 的真实来源
- 技术侧分段耗时（系统慢在哪）+ 用户侧断开时长（慢到什么程度用户走）= 完整的优化闭环

**SLA 推导**：
```
拍脑袋 SLA："响应要在 3 秒内"（无依据）
数据驱动 SLA：
  统计断开时长分布 → 发现多数用户在等待 X 秒后断开
  → SLA 定为"首字节 < X 秒的某个分位"
  → 优化目标有业务意义，验收有数据依据
```

## 2.4 工程实现原因

### 2.4.1 为什么优化要按"段"而不是按"感觉"（真实原因）

**来源**：git 提交记录 - `ed1c3b8`（分段耗时）

**详细解释**：
- 语音链路延迟 = STT + LLM + TTS + 链路传输，各段性质不同
- LLM 段慢 → 流式/兜底；链路段慢 → 传输优化；应用层循环 → 重试预算
- 不分段就无法选择正确的手段——"感觉慢"对应的优化往往是错的

### 2.4.2 为什么 FALLBACK 与流式要一起做（真实原因）

**来源**：git 提交记录 - `bd40e51`（同一提交）

**详细解释**：
- 流式拉低了正常路径的延迟，但流式中途失败的用户体验更差（说到一半断了）
- FALLBACK 兜底接管失败场景——流式负责"快"，兜底负责"稳"
- 两者在同一提交落地，说明是配套设计

## 2.5 业务价值原因

### 2.5.1 为什么语音延迟是产品生死线（合理推断）

**详细解释**：
- 语音面试的核心体验是"对话感"——延迟超过阈值，对话感崩塌
- 用户不会区分"AI 在思考"和"系统卡死"——长延迟一律解读为产品故障
- 延迟优化不是锦上添花，是语音产品的生存条件

### 2.5.2 为什么这套方法论可复用（合理推断）

**详细解释**：
- "实测 → 剖分 → 优化"适用于任何性能问题：先观测、再归因、后动手
- "用户行为定义 SLA"适用于任何体验优化：技术指标锚定业务后果
- "重试预算"适用于任何可靠性设计：成功率与延迟的平衡

## 3. 总结

### 3.1 核心原因总结

1. **150 分钟事故是转折点**（真实）：数量级异常暴露了无观测的致命盲区
2. **观测一天兑现价值**（真实）：08-05 上线，08-06 定位事故
3. **流式是语音延迟根治**（真实）：首字节延迟数量级改善
4. **断开时长是 SLA 来源**（真实）：优化目标锚定用户流失

### 3.2 技术原因总结

1. **单一 prompt 源**（真实）：消灭多处维护的不同步成本
2. **面经透传**（真实）：减少 LLM 加工环节直接降延迟
3. **重试预算**（真实）：无约束重试是耗时炸弹
4. **流式 + FALLBACK 配套**（真实）：快与稳的组合

### 3.3 业务价值总结

1. **数量级事故根治**：150 分钟级异常不再可能
2. **对话感保障**：首字节进入自然对话区间
3. **SLA 有据**：来自真实用户行为数据

# 第一部分：简略分析（原文档保留）

"实测驱动"的耗时优化方法论，直接起因是 **08-06 的 `08bcac0` 提交——"优化语音输出150分钟的问题"**。一个语音输出链路竟然出现 150 分钟级别的异常耗时，说明此前系统**根本没有耗时观测**，问题只能靠用户反馈暴露。这次事故与 08-05 刚建成的耗时统计体系（06 号文档）碰撞，催生了"先实测、再剖分、后优化"的方法论。

- 这正是"从感觉慢到实测"的核心：把主观的"慢"转化为可量化的"断开率 × 断开时长"

## 1.3 为什么必须是"实测驱动"而不是"经验驱动"？

### 经验驱动的失败已被证明

150 分钟这种事故，靠"经验猜"永远猜不到：
- 经验会说"LLM 调用慢，换个快模型"——但真因是 JSON 不合规触发的重试叠加
- 经验会说"网络慢，加缓存"——但真因在应用层的循环逻辑
- **只有分段实测数据能指出真正的瓶颈**

### 实测驱动方法论的三步

| 步骤 | 做什么 | 证据支撑 |
|:---|:---|:---|
| **1. 实测** | 分段耗时埋点，量化现状 | `ed1c3b8`（LLM/工具耗时） |
| **2. 剖分** | 按段归因：LLM 侧 / 工具侧 / 链路侧 | `08bcac0`（定位到 JSON 重试） |
| **3. 优化** | 针对性方案：流式 / 兜底 / 重试约束 | `bd40e51` `874b360` `7a9a540` |

### 用户侧指标闭环

`83f0849`（断开时长）+ `c201588`（08-02 "语音埋点上报增加日志"）构成用户侧闭环：
- 技术侧：分段耗时告诉你"系统慢在哪"
- 用户侧：断开时长告诉你"慢到什么程度用户会走"
- 两者结合才能定出**有业务意义的 SLA**，而不是拍脑袋的"3 秒内"

## 1.4 淘汰方案对比

**方案 A：直接换更快的模型**
- 团队确实有模型切换（`874b360` 兜底 v4 pro），但那是**可用性兜底**，不是延迟优化的主手段
- 换模型会牺牲质量（面试追问的深度），且 150 分钟问题换什么模型都解决不了

**方案 B：凭感觉逐个环节优化**
- 被 150 分钟事故证伪——没有观测时，团队甚至不知道存在这个问题
- 无实测的优化是"在黑暗中开枪"，可能优化了不慢的环节、忽略了真正的瓶颈

**方案 C：无限制重试保成功率**
- `08bcac0` 证明重试叠加会造成耗时爆炸；`7a9a540` 的"增加重试机制"必然是**有次数/退避约束的重试**
- 重试策略必须与超时预算联动：重试次数 × 单次超时 ≤ 用户可接受的断开阈值

## 1.5 反事实推理：如果不走实测驱动？

1. **150 分钟级事故会反复发生**：没有分段耗时，同类问题（重试叠加、死等）无法被提前发现
2. **优化资源错配**：凭感觉优化会把人力花在"感觉慢"但实际不慢的环节
3. **SLA 无依据**：没有断开时长数据，无法回答"优化到什么程度算够"

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 为什么"150 分钟"是方法论的转折点（真实原因）

**来源**：git 提交记录 - `08bcac0`

**提交信息原文**：
```
08bcac0 | 2026-08-06 | yitong | 优化语音输出150分钟的问题；解决模型未遵循json的问题
```

**详细解释**：
- "150分钟"写进提交标题——数量级异常（正常秒级），不是普通性能问题
- 与"模型未遵循json"同提交——两者强相关：JSON 不合规 → 解析失败 → 触发重试 → 无约束重试叠加 → 耗时爆炸
- 这类事故没有观测时完全不可见：用户只感知"语音卡死"，开发者无法定位环节

**业务场景**：
```
用户开始语音面试 → 某题回答后 AI 迟迟不响应
实际发生：模型输出 JSON 不合规 → 解析失败 → 重试
         重试仍不合规 → 再重试 → 循环累积
用户感知：语音"卡死"，最终放弃
若无观测：开发者只知道"用户说卡"，不知道是 JSON 重试循环
有观测：分段耗时显示同一 LLM 调用反复出现 → 立即定位重试循环
```

### 2.1.2 为什么观测是优化的入场券（真实原因）

**来源**：git 提交时序 - `ed1c3b8`（08-05）→ `08bcac0`（08-06）

**提交信息原文**：
```
ed1c3b8 | 2026-08-05 | 司棋 | feat: 每次请求结束时打印 LLM/工具耗时与 Token 汇总
08bcac0 | 2026-08-06 | yitong | 优化语音输出150分钟的问题……
```

**详细解释**：
- 08-05 分段耗时上线，08-06 即定位 150 分钟事故——**一天兑现观测价值**
- 分段（LLM 耗时 vs 工具耗时）是归因的关键：不分段只知道"总耗时异常"，分段后才知道"异常在哪个环节"
- 没有观测的优化是盲人摸象——这是方法论的第一原则

### 2.1.3 为什么流式是语音场景的根治手段（真实原因）

**来源**：git 提交记录 - `bd40e51`

**提交信息原文**：
```
bd40e51 | 2026-07-23 | yitong | voice: 单一 prompt 源 + 流式 LLM + FALLBACK 兜底 + 面经正文透传
```

**详细解释**：
- 语音场景的用户感知延迟 = 首字节延迟（听见 AI 第一个字的时间），不是总延迟
- 非流式：等完整回答生成（3-5s）+ TTS（2s）= 用户等 5-7s
- 流式：首 token（~0.5s）就开始合成播放 → 首字节 <1s
- 这是延迟数量级的改善，任何参数调优都做不到

**延迟对比**：
```
非流式：
  LLM 完整生成 3-5s → TTS 完整合成 2s → 播放
  用户首字节等待：5-7s（面试感崩塌区间）

流式：
  LLM 首 token ~0.5s → 短句即合成 → 播放
  用户首字节等待：<1s（自然对话区间）
```

## 2.2 技术实现原因

### 2.2.1 为什么要"单一 prompt 源"（真实原因）

**来源**：git 提交记录 - `bd40e51`、`0ad8011`

**提交信息原文**：
```
bd40e51 | 2026-07-23 | yitong | voice: 单一 prompt 源 + ……
0ad8011 | 2026-07-28 | yitong | 追问、反馈、点评话术要求同步至语音prompt
```

**详细解释**：
- 07-28 的"同步至语音prompt"提交反证了痛点：话术规则在文字版和语音版 prompt 之间不同步
- 多处 prompt 维护 = 行为不一致 + 双倍调试成本
- 单一 prompt 源从根上消灭"忘记同步"，也减少了延迟调试的重复工作

### 2.2.2 为什么要"面经正文透传"（真实原因 + 合理推断）

**来源**：git 提交记录 - `bd40e51`

**详细解释**：
- "透传"意味着面经正文不经过 LLM 加工，直接传递给下游
- 每减少一次 LLM 加工 = 减少一段 LLM 延迟
- 延迟优化的朴素原则：**能不过 LLM 的环节就不过 LLM**

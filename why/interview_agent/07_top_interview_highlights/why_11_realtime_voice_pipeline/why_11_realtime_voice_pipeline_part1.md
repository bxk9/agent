# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

语音链路的每个核心设计决策——**流式 LLM、单一 prompt 源、每次只出一题、点评后置、默认深度追问**——都能在 git 中找到明确的触发点。这条链路从 06-09 首建（`3682da6`）到 08-10 策略定型（`7607626`），历经 60+ 天、三人协作的持续打磨，是项目中演进密度最高的模块。

## 1.2 逐决策的真实成因

### 决策 1：为什么用流式 LLM？（07-23）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-23 | `bd40e51` | voice: 单一 prompt 源 + **流式 LLM** + FALLBACK 兜底 + 面经正文透传 |

- 流式改造与"单一 prompt 源""FALLBACK 兜底"在同一次提交完成——说明这是一次**整体架构升级**，而非零散优化
- 触发点：非流式方案下，用户答完题后要等 LLM 生成完整回应才能听到声音，等待感破坏"面试"的临场感。流式让首字节延迟从"完整生成时长"降为"首 token 时长"
- "面经正文透传"同步落地——减少一次 LLM 加工环节，直接降低延迟（与 07 号文档的耗时方法论一致）

### 决策 2：为什么"单一 prompt 源"？（07-23 → 07-28）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-28 | `0ad8011` / `a22fd4f` | 追问、反馈、点评话术要求**同步至语音prompt** |
| 07-28 | `4d34871` | **话术同步** |

- 07-28 一天内三条"同步"提交直接证明了痛点：**话术规则在文字版和语音版 prompt 之间不同步**——文字侧改了追问规则，语音侧忘了同步，导致两个入口行为不一致
- `bd40e51`（07-23）的"单一 prompt 源"就是对这个问题的架构级回答：**只维护一份 prompt，文字/语音共用**，从根上消灭"忘记同步"
- 多份 prompt 的维护成本随规则数量线性增长，而面试话术规则（追问/点评/反馈/结束语）恰恰是高频迭代的

### 决策 3：为什么"每次只出一题"？（07-31 → 08-05）

| 日期 | Commit | 作者 | 提交信息 |
|:---:|:---|:---:|:---|
| 07-31 | `a490baa` / `3341d7b` | yitong | **每次只出一题**，点评话术约束 |
| 07-31 | `2d0aecc` / `94a0242` | yitong | 仅改变配置不增加题号 |
| 08-05 | `25c2b95` | yitong | 强化语音内部不能点评，**文字逐题出** |
| 08-05 | `6750181` | 陈妮 | 添加**出题数量槽位**，约束开场白及延伸不计入数量 |

- "每次只出一题"在 07-31 落地后，08-05 还要"强化"——说明 LLM 有强烈的"一口气出多题"倾向，需要反复约束
- 为什么必须一题一题出：
  1. **语音场景无法回看**：文字聊天里用户可以上翻"第 2 题是什么"，语音里一次报 3 题，用户只会记住最后一题
  2. **追问依赖上一题的回答**：批量出题意味着放弃追问（08-10 `7607626` 最终把默认策略定为"深度追问"，与批量出题根本冲突）
  3. **题号管理**：`2d0aecc`（仅改变配置不增加题号）和 `422609b`（07-28 "取消输出题号，避免跟主agent的题号冲突"）说明多题并发会导致题号混乱
- 陈妮侧用"**出题数量槽位**"（`6750181`）配合——把"出几题"从 prompt 约束升级为结构化参数，且明确"开场白及延伸不计入数量"——说明"什么算一道题"也曾是歧义点

### 决策 4：为什么"点评后置到复盘"？（07-30）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-30 | `ff5f834` / `b5c9bd1` | 1. 语音面试点评策略调整：**从不提供反馈改为面试结束后通过复盘完成点评，点评能力不缺失，只是时机不同** 2. 路由规则加固……11. 语音链接：每次下发语音入口必须重新输出占位符……12. 面试结束不直接给总结…… |

**这条提交信息本身就是一份完整的决策文档**：

- "点评能力不缺失，只是时机不同"——这是明确的产品决策表述。为什么后置？
  1. **语音里听点评体验极差**：一段 300 字的点评用 TTS 念出来要 1 分钟以上，用户只能干听，无法跳读

- 08-05 `25c2b95` 再次"强化语音内部不能点评"——证明 LLM 的点评冲动需要持续压制，这是与"每次只出一题"并列的两大行为约束

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 为什么流式是语音的必选项（真实原因）

**来源**：git 提交记录 - `bd40e51`

**提交信息原文**：
```
bd40e51 | 2026-07-23 | yitong | voice: 单一 prompt 源 + 流式 LLM + FALLBACK 兜底 + 面经正文透传
```

**详细解释**：
- 非流式链路延迟 6-8s（STT 1s + LLM 3-5s + TTS 2s）——远超对话容忍阈值
- 流式把首字节延迟降为"首 token 时长 + 短句合成"（~600-900ms）
- 用户感知延迟 = 首字节延迟，不是总延迟——流式直接优化用户感知
- 四个动作同一提交落地，说明是配套的整体架构升级

**延迟对比**：
```
非流式：
  用户答完 → 等 LLM 完整生成（3-5s）→ 等 TTS 完整合成（2s）→ 播放
  首字节：6-8s（面试感崩塌）

全流式：
  用户答完 → LLM 首 token（~0.5s）→ 短句即合成播放
  首字节：<1s（自然对话）
```

### 2.1.2 为什么单一 prompt 源（真实原因）

**来源**：git 提交记录 - `0ad8011`、`4d34871`

**提交信息原文**：
```
0ad8011 | 2026-07-28 | yitong | 追问、反馈、点评话术要求同步至语音prompt
4d34871 | 2026-07-28 | yitong | 话术同步
```

**详细解释**：
- 一天内三条"同步"提交反证了痛点：文字版和语音版 prompt 各自维护，规则不同步
- 文字侧改了追问规则，语音侧忘了同步 → 两个入口行为不一致 → 用户困惑
- 单一 prompt 源从根上消灭"忘记同步"——只有一份，不存在同步问题
- 话术规则是高频迭代的（追问/点评/反馈/结束语），多份维护成本线性增长

### 2.1.3 为什么点评后置（真实原因）

**来源**：git 提交记录 - `ff5f834`

**提交信息原文**：
```
ff5f834 | 2026-07-30 | yitong | 1. 语音面试点评策略调整：从不提供反馈改为面试结束后
通过复盘完成点评，点评能力不缺失，只是时机不同 2. 路由规则加固……
11. 语音链接：每次下发语音入口必须重新输出占位符，禁止引用历史链接
12. 面试结束不直接给总结：无论正常结束还是主动终止，都先询问用户是否需要整体点评，确认后才输出评估
```

**详细解释**：
- 提交原文直接给出决策表述："点评能力不缺失，只是时机不同"
- 三个支撑理由：语音听点评体验差（无法跳读）、边面边评破坏节奏、选择权应给用户
- 第 12 条"先询问确认后才输出"——把灌输变为选择，尊重用户

处理：记录漏题原因 → 带完整题目清单重试 → 再校验
兜底：重试仍失败 → 报告标注未完成部分，不静默交付
```

**Case 3：数字冲突**
```
场景：转写中同一数字出现两种形态（"一千"/"1000"）
处理：数字铁律 → 采用原文首次出现形态，不做换算
```

## 6. 技术亮点总结

### 6.1 创新性

1. **铁律按失败模式固化**：每条铁律对应一类真实事故，拒绝笼统约束
2. **prompt 自律 + 代码他律**：概率层与确定层的分工协作
3. **拦截带归因**："并记录原因"让拦截成为改进的输入而非终点

### 6.2 技术深度

1. **ASR 文本治理**：同音变体容错边界、数字溯源
2. **交付闸门设计**：校验前置、通过与否留痕、重试策略
3. **链路减法**：移除危险环节而非无限打补丁

### 6.3 业务价值

1. **交付可信**：复盘报告零漏题、坏报告零落盘
2. **信任保护**：事实围栏杜绝"AI 没听我说话"的观感
3. **可审计**：校验日志 + 拦截原因全留痕

### 6.4 方法论抽象与迁移（原文档保留部分）

**抽象出的通用方法论——"铁律 + 硬闸"双保险**：

1. **铁律来自事故**：不要凭空设计 prompt 规则，从真实失败案例逐条提炼
2. **自律降概率、他律保确定**：LLM 的自律永远需要代码的他律兜底
3. **拦截必须归因**：只拦截不归因，问题会永远以同样方式出现
4. **交付链路做减法**：每个经手环节都是潜在故障点，能删就删

**可迁移场景**：

| 场景 | 迁移点 |
|:---|:---|
| AI 客服工单总结 | 逐条覆盖 + 事实围栏 |
| 会议纪要生成 | 全覆盖校验 + 数字溯源 |
| 语音助手文本产出 | ASR 同音变体治理 |
| 任何 LLM 交付物 | 交付前硬闸 + 留痕 |

**反例警示**：
- **反例 1**：只写"千万不要漏题"的 prompt → 概率性约束，无法归零
- **反例 2**：拦截不记录原因 → 漏题成因不明，无法分类治理
- **反例 3**：链接域名替换这类"顺手加工"环节 → 改坏正确数据（`92bc8e6` 移除）

## 7. 面试问答准备

### Q1: 为什么是五条铁律，怎么提炼出来的？

**A**：
1. 每条铁律对应一类真实事故：漏题（`05399d4`）、坏报告落盘（`023a47b`）、数字漂移、无依据点评、同音错字
2. 提炼方法：收集交付事故 → 按根因聚类 → 每类固化为一条可校验的规则
3. 不做笼统约束的原因：笼统规则无法校验，铁律必须能对应到具体校验动作

### Q2: prompt 铁律和代码校验什么关系？

**A**：
1. prompt 铁律降低违规概率——多数请求一次通过，控制重试成本
2. 代码校验保证最终确定性——漏网的必然被拦截
3. 两者缺一不可：只有 prompt 无法归零；只有代码则重试成本爆炸

### Q3: ASR 同音错字怎么处理？

**A**：
1. 识别同音变体，按正确术语呈现（"二插树" → "二叉树"）
2. 但设置容错边界：不臆造原文没有的内容，不过度纠错
3. 关键数字不做换算，采用原文形态（数字铁律）

### Q4: 漏题拦截后怎么办？

**A**：
1. 记录漏题原因（上下文过长/题号格式/转写缺失）——`05399d4` 明确要求
2. 带完整题目清单重试
3. 重试仍失败则显式标注未完成部分，绝不静默交付

### Q5: 这套方案的迁移价值？

**A**：
1. 任何"LLM 生成交付物"的场景：会议纪要、工单总结、报告生成
2. 迁移要点：失败模式提炼铁律 + 交付前代码硬闸 + 拦截归因
3. 核心认知：LLM 自律不可靠，交付物必须有代码他律

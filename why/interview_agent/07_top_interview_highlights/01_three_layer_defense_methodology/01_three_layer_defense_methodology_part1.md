# 三层防御方法论：LLM 结构化输出的 Schema × 正则 × 归一化 - 面试亮点

> **核心价值**：针对 LLM 提取简历结构化数据时"字段丢失 / 格式错乱 / 键名漂移"三类顽疾，设计并落地了 Schema × 正则 × 归一化的三层防御体系（4000+ 行归一化代码 + 双入口全覆盖 + 降级兜底），将字段类 bug 从"每周多发"收敛为体系化拦截，是 LLM 输出可信化的完整工程实践。

## 1. 核心概览（原文档保留部分）

### 1.1 一句话摘要

面对 LLM 提取简历结构化数据时**字段丢失、格式错乱、键名漂移**三类顽疾，我把失败模式按正交性拆成三层，用 **Schema 补全 × 正则兜底 × 归一化清洗**分层拦截，并坚持"双入口全覆盖 + 降级不拒绝"，让 LLM 的概率性输出变成渲染层可信任的确定性数据。

### 1.2 面试价值卡片

| 面向问题 | 我能讲什么 |
|:---|:---|

### 1.3 方案演进与关键决策

**演进时间线**（git 证据）：

```
阶段 1（08-02 ~ 08-04）：单点打补丁期
  3 天 4 起字段类 bug（035c00b/aa29906/ba6d575...），修一个冒一个
      ↓ 认识到：bug 分布在三类不同失败层，单层修复无效
阶段 2（08-04）：体系化时刻
  555285d "根因修复路径：LLM Schema → 正则兜底精度 → 归一化清洗，三层防御对齐"
      ↓ 三层防御正式命名并落地，双入口全覆盖
阶段 3（08-05 ~ 08-11）：策略打磨期
  fb29509 拒绝渲染 → 降级全量渲染
  9b1066c scope 检测迁移到工具层（入口失效教训）
  b636f11 extra_sections 提取增强
```

**关键决策 1：按失败模式正交分层，而不是按处理手段分层**

三层各挡一类失败，交集为空：

| 层 | 挡什么 | 被哪类 bug 证明必要 |
|:---|:---|:---|
| Schema 层 | 字段缺失、语义归类错 | `035c00b` `aa29906` `ba6d575` |
| 正则层 | 格式切分错（时间/电话/链接） | `08d7027` `13fff83` |
| 归一化层 | 键名漂移、嵌套形态不一 | `7291bf3` `2e782b2` |

**关键决策 2：双入口全覆盖**

`customize_for_sidebar`（侧边栏预览）和 `_normalize_jinja2_data`（模板渲染）两个入口均调用归一化——漏一个入口就会出现"预览正常、导出丢字段"的薛定谔 bug。

**关键决策 3：降级而非拒绝**

三层都拦不住时，不拒绝渲染，而是分级降级（补默认值 → 跳过字段 → 全量渲染）——简历是核心交付物，"宁可粗糙不可没有"。

**淘汰的方案**：

| 淘汰方案 | 淘汰原因 |
|:---|:---|
| **Prompt-only 约束** | `7291bf3` 实证：prompt 明确要求键名，LLM 仍自创 self_assessment |
| **正则-only 后处理** | `aa29906` 实证：字段根本没输出时，正则无米下锅 |
| **function calling 强约束** | 简历字段高度可变（论文/竞赛因人而异），刚性 schema 会拒掉合法内容；团队共识见 `4cbdbb4`（不稳定能力宁可砍掉） |

## 2. 项目背景与问题定义

### 2.1 业务场景

interview_agent 的 AI 简历生成链路：

```
用户上传简历原稿（PDF/DOCX/图片）
    ↓
文档解析 → 自由文本
    ↓
LLM 结构化提取 → JSON（15+ 字段：basic/education/work/project/extra_sections...）
    ↓
侧边栏实时预览（customize_for_sidebar 入口）
    ↓
Jinja 模板渲染 → HTML/DOCX/PDF（_normalize_jinja2_data 入口）
```

**输出特征**：
- 字段数量多：15+ 主字段 + extra_sections 弱字段（08-10 一次性新增 8 个学术 CV 字段，commit `b2384eb`）
- 模板数量多：15+ 套简历模板
- 输出格式多：HTML / DOCX / PDF 三种

### 2.2 失败模式分析

**体系化之前（08-02 至 08-04）的真实 bug 清单**（git 证据）：

| 日期 | Commit | bug 描述 | 失败层 |
|:---:|:---|:---|:---|
| 08-02 | `035c00b` | 简历个人信息字段丢失/映射错误 | Schema 层 |
| 08-02 | `aa29906` | 项目经历技术栈字段丢失和排版分散 | Schema 层 |
| 08-05 | `ba6d575` | 校园活动和项目经历混淆 | Schema 层 |
| 08-06 | `08d7027` | 小时匹配不分离（时间正则切错） | 正则层 |
| 08-05 | `2e782b2` | 个人信息英文字段错误 | 归一化层 |
| 08-07 | `7291bf3` | LLM 自创 self_assessment 英文键名导致补充信息模块异常 | 归一化层 |

**关键洞察**：
- 这些 bug 分布在**三个互不重叠的失败层**
- 单层修复只能挡住一类，所以单点 fix 修了一周还在冒新 bug
- **浪费**：每个新模板、新字段都要重新踩一遍同样的坑

**三类失败模式的典型样本**：

```
失败模式 1：字段缺失（Schema 层）
LLM 输出: {"basic": {...}, "education": [...]}
缺失:     work_experience 整个字段没输出
后果:     模板渲染时静默跳过 → 用户工作经历凭空消失

失败模式 2：格式错乱（正则层）
LLM 输出: "2020.03-2023.06 至今"（时间区间粘连）
期望:     start="2020.03", end="至今"
后果:     时间字段渲染成一坨，排版崩坏

失败模式 3：键名漂移（归一化层）
LLM 输出: {"self_assessment": "..."}（自创英文键名）
期望:     {"extra_sections": {"自我评价": "..."}}
后果:     补充信息模块整体异常（commit 7291bf3 的真实事故）
```

### 2.3 优化目标

**核心问题**：如何让 LLM 的概率性输出变成渲染层可信任的确定性数据？

**量化目标**：
- 字段丢失类 bug 收敛为 0（体系化拦截）
- 异常数据不拒绝交付，降级全量渲染（commit `fb29509`）
- 所有渲染入口行为一致（双入口覆盖）

## 3. 技术方案设计

### 3.1 核心思路

**三层防御体系**（命名直接来自 commit `555285d` 提交原文："根因修复路径：LLM Schema → 正则兜底精度 → 归一化清洗，三层防御对齐"）：

```
LLM 原始输出
    ↓
【第 1 层：Schema 防御】字段补全 + 语义归类 + 白名单校验
    ↓
【第 2 层：正则防御】时间/电话/链接的格式切分与兜底
    ↓
【第 3 层：归一化防御】键名翻译 + 嵌套容错 + 去重 + 清洗
    ↓
渲染层（15+ 模板 × 3 格式）
```

**关键挑战**：
1. 三层各挡什么？边界如何划分？
2. 系统有多个渲染入口，如何保证防御不遗漏？
3. 三层都拦不住的异常数据如何处置？

### 3.2 三层职责规则表

**设计原则**：三层的失败模式交集为空——没有任何一层能覆盖另外两层的失败模式

| 层 | 输入异常 | 处置规则 | 输出保证 |
|:---|:---|:---|:---|
| **Schema 层** | 字段缺失 | 补默认值/空容器 | 所有标准字段存在 |
| **Schema 层** | 归类错误（校园/工作混淆） | 关键词 + 毕业年份 + 公司白名单判定 | 归类正确 |
| **正则层** | 时间区间粘连 | 分隔符检测后切分 | start/end 分离 |
| **正则层** | 时长误匹配 | 小时/时长独立正则，不与日期共用 | 不误切 |
| **归一化层** | 自创键名 | 键名翻译表，未知键保留进 extra_sections | 内容不丢 |
| **归一化层** | 嵌套形态不一 | 预归一化展平 | 单一标准形态 |
| **归一化层** | 跨字段重复 | 时间重叠判定 + bullet 合并 | 不粗暴丢弃 |

124a5b1 | 2026-08-05 | 司棋 | fix: token 汇总合并为单条日志 + 修复 token 为 0 的问题
```

**详细解释**：
- 一次请求有多次 LLM 调用 + 多次工具调用，每次输出一条日志 → 高并发下多请求日志交错
- 交错的日志无法归属，失去汇总意义
- 合并为单条：请求结束时一次性输出总汇总，带 trace_id，一行看清成本

**场景示例**：
```
分散输出（旧）：
  [req-A] llm_call tokens=1200
  [req-B] llm_call tokens=800      ← 交错
  [req-A] tool_call tokens=300
  [req-B] llm_call tokens=500
  → 要人工拼凑每个请求的总量

单条汇总（新）：
  request_summary trace_id=req-A total_tokens=1500
  request_summary trace_id=req-B total_tokens=1300
  → 一行一请求，清晰归属
```

### 2.2.2 为什么 FIFO 字典要限容（合理推断）

**详细解释**：
- 请求异常中断时，flush（请求结束清理）不会被调用 → 条目残留
- 无限增长的字典会内存泄漏
- FIFO（OrderedDict + popitem(last=False)）限制最大条目数，最旧条目先挤出
- 本质：用有界缓存换内存安全——残留条目最终都会被挤出

### 2.2.3 为什么 ctx_log 要"内部防崩溃"（真实原因）

**来源**：git 提交记录 - `f3e2204`

**提交信息原文**：
```
f3e2204 | 2026-08-05 | 司棋 | feat: 所有直连 VFS 的 HTTP 调用加请求日志，ctx_log 内部防崩溃
```

**详细解释**：
- 日志组件如果抛异常，会把业务请求一起拖垮——本末倒置
- "内部防崩溃"：ctx_log 任何内部异常都静默降级，绝不上抛
- 这是可观测系统的第一原则：**观测组件自身的故障不能影响被观测对象**

## 2.3 性能与质量原因

### 2.3.1 为什么可观测要"全链路"而不是各模块自建（真实原因）

**来源**：git 提交记录 - `01dfc2c`

**提交信息原文**：
```
01dfc2c | 2026-07-29 | 司棋 | feat(logging): 为 LLM/VFS/Skill 主链路补全 ctx_log 日志
```

**详细解释**：
- 一次请求的 token 消耗跨越主 Agent LLM → 工具 → 子 Agent → VFS
- 各模块自建统计：口径不一、汇总对不上、断点不可见
- 统一 ctx_log：同一套字段规范（trace_id/tenant/user）、同一个聚合出口
- "补全主链路"的措辞说明这是有意识的体系化建设，不是零散加日志

### 2.3.2 为什么日志覆盖面要三次扩大（真实原因）

**来源**：git 提交记录 - `b215510` → `c669057` → `f3e2204`

**提交信息原文**：
```
b215510 | 2026-08-04 | 司棋 | feat(vfs): VFS 调用加请求日志……
c669057 | 2026-08-04 | 司棋 | feat(vfs): 所有 VFS 接口加请求日志……
f3e2204 | 2026-08-05 | 司棋 | feat: 所有直连 VFS 的 HTTP 调用加请求日志……
```

**详细解释**：
- 覆盖面递进："VFS 调用" → "所有 VFS 接口" → "所有直连 VFS 的 HTTP 调用"
- 说明第一次加日志时**低估了调用入口数量**——除了 VFSClient，还有绕过客户端直连 HTTP 的调用点
- 可观测的覆盖面必须穷举，漏一个入口就有一段链路是黑洞

## 2.4 工程实现原因

### 2.4.1 为什么线程前缀丢失会反复出现（真实原因）

**来源**：git 提交记录 - `41d47cf`

**提交信息原文**：
```
41d47cf | 2026-08-13 | 司棋 | fix: BlueclawChat 日志在 run_in_executor 线程中丢失 session/user/task 前缀
```

**详细解释**：
- 08-13 的这条修复与 08-05 的 `95bf297`（contextvar 跨线程失效）是**同一类根因**
- 线程切换丢上下文是 Python 混合并发模型的结构性问题，会在不同模块反复出现
- 应对：不是修一次就完，而是建立规范——凡 run_in_executor 必须显式携带上下文参数

### 2.4.2 为什么埋点要"日志留痕"（真实原因）

**来源**：git 提交记录 - `c201588`

**提交信息原文**：
```
c201588 | 2026-08-02 | yitong | 语音埋点上报增加日志
```

**详细解释**：
- 埋点上报本身也可能失败（网络、格式、服务不可用）
- 埋点不加日志，上报失败时无从排查——"数据没了"成为悬案
- 可观测系统自己也要可观测

## 3. 总结

### 3.1 核心原因总结

1. **五连修暴露异步断点**（真实）：usage-tokens 问题的顽固性倒逼体系化方案
2. **contextvar 跨线程失效**（真实）：提交原文点名，FIFO 字典是最终解
3. **三元组链路追踪**（真实）：trace_id/tenant/user 是高并发归因的最小完备集
4. **观测先行**（真实）：上线一天即定位重大事故

### 3.2 技术原因总结

1. **单条汇总日志**（真实）：高并发下分散日志不可读
2. **FIFO 限容**（合理推断）：异常中断的残留条目需要自动清理
3. **ctx_log 防崩溃**（真实）：观测组件不能成为故障源
4. **覆盖面穷举**（真实）：三次扩大日志覆盖面，漏一个入口就是黑洞

### 3.3 业务价值总结

1. **成本可见**：请求级 token 汇总
2. **优化有据**：150 分钟事故一天定位
3. **团队共识**：三开发者同日推进，观测成为基础设施

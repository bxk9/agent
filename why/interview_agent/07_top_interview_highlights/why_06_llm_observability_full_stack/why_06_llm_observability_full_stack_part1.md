## 1.1 结论先行

全链路可观测体系的建立，直接动因是 **07-30 当天 yitong 对 usage-tokens bug 的五连修**（同一主题 5 次提交）——token 统计这个"看起来简单"的功能，实际踩穿了异步上下文、跨线程传递、埋点口径三个深坑。而司棋侧的 ctx_log 基础设施建设（07-29 起）与 VFS 请求日志（08-04 起）则补上了"链路追踪"的另一半。**两条线在 08-05 汇合**，形成完整的可观测体系。

## 1.3 为什么"可观测"必须全链路而不是单点？

### 单点统计的失败已被证明

yitong 的五连修（07-30）和司棋的三连修（08-05）都发生在"单点统计"阶段——只统计自己模块内的 token。但真实系统的 token 消耗跨越：

```
主 Agent LLM 调用 → 工具调用 → 子 Agent（doc_agent）LLM 调用 → VFS 读写
```

单点统计的问题：
1. **口径不一**：各模块各自统计，汇总时对不上
2. **断点不可见**：contextvar 在某个线程切换处丢失，单点视角看不到"在哪丢的"
3. **无法归因**：用户反馈"这次请求好贵"，无法定位是哪个环节吃的 token

### 全链路的三个支柱

| 支柱 | 解决什么 | 对应提交 |
|:---|:---|:---|
| **trace_id 贯穿** | 一次请求的所有日志可聚合 | `b215510` `c669057` |
| **token/耗时统一汇总** | 请求级成本可见 | `ed1c3b8` `124a5b1` |
| **上下文安全传递** | 跨线程/异步不丢数据 | `95bf297`（FIFO 字典） |

## 1.4 淘汰方案对比

**方案 A：坚持 contextvar**
- 已被 `95bf297` 明确放弃（"避免 contextvar 跨线程失效"）
- contextvar 在纯 asyncio 内可用，但本项目大量使用 run_in_executor（`41d47cf` 佐证）和线程池，断点太多

**方案 B：每个调用点显式传参**
- 要求所有函数签名带统计参数——侵入性太大，且漏一个调用点就断链
- 模块级 FIFO 字典（最终方案）以 key（request_id）显式存取，兼顾可控性与低侵入

**方案 C：用 APM 平台（外部探针）**
- 外部 APM 拿不到 LLM 特有的语义数据（token 数、模型名、prompt 长度），且部署环境（内网 IDC，见 `304801e` "适配idc"）未必支持
- 自建 ctx_log 可以精确控制"记什么、怎么聚合、何时输出"

## 1.5 反事实推理：如果不建全链路可观测？

1. **成本失控**：不知道每次请求的 token 消耗，无法做成本预算与优化（07 号文档的耗时优化就无从谈起）
2. **bug 无法归因**：usage 为 0、日志丢前缀这类问题会永远"偶现"
3. **优化无方向**：`83b3da9` 证明"统计先行"直接驱动了效果优化——没有数据，优化就是盲人摸象

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 为什么 usage-tokens 要一天修六次（真实原因）

**来源**：git 提交记录 - 07-30 六连提交

**提交信息原文**：
```
a7e4583 | 2026-07-30 | yitong | fix usage-tokens bug
c711889 | 2026-07-30 | yitong | fix usage-tokens bug
3df567d | 2026-07-30 | yitong | fix usage-tokens bug
877a30c | 2026-07-30 | yitong | fix usage-tokens bug
2f55a8a | 2026-07-30 | yitong | fix usage-tokens bug
16a4dd7 | 2026-07-30 | yitong | fix usage bug
```

**详细解释**：
- 同一天、同一主题、6 次提交——整个仓库最密集的修复序列
- "修一个、冒一个"的模式指向**异步上下文传递断点**：每修一处，暴露下一处
- token 统计的验证必须等真实 LLM 调用完成，验证周期长 → 只能串行小步修

**业务场景**：
```
修复第 1 版：主协程内统计正常 → 上线
发现：工具调用后的 token 没统计上 → 断点在 executor 切换
修复第 2 版：executor 处补传递 → 上线
发现：子 Agent 回调的 token 又丢了 → 断点在回调嵌套
……反复 6 次才把所有断点清完
```

### 2.1.2 为什么最终放弃 contextvar（真实原因）

**来源**：git 提交记录 - `95bf297`

**提交信息原文**：
```
95bf297 | 2026-08-05 | 司棋 | fix: token 统计改用模块级 FIFO 字典，避免 contextvar 跨线程失效
```

**详细解释**：
- 提交原文直接点名失败原因："contextvar 跨线程失效"
- 症状是"token 为 0"（`124a5b1`）——统计值在跨线程后归零
- 本项目大量使用 run_in_executor（阻塞工具调用走线程池），contextvar 断点无法穷举修复
- 最终方案：模块级 FIFO 字典，以 request_id 显式存取——绕开上下文传递问题

**技术对比**：
```
contextvar：
- 绑定 asyncio Context，协程切换自动传递
- run_in_executor 到线程池线程 → Context 不完整 → 变量丢失
- 断点数量 = 线程池调用点数量，无法穷举

显式传参：
- 每个函数签名带统计参数 → 侵入性大
- 漏一个调用点就断链

模块级 FIFO 字典（最终方案）：
- 全局字典，request_id 为键 → 任何线程都能存取
- FIFO 限容 → 异常中断的残留条目自动挤出，不泄漏
- 调用点只需两处：记录 + 请求结束 flush
```

### 2.1.3 为什么日志要带 trace_id/tenant/user 三元组（真实原因）

**来源**：git 提交记录 - `b215510`

**提交信息原文**：
```
b215510 | 2026-08-04 | 司棋 | feat(vfs): VFS 调用加请求日志，包含 url/trace_id/tenant/user/path 等参数
```

**详细解释**：
- 没有 trace_id，高并发下日志无法归属到具体请求——"这条 VFS 调用是谁的？"无法回答
- tenant/user 是多租户系统的必备维度——排查问题必须先定位"哪个租户哪个用户"
- 三元组是链路追踪的最小完备集：trace_id 定位请求、tenant 定位租户、user 定位用户

## 2.2 技术实现原因

### 2.2.1 为什么 token 汇总要合并为单条日志（真实原因）

**来源**：git 提交记录 - `124a5b1`

**提交信息原文**：
```

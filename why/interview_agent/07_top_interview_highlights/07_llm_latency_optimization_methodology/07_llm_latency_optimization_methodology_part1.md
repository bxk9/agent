## 2. 项目背景与问题定义

### 2.1 业务场景

语音面试的延迟敏感性：

```
用户答完一题 → 等待 AI 回应
  延迟 < 1s：自然对话感
  延迟 1-3s：可接受，有等待感
  延迟 > 5s：面试感崩塌，用户怀疑系统卡死
  极端：150 分钟级异常 → 用户直接流失
```

**延迟的三段构成**：

```
用户说完 → [STT 转写] → [LLM 生成] → [TTS 合成] → 用户听见
              段1           段2           段3
优化目标：压缩每段 + 流式并行化
```

### 2.2 失败模式分析

**150 分钟事故的还原**（真实，commit `08bcac0`）：

```
提交原文："优化语音输出150分钟的问题；解决模型未遵循json的问题"
两个问题在同一提交 → 高度相关：
  模型未遵循 JSON → 解析失败 → 触发重试
  重试无约束 → 叠加循环 → 耗时爆炸到 150 分钟级
正常应为秒级的链路，因重试叠加变成数量级异常
```

**关键观察**：
- 这类事故**没有观测时完全不可见**——用户只感知"语音卡死了"
- 08-05 分段耗时上线（`ed1c3b8`），08-06 即定位——观测的价值一天兑现

### 2.3 优化目标

**核心问题**：如何把"感觉慢"变成可量化、可归因、可优化的工程问题？

**量化目标**：
- 每段耗时可测量（分段埋点）
- 数量级异常可发现（150 分钟级事故分钟级定位）
- 优化效果可验证（前后对比 + 断开时长）

## 3. 技术方案设计

### 3.1 核心思路

**实测驱动三步法**：

```
第 1 步：实测——分段耗时埋点，量化现状
  LLM 耗时 / 工具耗时 / 链路耗时 分开统计（ed1c3b8）
  
第 2 步：剖分——按段归因
  哪个环节吃的耗时最多？是 LLM 慢、工具慢、还是应用层循环？
  
第 3 步：优化——针对性方案
  LLM 慢 → 流式/兜底模型
  应用层循环 → 重试预算约束
  用户侧 → 断开时长监控
```

### 3.2 优化手段矩阵

| 手段 | 针对的段 | 提交 | 原理 |
|:---|:---|:---|:---|
| **流式 LLM** | LLM 生成段 | `bd40e51` | 首字节延迟 = 首 token 时长 |
| **面经正文透传** | 加工环节 | `bd40e51` | 减少一次 LLM 加工 = 减少一段延迟 |
| **兜底模型** | LLM 可用性 | `874b360` | 主模型慢/挂时切换，保可用 |
| **重试约束** | 应用层 | `7a9a540` + `08bcac0` | 重试有预算，防叠加爆炸 |
| **断开时长埋点** | 用户侧 | `83f0849` | 度量"用户能忍多久" |

## 4. 核心实现细节

### 4.1 流式改造（`bd40e51`）

**提交原文**：`voice: 单一 prompt 源 + 流式 LLM + FALLBACK 兜底 + 面经正文透传`

```python
# 非流式（旧）：等完整回答
async def respond_old(query):
    full_response = await llm.generate(query)   # 等 3-5s
    await tts.synthesize(full_response)          # 再等 2s
    # 用户总等待：5-7s

# 流式（新）：边生成边播
async def respond_new(query):
    async for chunk in llm.stream(query):        # 首 token ~0.5s
        await tts.stream_synthesize(chunk)       # 短句即播
    # 用户首字节等待：<1s
```

**四个动作的延迟逻辑**：
```
1. 流式 LLM：首字节延迟从"完整生成"降为"首 token"
2. 单一 prompt 源：消灭文字/语音 prompt 不同步的重复调试成本
3. FALLBACK 兜底：主模型超时 → 切兜底，避免无限等待
4. 面经正文透传：减少一次 LLM 加工环节，直接降一段延迟
```

### 4.2 重试预算约束（150 分钟事故的根治）

```python
# 事故模式（08bcac0 之前）：
while not success:           # 无约束重试
    result = await llm_call()
    if parse_json(result):   # 模型未遵循 JSON → 解析失败
        success = True
    # JSON 持续不合规 → 无限循环 → 150 分钟

# 修复后：重试预算 + 根因修复
MAX_RETRIES = 2
for i in range(MAX_RETRIES + 1):
    result = await llm_call(json_enforced=True)  # 强化 JSON 约束
    if parse_json(result):
        return result
# 超过预算 → 降级处理，绝不无限循环
```

### 4.3 模型兜底（`874b360`）

```python
# 主模型慢/挂时切兜底
async def llm_with_fallback(query):
    try:
        return await call_primary_model(query, timeout=T)
    except (TimeoutError, ServiceError):
        return await call_fallback_v4_pro(query)  # 兜底 v4 pro
# 原则：模型切换是可用性兜底，不是延迟优化主手段
```

### 4.4 用户侧指标：断开时长（`83f0849`）

```python
# 统计用户断开前的等待时长
def on_user_disconnect(session):
    wait_duration = now() - session.last_ai_response_time
    report_metric("disconnect_wait_duration", wait_duration)
# 用途：
# - 技术侧：分段耗时告诉你"系统慢在哪"
# - 用户侧：断开时长告诉你"慢到什么程度用户会走"
# - 两者结合 → 定出有业务意义的 SLA
```

### 4.5 边界 case 处理

**Case 1：JSON 不合规重试**
```
场景：模型输出不符合 JSON schema
处理：最多重试 2 次（带更强约束），超预算降级
教训：08bcac0 证明无约束重试 = 耗时炸弹
```

**Case 2：主模型超时**
```
场景：主模型响应超过阈值
处理：切兜底模型（874b360），保证有响应
原则：宁可质量略降，不可无响应
```

**Case 3：流式中断**
```
场景：流式生成中途失败
处理：FALLBACK 兜底接管，已播部分不重复
```

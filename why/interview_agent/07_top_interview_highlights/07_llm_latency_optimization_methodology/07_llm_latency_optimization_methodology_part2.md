**抽象出的通用方法论——"实测驱动三问"**：

1. **慢在哪一段？**：先建分段观测，再谈优化。没有数据的优化是盲人摸象
2. **目标函数是什么？**：技术指标要锚定业务后果（断开时长 = 流失）
3. **优化会不会引入新风险？**：重试要预算、兜底要降级、流式要处理中断

**可迁移场景**：

| 场景 | 迁移点 |
|:---|:---|
| 任何 LLM 应用 | 分段耗时观测 + 重试预算 |
| 实时对话系统 | 流式架构 + 首字节 SLA |
| 高可用服务 | 模型/服务级兜底 |
| 用户体验优化 | 用行为数据定义 SLA |

**反例警示**：
- **反例 1**：无观测凭感觉优化——150 分钟事故在没观测时根本不可见
- **反例 2**：无约束重试——成功率上去了，耗时爆炸了（`08bcac0`）
- **反例 3**：拍脑袋定 SLA——"3 秒内"没有业务依据，断开时长才是真依据

## 7. 面试问答准备

### Q1: 耗时优化的第一步是什么？

**A**：
1. 建分段观测，不是直接优化——150 分钟事故证明经验猜不到瓶颈
2. 分段模型：LLM 耗时 / 工具耗时 / 链路耗时分开统计
3. 实证：观测 08-05 上线，08-06 即定位数量级事故

### Q2: 150 分钟事故的根因和修复？

**A**：
1. 根因：模型未遵循 JSON → 解析失败 → 无约束重试叠加 → 耗时爆炸
2. 修复：重试预算（最多 N 次）+ JSON 约束强化 + 超预算降级
3. 教训：重试是双刃剑，必须与超时预算联动

### Q3: 为什么流式是语音场景的根治手段？

**A**：
1. 非流式：用户等完整回答生成（3-5s）+ TTS（2s）= 5-7s
2. 流式：首 token 出来就开始合成播放，首字节 <1s
3. 用户感知延迟 = 首字节延迟，不是总延迟——流式直接优化用户感知

### Q4: 性能 SLA 怎么定？

**A**：
1. 不拍脑袋定"3 秒"——要有业务依据
2. 断开时长埋点（`83f0849`）：统计用户断开前等了多久
3. 技术侧分段耗时 + 用户侧断开时长 → 定出"优化到什么程度用户不流失"的 SLA

### Q5: 模型切换是延迟优化手段吗？

**A**：
1. 不是主手段，是可用性兜底（`874b360` 的定位）
2. 换快模型牺牲质量，且救不了应用层问题（150 分钟换什么模型都没用）
3. 延迟优化主手段：流式、减加工环节、重试预算

## 9. 总结

LLM 耗时优化是一个典型的**方法论驱动案例**，展示了：

1. **实测先行**：观测上线一天即定位数量级事故
2. **系统性治理**：流式 + 兜底 + 重试预算 + 用户侧指标的组合拳
3. **业务锚定**：SLA 来自用户行为数据而非拍脑袋

**一句话总结**：以分段耗时观测为基础、以"150 分钟"事故为转折，建立"实测 → 剖分 → 优化"的耗时治理方法论，用流式、兜底、重试预算和用户断开时长指标把语音延迟治理变成可量化工程。

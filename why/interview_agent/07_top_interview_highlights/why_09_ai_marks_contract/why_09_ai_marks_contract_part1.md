# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

契约层与模板矩阵的建立，是被三类真实事故逼出来的：① **导出内容丢失**（07-16 "简历导出内容丢失"）；② **渲染逻辑与模板耦合导致的连锁 bug**（08-07 "统一 bullet 格式化 & 修复模板渲染逻辑"）；③ **scope（修改范围）判定在错误的层失效**（08-08 两条 scope 提交）。契约层的本质是：**在 LLM 输出和 N 个模板之间建立一个稳定的、可校验的中间层**。

## 1.3 为什么必须是"契约 + 矩阵"这个架构？

### 组合爆炸的数学

- LLM 输出字段 ~15+（且持续增长，见 `b2384eb` 一次加 8 个）
- 模板 15+ 套
- 输出格式 3 种（HTML/DOCX/PDF）

无契约时，任何字段变更的影响面 = 模板数 × 格式数 = **45+ 个渲染点**。`22e8097`（统一 bullet）和 `f60a9ba`（PDF/Word 一致）就是在为这种组合爆炸还债。

### 契约层的三个作用（均有事故对应）

| 作用 | 防御的事故 | 证据 |
|:---|:---|:---|
| **字段稳定性** | 导出内容丢失 | `135c21d` |
| **格式统一性** | bullet 格式混乱、PDF/Word 不一致 | `22e8097` `f60a9ba` |
| **可校验性** | scope 判错、字段静默丢失 | `fb29509`（降级而非拒绝） |

### 淘汰方案对比

**方案 A：每个模板直接消费 LLM 输出**
- 已被证伪：`22e8097` 之前的状态就是这样，结果是 bullet 格式各模板不一致

**方案 B：在 agent_executor 层做统一处理**
- 已被 `9b1066c` 证伪："agent_executor层注入无效"——层选错了，逻辑不生效

**方案 C：单一超级模板 + 参数化样式**
- 学术 CV 与技术简历的结构差异太大（论文列表 vs 项目经历），单一模板无法覆盖，必须模板矩阵 + 共享契约

## 1.4 反事实推理：如果不建契约层？

1. **每次加字段都是全链路手术**：`b2384eb` 的 8 个学术字段将需要改 45+ 个渲染点
2. **内容丢失事故反复发生**：字段不一致继续被静默吞掉（`135c21d` 的根因未除）
3. **scope 功能无法实现**：局部修改需要精确知道"哪些字段属于哪个模块"，没有契约就没有这个映射

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 为什么契约层要解决"静默丢失"（真实原因）

**来源**：git 提交记录 - `135c21d`

**提交信息原文**：
```
135c21d | 2026-07-16 | 11099826 | fix(resume): 修复简历导出内容丢失与技能冒号显示问题
```

**详细解释**：
- "导出内容丢失"是简历产品最高级别事故——用户的简历内容凭空消失
- 根因：LLM 输出字段与模板期望字段不一致时，模板渲染**静默跳过**——不报错、不告警、内容就没了
- 契约层的价值：字段不一致在契约层被显式处理（补全/翻译/降级），而不是在渲染层被静默吞掉

**业务场景**：
```
无契约：
  LLM 输出 {"skills": [...]}
  模板期望 {"skill_list": [...]}
  → 渲染时找不到 skill_list → 静默跳过 → 用户技能栏空白
  → 无任何报错，排查极其困难

有契约：
  契约层发现 skills → 翻译为 skill_list（或补全）
  → 渲染层永远拿到标准字段
  → 即使异常也走降级路径，不静默丢失
```

### 2.1.2 为什么要统一渲染逻辑到共享层（真实原因）

**来源**：git 提交记录 - `22e8097`、`f60a9ba`

**提交信息原文**：
```
22e8097 | 2026-08-07 | 11099826 | fix: 统一简历bullet点格式化 & 修复模板渲染逻辑
f60a9ba | 2026-08-07 | 11099826 | jpdf 和 word 渲染的内容保持一致
```

**详细解释**：
- "统一"二字反证了此前的分散：bullet 格式化各模板各自实现 → 行为不一致
- PDF 和 Word 内容不一致反证了多格式各走各逻辑 → 同一数据两种产物
- 解法：渲染逻辑收敛到共享层（shared 组件 + 契约），模板只做差异化样式

### 2.1.3 为什么 scope 检测要迁移到工具层（真实原因）

**来源**：git 提交记录 - `9b1066c`

**提交信息原文**：
```
9b1066c | 2026-08-08 | 11099826 | refactor: scope检测逻辑迁移到工具层，修复agent_executor层注入无效问题
```

**详细解释**：
- "注入无效"直接说明：scope 检测放在 agent_executor 层根本不生效
- 根因：agent_executor 层的注入时机/位置与模板渲染的数据流不匹配（合理推断）
- 迁移到工具层后，scope 检测在数据进入渲染前生效
- 教训：**横切逻辑必须放在数据流真正经过的层**——与 01 号文档"双入口覆盖"同一教训

## 2.2 技术实现原因

### 2.2.1 为什么契约要区分主字段与 extra_sections（真实原因 + 合理推断）

**来源**：git 提交记录 - `b636f11`

**提交信息原文**：
```
b636f11 | 2026-08-11 | 11099826 | fix: extra_sections字段提取增强 + bullet缩进修正 + 语音URL修复
```

**详细解释**：
- 主字段（教育/工作/项目）：所有简历必有，所有模板必渲染
- extra_sections（奖项/语言/爱好/学术字段）：因人而异，模板选择性渲染
- 区分的原因：主字段的模板差异只是排版顺序；弱字段不同模板差异很大（学术模板不放爱好、创意模板可能放）
- `b636f11` 的"extra_sections 提取增强"说明弱字段是持续演进区——契约的弹性设计让演进不波及主字段

### 2.2.2 为什么 scope 判定要 LLM 兜底（真实原因）

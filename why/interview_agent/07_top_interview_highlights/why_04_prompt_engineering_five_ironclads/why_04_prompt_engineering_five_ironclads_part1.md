# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

五大铁律不是"写 prompt 的经验总结"，而是**复盘链路从 06-09 接入 ASR 到 08-07 上线交付拦截，两个月里逐条被事故逼出来的硬规则**。每一条铁律背后都对应一类真实翻车：漏题、幻觉数字、ASR 同音错字、无依据点评、脏产物放行。

## 1.2 逐条铁律的真实成因

### 铁律 1：全覆盖（逐题分析不许漏题）

**直接证据**：

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 08-07 | `05399d4` | feat(复盘报告): **交付前拦截逐题分析漏题并记录原因** |

- 这条提交直接说明：**逐题分析曾经会漏题**，而且严重到需要在"交付前"加一道拦截
- "并记录原因"——不只是拦截，还要归因，说明漏题有多种成因（上下文过长、题号格式不一、LLM 跳题），需要分类治理
- 漏题对复盘产品是致命的：用户答了 8 题，报告只点评 6 题，用户立刻质疑产品专业性

**为什么用"交付前拦截"而不是"prompt 里多强调几遍"**：prompt 强调只能降低概率，不能归零；复盘报告是**交付物**，必须有确定性闸门。`023a47b`（同日 "save_review_report 增加校验通过日志"）说明校验是正式流程的一环，通过与否都留痕。

### 铁律 2：硬闸（校验不过不许落盘）

**直接证据**：

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 08-07 | `023a47b` | feat: **save_review_report 增加校验通过日志** |

- 保存动作（save_review_report）被加了校验环节——即"产物不合格就不落盘"的硬闸
- 此前大概率发生过"坏报告直接落盘并推送给用户"的事故，才促使把校验前置到保存之前

### 铁律 3 & 5：数字精确 + 同音变体（ASR 输入的特殊性）

**背景证据——复盘输入来自语音转写**：

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 06-09 | `48f4d39` | 陈乾 · **新增asr工具 接入面试复盘链路** |
| 06-09 | `e63ab74` | 陈乾 · **ASR超时时间设为600s** |
| 06-09 | `0f4c103` | 陈乾 · feat(agent): 解析 message.metadata.audioUrl，拼入 query 供面试复盘使用 |

- 复盘的原始素材是**面试录音的 ASR 转写文本**，不是结构化数据
- ASR 文本有两大顽疾，直接催生两条铁律：
  1. **同音错字**：语音中"二叉树"可能被转成"二插树"。如果复盘 prompt 要求"严格按原文引用"，LLM 会把错字原样带进报告；如果要求"纠正"，又可能改错。**同音变体铁律**就是给 LLM 明确的容错边界：识别同音变体、按正确术语呈现、但不臆造原文没有的内容
  2. **数字漂移**：ASR 对数字的转写错误率高，而复盘里涉及评分、题数、时长等关键数字。**数字铁律**要求关键数字必须可溯源到原文，禁止 LLM 心算或估算
- `e63ab74` 把 ASR 超时设为 600s——说明面试录音转写是**长耗时、大文本**任务，转写质量波动大，下游 prompt 必须防御性设计

### 铁律 4：事实围栏（不许无依据点评）

- 复盘报告最伤用户的错误是"点评了用户没说过的话"——LLM 基于转写噪声脑补出"候选人提到了 XX 经验"，用户一看便知是幻觉，信任崩塌
- 事实围栏的设计：每条点评必须能对应到转写原文的依据，无依据的判断要么不写、要么显式标注为"建议补充"
- 旁证：`1df495b`（07-28 "复盘素材来自错题本时，按照时间顺序展示题目"）说明团队对"素材与产物的对应关系"有强执念——素材可溯源是复盘产品的一贯要求

## 1.3 为什么是"铁律"而不是"建议"？

### 复盘报告的产品地位

复盘报告是面试产品的**核心交付物**：
- 用户完成一场面试后，复盘报告是"这次练习值不值"的最终判断依据
- 报告错误（漏题、幻觉、错字）直接等于产品不合格
- 因此 prompt 规则必须是**铁律级**（违反即拦截），而非建议级（违反仅扣分）

### 交付拦截的架构选择

`05399d4` 的"交付前拦截"体现了一个关键架构决策：**不信任 LLM 的自律，用代码做他律**。

| 路线 | 做法 | 问题 |
|:---|:---|:---|
| **prompt 自律** | 在 prompt 里写"千万不要漏题" | 概率性，无法归零，无法归因 |
| **代码他律** | 交付前用代码核对题目清单，缺题即拦截重试 | 确定性，可记录原因（`05399d4` 原文） |

团队选择了**两者结合**：prompt 铁律降低违规概率（减少重试成本），代码拦截保证最终确定性。

### 链接治理的旁证：交付链路的每个环节都要治理

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 08-04 | `341e183` | 新增 GET_AUDIO_PUBLIC_URL 开关，开启时音频文件额外签发 public 短链并记录日志 |
| 08-04 | `92bc8e6` | **移除复盘报告链接域名替换流程** |

- 复盘报告的交付不只是文本，还包括**音频回听链接**——链接的签发（`341e183` 加开关+日志）与域名处理（`92bc8e6` 移除危险替换）都被逐一治理
- `92bc8e6` "移除域名替换流程"很可能是发现替换逻辑会把正确链接改坏——与其打补丁不如直接移除，体现了"交付链路上能删的环节就删"的减法思维

## 1.4 五大铁律的成因汇总表

| 铁律 | 防御的失败模式 | 证据 |
|:---|:---|:---|
| **全覆盖** | 逐题分析漏题 | `05399d4` 提交原文 |
| **硬闸** | 坏报告落盘推送 | `023a47b` 校验日志 |
| **数字精确** | ASR 数字转写漂移 + LLM 心算幻觉 | ASR 链路提交（`48f4d39` 等） |
| **事实围栏** | 无依据点评/脑补 | 素材可溯源传统（`1df495b`） |
| **同音变体** | ASR 同音错字进报告 | ASR 链路提交 |

## 1.5 反事实推理：如果没有这些铁律？

1. **无全覆盖**：漏题报告流向用户 → "AI 连我答了几题都数不清" → 产品信任崩塌
2. **无硬闸**：偶发的坏报告直接落盘 → 事故不可追溯（没有"校验通过日志"）
3. **无同音变体规则**：报告里出现"二插树"级别的笑话，或 LLM 过度纠错把对的改错
4. **无事实围栏**：幻觉点评让用户觉得"AI 根本没听我说话"

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 为什么漏题需要"交付前拦截"而不是 prompt 强调（真实原因）

**来源**：git 提交记录 - `05399d4`

**提交信息原文**：
```
05399d4 | 2026-08-07 | 陈乾 | feat(复盘报告): 交付前拦截逐题分析漏题并记录原因
```

**详细解释**：
- "交付前拦截"这个措辞说明：漏题问题已经严重到需要在最后一道关口设卡
- prompt 强调（"千万不要漏题"）只能降低概率，无法归零，更无法归因
- 代码核对题目清单是确定性操作：缺哪题、为什么缺，一清二楚

**业务场景**：
```
用户答了 8 题，复盘报告只点评了 6 题
用户感知："AI 连我答了几题都数不清" → 直接质疑产品专业性
漏题成因多样：
- 上下文过长 → LLM 跳题
- 题号格式不一 → LLM 不认为是题目
- 某题转写缺失 → 无素材可分析
不"记录原因"就无法分类治理，拦截会变成无脑重试
```

### 2.1.2 为什么校验要前置到保存动作（真实原因）

**来源**：git 提交记录 - `023a47b`

**提交信息原文**：
```
023a47b | 2026-08-07 | 陈乾 | feat: save_review_report 增加校验通过日志
```

**详细解释**：
- 校验加在 save_review_report（保存动作）上——即"不合格不落盘"
- 落盘是交付的起点（落盘后会推送用户），把闸门设在落盘前，坏产物永远到不了用户
- "校验通过日志"说明通过与否都留痕——审计与归因的基础

**技术对比**：
```
生成后人工审核：
- 复盘报告是高频自动交付物 → 人工不可扩展
- 延迟高，用户体验差

落盘后召回：
- 用户可能已经看到坏报告 → 伤害已造成
- 召回动作本身暴露问题，更伤信任

落盘前硬闸（最终方案）：
- 自动化、确定性、零用户感知
- 不合格直接重试或降级
```

### 2.1.3 为什么复盘素材必须"可溯源"（真实原因）

**来源**：git 提交记录 - `1df495b`

**提交信息原文**：
```
1df495b | 2026-07-28 | 陈乾 | 复盘素材来自错题本时，按照时间顺序展示题目
```

**详细解释**：
- 复盘素材来自错题本时要求"按时间顺序展示"——素材的组织方式直接影响产物的可核对性
- 素材可溯源是事实围栏的前提：只有点评能对应到具体素材，才能判断"有没有依据"
- 这是复盘产品的一贯要求，不是事后补救

## 2.2 技术实现原因

### 2.2.1 为什么数字必须"溯源原文"而不是让 LLM 计算（真实原因 + 合理推断）

**来源**：git 提交记录 - `48f4d39`、`e63ab74`（ASR 链路）

**提交信息原文**：
```
48f4d39 | 2026-06-09 | 陈乾 | 新增asr工具 接入面试复盘链路
e63ab74 | 2026-06-09 | 陈乾 | ASR超时时间设为600s
```

**详细解释**：
- 复盘素材是 ASR 转写文本，数字转写错误率高（"一千"与"1000"混用、同音数字错转）
- LLM 心算/估算会叠加第二层错误：转写错的数字 + LLM 再加工 = 错上加错
- 数字铁律：关键数字（评分、题数、时长）必须溯源转写原文，禁止心算

**错误叠加分析**：
```
原始语音："大概一千行代码"
ASR 转写："大概1000行代码"（形态变化，尚可接受）
若 LLM 再加工："约数千行代码"（估算，信息失真）

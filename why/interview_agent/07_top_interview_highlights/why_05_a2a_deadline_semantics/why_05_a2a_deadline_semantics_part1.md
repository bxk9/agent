# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

deadline 语义的最终形态（"收到进度消息即重置 deadline"）不是设计出来的，而是**07-16 至 07-28 连续 12 天、至少 7 次提交打磨出来的**。其中 07-21 一天内的两次修复（`0d3d2dd` + `b05db56`）和 07-27 的"三个 bug"提交（`02914d8`）构成了完整的事故-修复链。

## 1.2 真实原因（git 证据链，按时间顺序）

### 阶段 1：先解决"产物路径在哪"（07-16）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-16 | `ab71cda` | fix(doc_agent): 提取 statusUpdate.message.parts 中的产物路径并**补充完整调试日志** |
| 07-16 | `abd7c19` | feat(doc_agent): **产物路径优先从 data.uri 提取** + 命名规范更新 + 进度转发主Claw |

**为什么先做这个**：
- 一天内两次提交说明：第一版从 `statusUpdate.message.parts` 提路径不够可靠，当天就改为"**优先从 data.uri 提取**"——即产物路径在 A2A 消息里有多个可能位置，必须定优先级
- "补充完整调试日志"先于功能完善——说明当时 doc_agent 的产物丢失问题**难以复现和定位**，必须先有日志才能谈修复
- 这一阶段的根因认知是：**产物明明生成了，但主 Agent 拿不到路径** → 用户看不到文件

### 阶段 2：deadline 语义的两次关键修正（07-21）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-21 | `0d3d2dd` | fix(doc_agent): **移除 lastChunk 缩短 deadline 逻辑，避免提前退出丢失后续 artifact** |
| 07-21 | `b05db56` | fix(doc_agent): **收到进度消息时重置deadline，确保所有后续artifacts完整接收** |
| 07-21 | `48b6237` | feat(agent_executor): 文档Agent链接注入metadata.resources**兜底传递** |

这三条提交是理解"为什么"的核心：

**`0d3d2dd` 揭示的错误设计**：
- 最初存在一个"lastChunk 缩短 deadline"的优化——意图是"既然对方说这是最后一块，那就缩短等待时间快点结束"
- 后果：**提前退出丢失后续 artifact**——A2A 服务端标记的"lastChunk"并不可靠，后面还有产物
- 教训：这是典型的"用对端不可靠的信号来优化自己的超时"——把控制权交给了不可信的一方

**`b05db56` 确立的正确语义**：
- 改为"**收到进度消息时重置 deadline**"——只要对方还在发进度，就证明还活着、还在干活，deadline 就应该顺延
- 这个语义的本质是：**超时应该度量"静默时长"而不是"总时长"**。文档生成是长任务（几十秒到几分钟），总时长超时必然误杀正常任务；静默超时只惩罚真正卡死的任务

**`48b6237` 的兜底思维**：
- 同一天还加了"链接注入 metadata.resources 兜底传递"——即使主路径失败，也要有备用通道把链接传回去
- 说明团队此时的认知已升级为：**产物送达不能依赖单一通道**

### 阶段 3：静默超时的三个 bug 总清算（07-27）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-27 | `02914d8` | fix(doc_agent_client): **修复 A2A 静默超时导致产物丢失的三个 bug** |

- 提交标题直接点名"**三个 bug**"和"**静默超时导致产物丢失**"——这是对前一周修复的总清算，说明 07-21 的修复上线后仍有残留路径会触发产物丢失
- 三个 bug 的典型形态（结合 A2A 客户端实现推断）：
  1. 超时触发时**已收到的部分产物被整体丢弃**（应该保留已收部分）
  2. 超时计时器**没有在正确的消息类型上重置**（只在部分消息上重置）
  3. 超时后的**清理逻辑误伤了正常完成的会话**

### 阶段 4：参数固化与优雅关闭（07-20、07-28）

| 日期 | Commit | 提交信息 |
|:---:|:---|:---|
| 07-20 | `37a9175` | add Claw A2A WebSocket 的**优雅关闭逻辑** |
| 07-28 | `8b03975` | fix(doc_agent_tool): format_document 创建 A2AClient 时 **timeout 改为 600s** |

- `8b03975` 把 timeout 提到 600s——与陈乾把 ASR 超时设为 600s（`e63ab74`）是同一个数字，说明团队对"长任务 10 分钟上限"形成了共识参数
- `37a9175` 优雅关闭——超时/结束时不能直接断连，要走关闭握手，否则对端可能把"连接断开"误判为事故

## 1.3 为什么"静默超时"是唯一正确的语义？

| 语义 | 定义 | 问题 | 项目中的验证 |
|:---|:---|:---|:---|
| **总时长超时** | 从请求发出开始计时 | 长任务必被误杀 | 早期版本的事故来源（推断） |
| **lastChunk 信号超时** | 信任对端的"最后一块"标记 | 对端标记不可靠 → 提前退出 | `0d3d2dd` 明确移除 |
| **静默超时** | 只度量"多久没收到任何消息" | 需要正确的重置点 | `b05db56` 确立 + `02914d8` 修复三个重置点 bug |

**深层原理**：A2A 场景下，**"对端还活着"的唯一可靠证据是"还在收到消息"**。任何基于对端声明（lastChunk、progress 百分比）的判断都是不可信的——这与 TCP 的 keepalive、心跳机制同构。后来 08-13 的心跳修复（`ab4416e` "修复主Claw 180s 超时断连"）再次验证了同一原理：**活性靠持续的消息证明，不靠一次性声明**。

## 1.4 为什么这个 bug 这么难修（12 天 7 次提交）？

1. **难以复现**：只在"文档生成足够慢 + 产物足够多"时触发——测试环境的小文档永远不超时
2. **多通道干扰**：产物路径有多个来源（message.parts / data.uri / metadata.resources），修了一个通道另一个还在漏
3. **状态机复杂**：WebSocket 连接状态 × A2A 任务状态 × 超时计时器，三者交织
4. **修复本身引入新问题**：`0d3d2dd` 修的是上一个"优化"引入的 bug——超时逻辑的每次改动都可能改变时序

**这也是为什么 `ab71cda` 第一步就是"补充完整调试日志"**——没有日志，这个 bug 根本无从下手。

## 1.5 反事实推理：如果不修 deadline 语义？

1. **大文档必丢产物**：简历/报告这类长文档生成，产物丢失 = 用户等了 3 分钟拿到空结果
2. **"优化"越做越糟**：lastChunk 缩短逻辑若不移除，会持续误杀正常任务
3. **无法定位**：没有"三个 bug"的总清算，残留路径会持续偶发丢产物，变成永远的"偶现 bug"

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 为什么第一步是补日志而不是改逻辑（真实原因）

**来源**：git 提交记录 - `ab71cda`

**提交信息原文**：
```
ab71cda | 2026-07-16 | 司棋 | fix(doc_agent): 提取 statusUpdate.message.parts 中的产物路径并补充完整调试日志
```

**详细解释**：
- 产物丢失问题在当时**难以复现和定位**——用户报"文档没生成"，但文档 Agent 日志显示生成成功
- 没有完整日志，无法回答"产物路径到底在哪条消息里、主 Agent 有没有收到"
- 所以第一步是补全调试日志——这是分布式 bug 排查的纪律：**观测先于修改**

**业务场景**：
```
用户："我请求生成简历，等了三分钟，没有链接"
文档 Agent 日志："简历已生成并上传 VFS"
矛盾点：产物生成了，但主 Agent 没拿到路径
无日志：不知道路径在哪条消息、主 Agent 收到没有 → 无从下手
有日志：定位到路径在 data.uri 而提取逻辑只看 message.parts → 根因清晰
```

### 2.1.2 为什么产物路径要定优先级（真实原因）

**来源**：git 提交记录 - `abd7c19`

**提交信息原文**：
```
abd7c19 | 2026-07-16 | 司棋 | feat(doc_agent): 产物路径优先从 data.uri 提取 + 命名规范更新 + 进度转发主Claw
```

**详细解释**：
- A2A 协议中产物路径可能出现在多个位置：data.uri（结构化字段）、statusUpdate.message.parts（消息文本）
- 同一天早先的 `ab71cda` 只从 message.parts 提取，当天就发现不够可靠
- "优先从 data.uri 提取"确立了优先级：结构化字段 > 消息文本
- 本质：**多个来源并存时必须有明确的优先级规则**，否则提取行为不确定

### 2.1.3 为什么要移除 lastChunk 缩短逻辑（真实原因）

**来源**：git 提交记录 - `0d3d2dd`

**提交信息原文**：
```
0d3d2dd | 2026-07-21 | 司棋 | fix(doc_agent): 移除 lastChunk 缩短 deadline 逻辑，避免提前退出丢失后续 artifact
```

**详细解释**：
- lastChunk 缩短 deadline 的本意是优化：对端说"这是最后一块"，那就缩短等待快点结束
- 但 A2A 服务端标记的 lastChunk **并不可靠**——标记后仍可能有后续 artifact
- 后果：提前退出 → 后续 artifact 丢失（提交原文明确）
- 深层教训：**不要用对端的声明性信号来优化自己的超时控制**——声明可能撒谎，消息流不会

**技术对比**：
```
lastChunk 信号超时（已移除）：
- 依据：对端声明"这是最后一块"
- 风险：声明不可靠 → 提前退出丢产物
- 控制权：交给了对端

静默超时（最终方案）：
- 依据：自己观察"多久没收到消息"
- 风险：仅需保证重置点完整
- 控制权：在自己手里
```

### 2.1.4 为什么"收到进度即重置 deadline"是正确语义（真实原因）

**来源**：git 提交记录 - `b05db56`

**提交信息原文**：
```
b05db56 | 2026-07-21 | 司棋 | fix(doc_agent): 收到进度消息时重置deadline，确保所有后续artifacts完整接收
```

**详细解释**：
- 文档生成是长任务（几十秒到几分钟），总时长超时必然误杀
- "收到进度消息"是"对端还活着、还在干活"的硬证据

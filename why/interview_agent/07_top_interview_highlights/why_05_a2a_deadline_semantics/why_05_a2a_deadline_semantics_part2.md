- 只要持续收到进度，deadline 持续顺延 → 正常长任务永不误杀
- 只有完全静默超过阈值才判定卡死 → 真正卡死的任务必然释放

**场景示例**：
```
场景1：文档生成 3 分钟，每 10s 一条进度消息
  总时长超时（60s）：第 60s 误杀 → 产物丢失
  静默超时（60s）：每条进度重置 deadline → 3 分钟后正常完成 ✓

场景2：文档 Agent 卡死，无任何消息
  总时长超时：60s 后释放 ✓
  静默超时：60s 后释放 ✓
  → 静默语义在两个场景都正确，总时长语义只在场景2正确
```

## 2.2 技术实现原因

### 2.2.1 为什么产物送达要多通道兜底（真实原因）

**来源**：git 提交记录 - `48b6237`

**提交信息原文**：
```
48b6237 | 2026-07-21 | 司棋 | feat(agent_executor): 文档Agent链接注入metadata.resources兜底传递
```

**详细解释**：
- 产物路径的传递通道可能故障（消息丢失、字段缺失、解析失败）
- 单一通道故障 = 产物丢失，不可接受
- 兜底通道：agent_executor 层把链接注入 metadata.resources——即使 A2A 消息层失败，执行层还有一条路
- 三级通道：data.uri（P0）→ message.parts（P1）→ metadata.resources（P2）

### 2.2.2 为什么要优雅关闭（真实原因）

**来源**：git ��交记录 - `37a9175`

**提交信息原文**：
```
37a9175 | 2026-07-20 | 司棋 | add Claw A2A WebSocket 的优雅关闭逻辑
```

**详细解释**：
- 超时或任务结束时如果直接断连，对端无法区分"正常结束"和"事故断连"
- 对端误判事故 → 可能触发不必要的重试或告警
- 优雅关闭：发送关闭帧 → 等待确认 → 关闭连接，让对端正常收尾

### 2.2.3 为什么超时是 600s（真实原因）

**来源**：git 提交记录 - `8b03975`、`e63ab74`

**提交信息原文**：
```
8b03975 | 2026-07-28 | 司棋 | fix(doc_agent_tool): format_document 创建 A2AClient 时 timeout 改为 600s
e63ab74 | 2026-06-09 | 陈乾 | ASR超时时间设为600s
```

**详细解释**：
- 两个不同模块（A2A 调用、ASR 转写）都把长任务超时定为 600s
- 说明团队形成了"长任务 10 分钟上限"的共识参数
- 静默语义下 600s 的含义是"完全失联的容忍上限"，不是任务时长上限——有进度的任务不受此限

## 2.3 性能与质量原因

### 2.3.1 为什么三个 bug 要做"总清算"而不是逐个修（真实原因）

**来源**：git 提交记录 - `02914d8`

**提交信息原文**：
```
02914d8 | 2026-07-27 | 司棋 | fix(doc_agent_client): 修复 A2A 静默超时导致产物丢失的三个 bug
```

**详细解释**：
- 07-21 的修复上线后仍有产物丢失——说明问题不是单点，而是**同一语义缺陷的多个残留路径**
- 逐个修会陷入"修一个冒一个"的循环（01 号文档三层防御前的同样困境）
- 总清算：把静默超时相关的所有路径一次性梳理，三个 bug 一个提交解决
- 这与"体系化防御优于单点补丁"是同一方法论

### 2.3.2 为什么超时后保留已收产物（合理推断）

**详细解释**：
- 超时是止损手段，不是惩罚——已收到的产物是有效成果
- 整体丢弃会把损失扩大：用户等了 3 分钟，连部分产物都拿不到
- 正确做法：保留已收部分 + 标记未完成 + 上报超时事件

## 2.4 工程实现原因

### 2.4.1 为什么这个 bug 修了 12 天（合理推断，基于提交节奏）

**详细解释**：
- **难复现**：只在"文档生成足够慢 + 产物足够多"时触发，测试环境的小文档永远不超时
- **多通道干扰**：产物路径三个来源，修一个通道另一个还在漏
- **状态机复杂**：WebSocket 连接状态 × A2A 任务状态 × 超时计时器三者交织
- **修复引入新问题**：`0d3d2dd` 修的就是上一个"优化"引入的 bug——超时逻辑的每次改动都可能改变时序
- 应对：日志先行（`ab71cda`）+ 关键日集中攻坚（07-21 一天三提交）+ 总清算（`02914d8`）

### 2.4.2 为什么心跳修复是同一原理的再验证（真实原因）

**来源**：git 提交记录 - `ab4416e`

**提交信息原文**：
```
ab4416e | 2026-08-13 | 司棋 | fix: 恢复心跳 message 字段，修复主Claw 180s 超时断连
```

**详细解释**：
- 三周后的心跳修复再次验证同一原理：主 Claw 靠"持续收到心跳消息"判断对端存活
- 心跳字段被移除 → 主 Claw 收不到活性证明 → 180s 超时断连
- 与 A2A deadline 同构：**活性靠持续的消息证明，不靠一次性声明**

## 3. 总结

### 3.1 核心原因总结

1. **日志先行**（真实）：产物丢失难复现，补全日志才能定位
2. **路径定优先级**（真实）：多来源并存必须有明确规则
3. **移除 lastChunk**（真实）：对端声明不可靠，控制权要在自己手里
4. **静默超时**（真实）：度量失联时长而非任务时长，长任务不误杀

### 3.2 技术原因总结

1. **多通道兜底**（真实）：产物送达不依赖单一通道
2. **优雅关闭**（真实）：让对端能区分正常结束与事故
3. **600s 共识**（真实）：长任务 10 分钟上限的团队参数
4. **总清算**（真实）：同一语义缺陷的多个残留路径一次性解决

### 3.3 业务价值总结

1. **交付确定性**：生成的产物必然送达
2. **长任务友好**：几分钟的文档生成不被误杀
3. **止损可控**：卡死任务 600s 内释放

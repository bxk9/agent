3. **日志自防护**：ctx_log 防崩溃，日志组件永不拖垮业务

2. **链路追踪设计**：trace_id/tenant/user 三元组贯穿 LLM/VFS/Skill
3. **内存安全**：FIFO 限容防泄漏

### 6.3 业务价值

1. **成本可见**：请求级 token 汇总，成本可核算
2. **优化有据**：150 分钟事故一天定位
3. **报障可归因**：trace_id 回查全链路

### 6.4 方法论抽象与迁移（原文档保留部分）

**抽象出的通用方法论——"可观测三支柱 + 观测先行"**：

1. **观测是优化的入场券**：没有分段数据，"感觉慢"永远是悬案（150 分钟事故一天定位是最佳证明）
2. **上下文传递要匹配并发模型**：纯 asyncio 用 contextvar，混合线程池必须显式传递
3. **汇总要聚合**：分散的指标在高并发下无价值，请求级单条汇总才可用
4. **日志自防护**：可观测组件自身的故障必须静默降级

| 场景 | 迁移点 |

## 7. 面试问答准备

### Q1: contextvar 为什么会失效？

**A**：
1. contextvars 绑定在 asyncio 的 Context 上，协程切换时自动传递
2. 但 run_in_executor 把函数丢到线程池线程执行，默认不复制完整 Context → 变量丢失
3. 本项目大量使用 executor（工具调用、阻塞 IO），断点太多
4. 解法：模块级 FIFO 字典，以 request_id 显式存取（`95bf297`）

### Q2: 为什么用 FIFO 字典而不是普通 dict？

**A**：
1. 请求异常中断时 flush 不会被调用，条目会残留
2. 普通 dict 会无限增长 → 内存泄漏
3. FIFO（OrderedDict + popitem(last=False)）限制容量，最旧条目先挤出
4. 本质：用有界缓存换内存安全

### Q3: 为什么 token 汇总要单条日志？

**A**：
1. 一次请求有多次 LLM 调用 + 多次工具调用，分散输出在高并发下交错
2. 交错的日志无法归属到具体请求，失去汇总意义
3. 单条汇总 + trace_id：一行看清请求总成本（`124a5b1`）

### Q4: 可观测体系建好后第一个收获是什么？

**A**：
1. 上线一天内定位 150 分钟级事故（08-05 上线，08-06 `08bcac0` 修复）
2. 此前这类事故只能靠用户反馈暴露，无法定位是哪个环节
3. 分段耗时数据直接指出瓶颈——这是"观测先行"价值的最佳证明

### Q5: 日志系统自身如何保证可靠？

**A**：
1. ctx_log 内部防崩溃（`f3e2204`）：任何异常静默降级，绝不抛出
2. 日志组件不能成为业务故障源——这是可观测系统的第一原则
3. 线程前缀显式传递（`41d47cf`）：线程切换丢上下文是反复出现的坑，要持续治理

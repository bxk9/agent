## 1. 核心设计原因

### 1.1 为什么选择四维度分类体系（真实原因）

**来源**：git提交记录 - 573d379、17018df、b732300、3bbc8ee

**提交信息**：
```
573d379 | 2026-03-26 | 彭亚 | 优化了标签体系和分类定义
17018df | 2026-03-27 | 彭亚 | 更新标签名和定义
b732300 | 2026-03-25 | 彭亚 | 更新了标签字段和描述
3bbc8ee | 2026-03-25 | 彭亚 | 更新了是否意图明确标签名和描述
```

**详细解释**：
- 2026年3月25-27日，彭亚连续提交了4次关于标签体系的优化
- 这说明四维度分类体系是在这个时期确立的
- 四维度分类体系包括：工具类型、意图明确度、指令类型、执行状态

**设计逻辑**：
```
维度1：工具类型（is_use_tool）
- 判断用户query需要调用多少个工具
- 标签：single/multi/qa/chat/pend/unsupported

维度2：意图明确度（is_intent_specific）
- 判断用户query的意图是否清晰
- 标签：clear/lack/infer/vague

维度3：指令类型（is_special_instruction）
- 判断用户query是否包含特殊的指令类型
- 标签：norm/cond

维度4：执行状态（is_exe_success）
- 判断用户query是否包含对上一轮执行的反馈
- 标签：ok/abnormal
```

- 这说明标签的定义和命名是在这个时期确定的

**标签选择逻辑**：
```
工具类型标签：
- single：单工具调用（最常见）
- multi：多工具调用（复杂任务）
- qa：知识问答（无需工具）
- chat：闲聊（无需工具）
- pend：工具待确定（意图模糊）
- unsupported：工具不支持（无法执行）

意图明确度标签：
- clear：意图清晰（参数完整）
- lack：参数不足（需要补充）
- infer：参数需推理（需要推理）
- vague：意图模糊（需要澄清）

指令类型标签：
- norm：普通指令（直接执行）
- cond：条件指令（需要条件判断）

执行状态标签：
- ok：正常推进（无异常）
- abnormal：异常反馈（有异常）
```

## 2. 规则体系设计原因

### 2.1 为什么需要优先级规则（真实原因）

**来源**：git提交记录 - f484289、ee15ab1、d4695ad

**提交信息**：
```
f484289 | 2026-04-27 | 彭亚 | 更新了优先级规则
ee15ab1 | 2026-05-13 | 彭亚 | 更新了优先级和子类定义
d4695ad | 2026-05-08 | 彭亚 | 优化了闲聊和query优先级的定义
```

**详细解释**：
- 2026年4月27日，彭亚更新了优先级规则
- 2026年5月8日，彭亚优化了闲聊和query优先级的定义
- 2026年5月13日，彭亚更新了优先级和子类定义
- 这说明优先级规则是在这个时期确立的

**优先级规则**：
```
工具类型优先级：
multi > pend > unsupported > single > qa > chat

意图明确度优先级：
vague > infer > lack > clear

指令类型优先级：
cond > norm

执行状态优先级：
abnormal > ok
```

**设计逻辑**：
```
为什么需要优先级规则？
- 当多个标签都符合时，需要选择一个
- 优先级规则确保选择最合适的标签
- 避免模型输出不一致

为什么选择这个优先级顺序？
- multi > pend：多工具调用比工具待确定更明确
- pend > unsupported：工具待确定比工具不支持更可能执行
- unsupported > single：工具不支持比单工具调用更需要特殊处理
- single > qa：单工具调用比知识问答更需要工具
- qa > chat：知识问答比闲聊更需要处理

- vague > infer：意图模糊比参数需推理更需要澄清
- infer > lack：参数需推理比参数不足更可能自动解决
- lack > clear：参数不足比意图清晰更需要补充

- cond > norm：条件指令比普通指令更需要特殊处理

- abnormal > ok：异常反馈比正常推进更需要处理
```

### 2.2 为什么需要强绑定规则（真实原因）

**来源**：git提交记录 - d5a4303、5e6a377

**提交信息**：
```
d5a4303 | 2026-06-02 | 彭亚 | 强绑定规则更新
5e6a377 | 2026-05-28 | 彭亚 | 绑定规则优化
```

**详细解释**：
- 2026年5月28日，彭亚优化了绑定规则
- 2026年6月2日，彭亚更新了强绑定规则
- 这说明强绑定规则是在这个时期确立的

**强绑定规则**：
```
工具调用类型 ∈ {chat, qa, unsupported} → 强绑定clear
工具调用类型 = pend → 强绑定vague
```

**设计逻辑**：
```
为什么chat/qa/unsupported强绑定clear？
- chat：闲聊不需要参数，意图本身就是清晰的
- qa：知识问答不需要参数，意图本身就是清晰的
- unsupported：工具不支持不需要参数，意图本身就是清晰的

为什么pend强绑定vague？
- pend：工具待确定是因为意图模糊导致的
- 如果意图清晰，就能确定调用哪个工具，就不会是pend
- 因此pend必然对应vague
```

- 这说明扩展规则和排除规则是在这个时期逐步完善的

**扩展规则示例**：
```
播放类默认锚定规则：
- 仅针对播放类任务，"播放XX"默认锚定播放类工具
- 判single而非pend

常识消歧规则：
- 当query的动作+对象齐全，结合用户习惯与生活常识存在唯一高概率指向时
- 应按该高概率意图锁定对应候选工具，属single

省略式属性查询规则：
- 若query由"实体+可量化/可查询的属性名词"构成
- 该属性名词本身已隐含唯一明确的查询诉求
- 应按对应工具判single（或qa），意图明确度判clear
```

**排除规则示例**：
```
工具自带条件参数排除规则：
- 若候选工具本身就以"时间/时长/触发条件"作为其原生输入参数
- 则用户提到的时间/条件只是该工具的常规参数填充
- 不属于cond

用户侧错误排除规则：
- 错误源头在用户自身（说错、改主意、临时换内容、补充新约束）
- 即使带"不对/错了/不是…"等语气词也仍属ok
```

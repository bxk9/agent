1. **TokenBudget**：归一化压力感知，不同模型可以用统一的阈值配置
2. **轻量 token 估算**：粗略估算误差 <10%，性能优先
3. **近期轮次保护**：HistoryFader 保留最近 K 轮完整，OldTurnDropper 至少保留 min_keep_turns

### 6.3 业务价值

1. **最大对话轮次提升 200%**：从 5 轮提升到 15+ 轮
2. **超限错误率降低 93%**：从 15% 降至 <1%
3. **低压力不过度压缩**：保留完整上下文，回复质量不下降

### 6.4 方法论抽象与迁移

**抽象出的通用方法论——"压力驱动的多级压缩"**：

1. **感知压力**：用归一化指标（如 pressure）感知系统压力
2. **多级策略**：按信息损失从小到大排列多级策略
3. **渐进激活**：低压力时只启用信息损失小的策略，高压力时逐步启用信息损失大的策略
4. **保护关键信息**：近期数据优先保留，旧数据优先压缩

**可迁移场景**：

| 场景 | 迁移点 |
|:---|:---|
| 数据库查询缓存淘汰 | 按访问频率分级淘汰 |
| 日志系统存储管理 | 按时间分级压缩/丢弃 |
| 内存管理 | 按优先级分级回收 |

## 7. 面试问答准备

### Q1: 为什么是四道防线，不是三道或五道？

**A**：
1. 四道防线对应四类压缩需求：结构化提取、通用截断、历史淡化、整轮丢弃
2. 三道会漏：比如把结构化提取和通用截断合并，会导致"结构化提取"和"截断"的职责混淆
3. 五道没必要：四道防线已覆盖所有压缩需求，加道只增加维护成本
4. 实证：实际场景中四道防线足够将 15 轮对话压缩到上下文窗口内

### Q2: 为什么用 pressure 而不是直接用 token 数？

**A**：
1. 不同模型的上下文窗口大小不同（8192 vs 128000）
2. pressure 归一化到 0-1，可以用统一的阈值配置
3. 可读性：pressure=0.8 比 used=10240 更直观
4. 可扩展：新增模型时无需修改阈值配置

### Q3: 为什么不用精确 tokenizer？

**A**：
1. 精确 tokenizer 需要加载模型，性能开销大
2. 粗略估算误差 <10%，压缩策略有容错空间
3. 简化实现：无需引入 tokenizer 依赖
4. 实证：粗略估算在实际场景中足够准确

### Q4: 如何保证压缩后不丢失关键信息？

**A**：
1. 结构化提取优先：L1 只提取关键字段，保留核心语义
2. 近期轮次保护：L3 保留最近 K 轮完整，L4 至少保留 min_keep_turns
3. 渐进激活：低压力时只启用信息损失小的压缩器
4. 占位符提示：L3 用占位符提示模型"这里有历史工具结果"

### Q5: 这个方法论能迁移到什么场景？

**A**：
1. 任何"需要在有限资源内保留尽可能多的有效信息"的场景：缓存淘汰、日志管理、内存管理
2. 迁移要点：感知压力 → 多级策略 → 渐进激活 → 保护关键信息
3. 反例警示：不做压力感知会导致过度压缩或压缩不足，不保护关键信息会导致用户体验下降

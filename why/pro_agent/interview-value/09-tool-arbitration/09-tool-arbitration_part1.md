```
      ↓ 工具共现仲裁系统正式落地
```

**关键决策 1：声明式规则，而不是硬编码**

产品人员可以直接修改 MD 文件配置策略，无需开发人员介入，修改后无需重启服务。

**关键决策 2：JSON 元数据 + MD 策略正文分离**

JSON 存储结构化元数据（触发条件、规则名称），MD 存储策略正文（可直接预览编辑），分离关注点。

**关键决策 3：双维度触发（工具共现 + 请求特征）**

单维度无法覆盖所有场景，双维度设计覆盖更多场景，且支持 AND 组合实现精确匹配。

**淘汰的方案**：

| 淘汰方案 | 淘汰原因 |
|:---|:---|
| **硬编码策略** | 产品人员无法参与配置，修改需重启服务 |
| **单维度触发** | 无法覆盖纯请求特征场景或纯工具共现场景 |
| **策略正文写在 JSON 中** | 长文本难以阅读和编辑，无法直接预览 |
| **无条件全局注入** | 增加 system_prompt 长度，影响模型性能 |

## 2. 项目背景与问题定义

### 2.1 业务场景

pro_agent 支持 148 个工具，覆盖 13 个业务领域，某些工具能力重叠：

```
场景 1：闹钟 vs 日程
用户: "帮我定一个明天早上八点的闹钟"
  → 意图检索同时召回: create_alarm（闹钟）和 create_schedule（日程）
  → 模型可能选择任一工具
  → 产品期望: 应该选择 create_alarm（闹钟更适合定时提醒）

场景 2：音量调节 vs 设置跳转
用户: "把音量调到 50%"
  → 意图检索同时召回: adjust_volume（音量调节）和 adjust_phone_settings（设置跳转）
  → 模型可能选择任一工具
  → 产品期望: 应该选择 adjust_volume（直接调节音量数值）

场景 3：图片工具选择
用户: (上传图片，未输入文字)
  → 意图检索召回多个图片工具: general_image_qa, image_text_translate, ...
  → 模型不知道选择哪个工具
  → 产品期望: 根据图片类型和历史对话选择最合适的工具
```

**系统特征**：
- 工具数量：148 个工具，覆盖 13 个业务领域
- 能力重叠：某些工具能力重叠（如闹钟和日程、音量调节和设置跳转）
- 模型不确定性：能力重叠时模型选择具有不确定性
- 产品策略：产品团队有明确的工具选择策略，但难以落地

### 2.2 问题分析

**体系化之前的真实问题**：

| # | 问题 | 严重程度 | 具体表现 |
|---|---|---|---|
| 1 | 工具选择不确定 | **用户体验差** | 能力重叠时模型随机选择，用户体验不一致 |
| 2 | 产品策略难落地 | **可维护性差** | 策略逻辑硬编码在代码中，修改需重启服务 |
| 3 | 规则难以管理 | **可扩展性差** | 规则散落在各处，难以维护和审计 |
| 4 | 产品人员无法参与 | **协作效率低** | 产品人员无法直接配置策略，需要开发人员介入 |

**关键洞察**：
- 这些问题的根因是**缺乏声明式的规则引擎**
- 硬编码策略无法快速响应产品需求变化
- **浪费**：每次调整策略都需要修改代码、测试、发版

**三类失败模式的典型样本**：

```
失败模式 1：工具选择不确定
场景: 用户说"明天早上八点提醒我开会"
问题: 意图检索同时召回 create_alarm 和 create_schedule
后果: 模型随机选择，可能创建日程而不是闹钟，用户错过提醒

失败模式 2：产品策略硬编码
场景: 产品团队调整闹钟/日程选择策略
问题: 策略逻辑硬编码在代码中，修改需重启服务
后果: 策略调整周期长（修改代码 → 测试 → 发版 → 重启），响应慢

失败模式 3：规则难以管理
场景: 新增一条仲裁规则
问题: 规则散落在各处，难以找到合适的位置添加
后果: 规则管理混乱，难以维护和审计
```

### 2.3 优化目标

**核心问题**：如何让产品人员可以直接配置工具选择策略，而无需开发人员介入？

**量化目标**：
- 工具选择准确率从 70% 提升到 95%
- 用户投诉率从 5% 降至 0.5%
- 规则修改成本降低 80%（从"修改代码 + 重启"降至"修改配置 + 热更新"）

## 3. 技术方案设计

### 3.1 核心思路

**声明式规则引擎 + 双维度触发 + 策略注入**（命名直接来自设计文档）：

```
_stage_infer
    ↓
collect_arbitration_prompts(tools, request_flags)
    ├─ 加载规则（configs/*.json + configs/*.md）
    ├─ 评估触发条件（trigger_tools + trigger_flags）
    └─ 返回命中的 prompt 列表
    ↓
注入到 system_prompt 末尾
    ↓
模型推理（根据策略做出确定性选择）
```

**关键挑战**：
1. 如何设计声明式的规则配置？
2. 如何设计灵活的触发机制？
3. 如何防止非法配置导致的全局污染？
4. 如何支持热更新？

### 3.2 规则配置格式

**设计原则**：JSON 元数据 + MD 策略正文，分离结构和内容

**JSON 元数据**（configs/alarm_schedule.json）：

```json
{
    "name": "alarm_schedule_arbitration",
    "description": "闹钟/日程仲裁：当 create_alarm 和 create_schedule 同时被召回时",
    "trigger_tools": ["create_alarm", "create_schedule"],
    "trigger_flags": [],
    "prompt_file": "alarm_schedule.md"
}
```

**MD 策略正文**（configs/alarm_schedule.md）：

```markdown
## 工具选择策略

当用户请求可能同时适用于闹钟和日程时，请按以下优先级判断：

1. **打断强度**：需要强打断（响铃/振动）→ 闹钟
2. **时间形态**：精确时间点 → 闹钟；时间段 → 日程
3. **信息复杂度**：简单提醒 → 闹钟；复杂事项 → 日程
4. **规划感**：临时性 → 闹钟；计划性 → 日程
5. **兜底**：无法判断时 → 闹钟

示例：
- "明天早上八点提醒我开会" → create_alarm（精确时间 + 强打断）
- "明天上午安排一个产品评审会" → create_schedule（时间段 + 复杂事项）
```

### 3.3 双维度触发机制

**设计原则**：双维度覆盖更多场景，AND 组合实现精确匹配

| 维度 | 说明 | 示例 |
|:---|:---|:---|
| **trigger_tools** | 工具共现：所有工具同时被召回 | ["create_alarm", "create_schedule"] |
| **trigger_flags** | 请求特征：所有标记都由调用方传入 | ["image_mock_query"] |

**组合规则**：
- 两者同时声明时取 AND（必须同时满足）
- 某项留空则该项不约束（只检查另一项）
- 两者皆空视为非法配置，跳过并告警

## 4. 核心实现细节

### 4.1 仲裁引擎

**实现位置**：`operations/arbitration/engine.py`

```python
_rules: list[dict] = []

def init():
    """初始化仲裁规则（启动时调用一次）"""
    global _rules
    _rules = _load_rules()
    logger.info(f"[arbitration] 加载仲裁规则 {len(_rules)} 条")

def _load_rules() -> list[dict]:
    """从 configs/ 目录加载所有 JSON 仲裁规则"""
    rules = []
    for filename in sorted(os.listdir(_CONFIGS_DIR)):
        if not filename.endswith(".json"):
            continue
        filepath = os.path.join(_CONFIGS_DIR, filename)
        data = read_json(filepath)
        if isinstance(data, list):
            rules.extend(data)
        else:
            rules.append(data)
    _resolve_prompt_files(rules)
    return rules

def _resolve_prompt_files(rules: list[dict]):
    """将 prompt_file 指向的 MD 内容加载到 arbitration_prompt 字段"""
    for rule in rules:
        prompt_file = rule.get("prompt_file")
        if not prompt_file:
            continue
        md_path = os.path.join(_CONFIGS_DIR, prompt_file)
        rule["arbitration_prompt"] = read_text(md_path).strip()
```

**关键设计**：
- 启动时加载所有规则，缓存到全局变量 `_rules`
- JSON 元数据和 MD 策略正文分离，启动时合并
- 规则文件按文件名排序加载，保证确定性

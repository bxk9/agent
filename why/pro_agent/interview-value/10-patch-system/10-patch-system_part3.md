5. **ManagedConfigBridge 集成**：支持配置中心热更新，validator 校验 + fallback 兜底

### 6.3 业务价值

1. **新增场景成本降低 90%**：从"修改代码 + 重启"降至"修改配置 + 热更新"
2. **运营响应时间降低 99%**：从 1-2 天降至 5 分钟
3. **工具选择准确率提升 12%**：从 85% 提升到 95%
4. **运营人员可参与配置**：运营人员可以直接编辑 JSON 配置，无需开发人员介入

### 6.4 方法论抽象与迁移

**抽象出的通用方法论——"声明式规则引擎设计五原则"**：

1. **声明式配置**：让非技术人员可以直接配置规则，无需开发人员介入
2. **多种触发器**：覆盖各种触发场景，支持组合使用
3. **多种干预动作**：灵活组合，满足各种干预需求
4. **安全校验**：硬校验 + 白名单校验，保证系统安全性
5. **热更新支持**：通过配置中心实时下发规则，快速响应需求变化

## 7. 面试问答准备

### Q1: 为什么设置 200 字硬校验？

**A**：
1. 性能保护：过长的提示词会增加 system_prompt 长度，影响模型推理速度
2. 定位明确：Patch 定位为"轻量引导"，长策略应投仲裁系统
3. 防止滥用：硬校验防止运营人员无意中注入过长内容
4. 全局一致：200 字限制对全部 74 个 Patch 生效，保证一致性
5. 实证：早期测试时发现一条规则注入 1000 字提示词，导致模型推理速度下降 30%

### Q2: Patch 系统与仲裁系统的分工是什么？

**A**：
1. 仲裁系统：解决工具共现冲突，注入长策略正文（MD 文件，无长度限制）
2. Patch 系统：动态干预，注入短提示词（200 字限制）
3. 分工明确：长策略投仲裁，短提示投 Patch
4. 实证：闹钟/日程选择策略需要 500+ 字详细描述，适合仲裁系统；天气查询续接策略只需 50 字，适合 Patch 系统

### Q3: 自定义触发器的设计思路是什么？

**A**：
1. 注册表模式：通过装饰器注册，不修改核心代码
2. 统一接口：所有触发器接收 (query, body, patch) 参数
3. 灵活扩展：运营人员可以请求开发人员添加新的自定义触发器
4. 安全隔离：触发器异常不影响其他 Patch 规则
5. 实证：支付宝支付场景需要检查前台 App，声明式配置无法表达，使用自定义触发器

### Q4: 为什么需要白名单校验？

**A**：
1. 防止误操作：运营人员可能误写模块名或验证器名
2. 安全性：防止禁用关键模块或豁免关键验证器
3. 可追溯：白名单变更需要代码审查，便于追溯
4. 实证：早期测试时发现一条规则误禁用 critical_module，导致系统功能异常

### Q5: 这个方法论能迁移到什么场景？

**A**：
1. 任何"需要非技术人员参与规则配置"的场景：推荐系统、风控系统、运营活动
2. 迁移要点：声明式配置 → 多种触发器 → 多种干预动作 → 安全校验 → 热更新
3. 反例警示：不做安全校验会导致误操作导致系统异常，不做热更新会导致响应速度慢

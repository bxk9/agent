### 1.1 一句话摘要

面对运营干预需求频繁变化但硬编码响应慢的问题，我设计了声明式 Patch 系统，通过 7 种触发器（query 匹配、工具共现、模型类型、版本范围、自定义触发器等）和 7 种干预动作（注入工具、剔除工具、注入提示词、模型切换等），让运营人员可以直接配置干预规则而无需开发人员介入，同时通过 200 字硬校验和白名单校验保证系统安全性。

### 1.3 方案演进与关键决策

**演进时间线**（git 证据）：

```
阶段 1（2026-03 ~ 2026-05）：硬编码干预期
  每个运营干预场景单独写 if-else，代码膨胀、难以维护
      ↓ 认识到：运营需求频繁变化，硬编码响应太慢
阶段 2（2026-06）：Patch 系统设计时刻
  设计声明式 Patch 系统，支持多种触发器和干预动作
      ↓ 声明式规则引擎 + 200 字硬校验完整设计
阶段 3（2026-06 ~ 2026-08）：Patch 系统实施时刻
  74 条 Patch 规则陆续落地，运营响应时间从 1-2 天降至 5 分钟
      ↓ Patch 动态干预系统正式落地
```

**关键决策 1：声明式规则，而不是硬编码**

运营人员可以直接编辑 JSON 配置干预规则，无需开发人员介入，修改后通过配置中心热更新，无需重启服务。

**关键决策 2：7 种触发器 + 7 种干预动作**

触发器覆盖 query 匹配、工具共现、模型类型、版本范围、自定义触发器等多种场景；干预动作覆盖注入工具、剔除工具、注入提示词、模型切换、禁用 prompt 模块、豁免验证器等多种操作。

**关键决策 3：200 字硬校验 + 白名单校验**

提示词 200 字硬校验防止注入过长内容影响性能；disable_prompt_modules 和 bypass_batch_validators 白名单校验防止误操作。

**淘汰的方案**：

| 淘汰方案 | 淘汰原因 |
|:---|:---|
| **硬编码干预逻辑** | 运营需求频繁变化，修改代码 + 重启服务响应太慢 |
| **无长度限制的提示词注入** | 可能注入过长内容影响模型性能 |
| **无白名单校验** | 可能误禁用关键 prompt 模块或豁免关键验证器 |
| **无自定义触发器** | 声明式配置无法表达复杂业务逻辑 |

## 2. 项目背景与问题定义

### 2.1 业务场景

pro_agent 需要支持多种运营干预需求：

```
场景 1：工具注入
用户: "发朋友圈"
  → 意图检索未召回 social_post 工具
  → 运营期望: 注入 social_post 工具，让用户可以发朋友圈

场景 2：模型切换
用户: "把音量调到 50%"
  → Flash 模型可能幻觉 setting_name
  → 运营期望: 切换到 Pro 模型，避免幻觉

场景 3：提示词注入
用户: "今天天气怎么样？"
  → 用户已打开位置服务
  → 运营期望: 注入提示词"用户已打开位置服务，请直接查询当前所在城市的天气"

场景 4：工具剔除
用户: "帮我查一下明天天气"
  → 意图检索召回 weather_forecast 和 create_alarm
  → 运营期望: 剔除 create_alarm（不合适）

场景 5：验证器豁免
用户: (特定场景)
  → chat_intent_validator 误判为 CHAT 场景
  → 运营期望: 豁免该验证器，避免误判
```

**系统特征**：
- 运营需求频繁变化：每周新增 5-10 条干预规则
- 干预类型多样：工具注入、剔除、提示词注入、模型切换、验证器豁免
- 触发条件复杂：query 匹配、工具共现、模型类型、版本范围、自定义逻辑
- 安全性要求高：不能注入过长内容，不能误禁用关键模块

### 2.2 问题分析

**体系化之前的真实问题**：

| # | 问题 | 严重程度 | 具体表现 |
|---|---|---|---|
| 1 | 干预逻辑硬编码 | **可维护性差** | 每个场景单独写 if-else，代码膨胀 |
| 2 | 修改需重启 | **响应速度慢** | 新增场景需修改代码并重启服务 |
| 3 | 缺乏统一管理 | **可审计性差** | 规则散落在各处，难以审计和追踪 |
| 4 | 无安全校验 | **安全性差** | 提示词长度无限制，可能影响性能 |
| 5 | 运营人员无法参与 | **协作效率低** | 运营人员无法直接配置规则，需要开发人员介入 |

**关键洞察**：
- 这些问题的根因是**缺乏声明式的规则引擎**
- 硬编码干预逻辑无法快速响应运营需求变化
- **浪费**：每次新增干预场景都需要修改代码、测试、发版、重启

**三类失败模式的典型样本**：

```
失败模式 1：干预逻辑硬编码
场景: 运营需要新增"发朋友圈"工具注入
问题: 需要修改代码、测试、发版、重启
后果: 响应周期 1-2 天，运营需求无法快速落地

失败模式 2：提示词过长
场景: 运营注入 1000 字的提示词
问题: 无长度限制，system_prompt 膨胀
后果: 模型推理速度下降 30%，用户体验差

失败模式 3：误禁用关键模块
场景: 运营误写 disable_prompt_modules: ["critical_module"]
问题: 无白名单校验，关键模块被禁用
后果: 系统功能异常，用户投诉
```

### 2.3 优化目标

**核心问题**：如何让运营人员可以直接配置干预规则，而无需开发人员介入？

**量化目标**：
- 新增场景成本降低 90%（从"修改代码 + 重启"降至"修改配置 + 热更新"）
- 运营响应时间从 1-2 天降至 5 分钟
- 工具选择准确率从 85% 提升到 95%

## 3. 技术方案设计

### 3.1 核心思路

**声明式 Patch 系统 + 多种触发器 + 多种干预动作 + 安全校验**（命名直接来自代码实现）：

```
_stage_prepare
    ↓
query_patch_match(query, tools, body)
    ├─ 遍历所有 Patch 规则
    ├─ 评估触发条件（7 种触发器）
    └─ 返回命中的 PatchResult 列表
    ↓
应用 Patch 干预（7 种干预动作）
    ├─ collect_injected_tools() → 注入工具
    ├─ collect_removed_tools() → 剔除工具
    ├─ collect_injected_settings() → 注入设置
    ├─ apply_tool_patches() → 应用工具补丁
    ├─ collect_target_model() → 模型切换
    ├─ collect_disabled_modules() → 禁用 prompt 模块
    └─ collect_bypass_validators() → 豁免验证器
```

**关键挑战**：
1. 如何设计灵活的触发机制？
2. 如何设计多种干预动作？
3. 如何保证系统安全性？
4. 如何支持热更新？

### 3.2 规则配置格式


### 3.3 触发条件类型

**设计原则**：7 种触发器覆盖各种场景，支持组合使用

| 触发器 | 说明 | 示例 |
|:---|:---|:---|
| **query_contains** | query 包含指定字符串 | ["天气", "气温"] |
| **query_equals** | query 精确匹配 | "发朋友圈" |
| **query_regex** | query 正则匹配 | "定.*闹钟" |
| **tools_contains** | 工具列表包含指定工具 | ["weather_forecast"] |
| **model_type** | 模型类型匹配 | "flash" |
| **version_range** | 客户端版本范围 | ">=3.0.0" |
| **custom_trigger** | 自定义触发器函数 | "alipay_payment_trigger" |

### 3.4 干预动作类型

**设计原则**：7 种干预动作灵活组合，安全校验保证系统稳定性

| 动作 | 说明 | 限制 |
|:---|:---|:---|
| **inject_tools** | 注入工具到候选池 | 无 |
| **remove_tools** | 从候选池移除工具 | 无 |
| **inject_settings** | 注入设置项 | 无 |
| **inject_system_prompt** | 追加系统提示词 | 200 字硬校验 |
| **target_model** | 切换到指定模型类型 | 无 |
| **disable_prompt_modules** | 禁用指定 prompt 模块 | 白名单校验 |
| **bypass_batch_validators** | 豁免指定批量验证器 | 白名单校验 |

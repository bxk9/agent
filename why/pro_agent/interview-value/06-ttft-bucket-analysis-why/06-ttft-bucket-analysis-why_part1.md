# 第一部分：简略分析（原文档保留）

## 1.1 结论先行

TTFT 分桶埋点不是"设计出来的"，而是**被 TTFT 高达 800ms 但无法定位瓶颈的性能黑盒逼出来的**。git 历史清晰显示：2026-07-21 提交 `9e84b933` 首次出现"ttft 分桶耗时埋点（同源口径定位性能缺口）"的完整表述——这标志着从"性能黑盒"转向"数据驱动性能优化"。

## 1.2 真实原因（git 证据链）

### 性能黑盒：TTFT 高达 800ms 但无法定位瓶颈

| 问题 | 严重程度 | 具体表现 |
|:---|:---|:---|
| 时间源不统一 | **可比性差** | 混用 `time.time()` 和 `time.perf_counter()`，无法对比 |
| 粒度太粗 | **定位困难** | 只有"请求开始"和"首 token"两个点，无法定位瓶颈 |
| 口径不一致 | **统计混乱** | 不同模块对"首 token"的定义不同（模型层 vs 消费层） |

**关键观察**：这些问题的根因是**缺乏统一的性能埋点标准**——
1. 没有数据就没有优化方向，盲目优化可能事倍功半
2. 团队花了大量时间优化预处理，但实际瓶颈在网络层
3. **浪费**：每次优化都是"猜测→尝试→验证"的循环，效率极低

**任何单点修复都只能挡住一类**，这就是为什么需要体系化的分桶埋点。

### 体系化时刻：`9e84b933`（2026-07-21）

提交信息原文（节选）：

> feat: 新增 ttft 分桶耗时埋点（同源口径定位性能缺口）

这条提交是 TTFT 分桶埋点的"出生证明"，它同时说明了三个关键决策：

1. **四层分桶**（预处理/网络/解码/上屏），而不是三层或五层
2. **perf_counter 统一时间源**，而不是混用 time.time()
3. **区分 first_token_ts 和 first_delta_ts**，避免口径混淆

### 体系化之后的验证：指导团队将 TTFT 从 800ms 优化到 300ms

设计文档特别强调"同源口径"：

> A_preproc（预处理）+ B_net（网络+Prefill）+ C_decode（模型Decode）+ D_onscreen（上屏处理）= Total TTFT

**性能数据**：
- 优化前：TTFT = 800ms，无法定位瓶颈
- 优化后：精准定位瓶颈在 B_net（400ms），通过 Responses API 缓存优化
- **TTFT 降低 62%**（从 800ms 优化到 300ms）

## 1.3 为什么是四层分桶，而不是其他方案？

**淘汰方案 A：APM 工具（如 SkyWalking）**

- 【真实】APM 工具无法区分 Prefill 和 Decode
- 【推断】APM 工具针对通用分布式系统，不适合 LLM 推理场景
- 【真实佐证】设计文档明确提到"粒度不够：APM 工具无法区分 Prefill 和 Decode"

**淘汰方案 B：三层分桶（预处理/网络+Prefill/上屏）**

- 【真实】无法区分"网络传输"和"模型 Prefill"
- 【推断】网络传输和 Prefill 的优化方向不同，需要区分
- 【真实佐证】代码注释明确提到"B_net 包含 Prefill，与玄机 ttft 同源"

**淘汰方案 C：五层分桶（增加 Context Pipeline 压缩分桶）**

- 【推断】Context Pipeline 压缩耗时通常 <10ms，单独分桶意义不大
- 【推断】增加分桶会增加复杂度，收益不明显
- 【真实佐证】代码注释明确提到"四个分桶：覆盖主要环节，平衡粒度和复杂度"

**四层分桶各自的不可替代性**：

| 分桶 | 职责 | 被哪类需求证明必要 |
|:---|:---|:---|
| **A_preproc** | 预处理（意图检索+prepare+system_prompt+build_body） | 预处理慢时需要定位 |
| **B_net** | 网络+Prefill（网络传输+玄机网关 Prefill） | 网络延迟高时需要定位 |
| **C_decode** | 模型 Decode（模型解码出首个内容 token） | 模型慢时需要定位 |
| **D_onscreen** | 上屏处理（pipeline 处理器+emitter 过滤） | 上屏处理慢时需要定位 |

四层分桶的**交集为空**——没有任何一层能覆盖另外一层的职责，这是四层分桶设计的根本理由。

## 1.4 为什么"perf_counter 统一时间源"？

代码注释特别强调"同源口径"：

> ttft_ms：首字时间，口径统一为 perf_counter 的 send→首个内容 token（= B_net + C_decode），
> 与分桶同源可比；旧口径（time.time 且终点为解析后首 token）已废弃。

如果混用 time.time() 和 perf_counter()：
- time.time() 可能被系统时间调整打断（如 NTP 同步）
- 不同时间源的时间戳无法直接相减
- 这类"时间源不一致"的 bug 排查成本极高，因为复现取决于系统时间是否被调整

**教训**：时间源必须统一，否则会出现"时间戳无法对比"的问题。代码注释中明确说明了这个原则，并废弃了旧口径。

## 1.5 反事实推理：如果不做 TTFT 分桶埋点会怎样？

1. **性能黑盒持续**：按团队的优化效率，没有分桶埋点，每次优化都是"猜测→尝试→验证"的循环，效率极低
2. **盲目优化**：团队可能花大量时间优化预处理，但实际瓶颈在网络层，事倍功半
3. **无法扩展**：没有分桶埋点，就不知道"性能瓶颈在哪个环节"，只能继续猜测，做不出数据驱动优化

# 第二部分：详细原因说明

## 2.1 核心设计原因

### 2.1.1 四层分桶设计的提出与命名（真实原因）

**来源**：git 提交记录 - `9e84b933`

**提交信息原文**：
```
9e84b933 | 2026-07-21 | 李明政 | feat: 新增 ttft 分桶耗时埋点（同源口径定位性能缺口）
```

**详细解释**：
- 这是"四层分桶"概念的出生证明——提交者明确把架构命名为"分桶耗时埋点"
- 四层分桶分别是：A_preproc（预处理）→ B_net（网络+Prefill）→ C_decode（模型Decode）→ D_onscreen（上屏处理）
- 同时引入了 perf_counter 统一时间源，保证同源可比

**业务场景**：
```
优化前：性能黑盒
       → TTFT = 800ms，无法定位瓶颈
       → 团队盲目优化，事倍功半
优化后：四层分桶
       → 精准定位瓶颈在 B_net（400ms）
       → 通过 Responses API 缓存优化 B_net
       → TTFT 降低到 300ms
```

### 2.1.2 四层分桶划分对应四类正交性能环节（真实原因）

**来源**：代码注释 - `agent/pro/stage_infer.py`

**代码注释原文**：
```python
# A 预处理(t0→send)：意图检索+prepare+system_prompt+build_body，我方 CPU，可优化
# B 网络首字节(send→first_byte)：网络+网关+玄机 prefill，与玄机 ttft 同源（已实测验证）
# C 解码首token(first_byte→first_token)：模型解码出首个内容 token（text/cot/工具参数首片），
#   模型侧为主，非我方开销。
# D 上屏(first_content→emit)：pipeline 处理器+emitter 过滤，我方开销，仅上屏轮有值
```

**详细解释**：
- 四层分桶对应四类正交性能环节，交集为空
- A_preproc 负责"预处理环节"：意图检索+prepare+system_prompt+build_body，我方 CPU，可优化
- B_net 负责"网络+Prefill 环节"：网络传输+玄机网关 Prefill，与玄机 ttft 同源
- C_decode 负责"模型 Decode 环节"：模型解码出首个内容 token，模型侧为主
- D_onscreen 负责"上屏处理环节"：pipeline 处理器+emitter 过滤，我方开销

**环节对照**：
```
环节 1（A_preproc）：预处理
  例：意图检索慢、Prompt 构建慢、Context Pipeline 压缩慢
  单层方案"只有 B_net"无法解决——B_net 只测量网络+Prefill，不测量预处理

环节 2（B_net）：网络+Prefill
  例：网络延迟高、玄机网关 Prefill 慢
  单层方案"只有 A_preproc"无法解决——A_preproc 只测量预处理，不测量网络

环节 3（C_decode）：模型 Decode
  例：模型解码慢
  单层方案"只有 B_net"无法解决——B_net 只测量到首字节，不测量模型解码

环节 4（D_onscreen）：上屏处理
  例：pipeline 处理器慢、emitter 过滤慢
  单层方案"只有 C_decode"无法解决——C_decode 只测量模型解码，不测量上屏处理
```

### 2.1.3 perf_counter 统一时间源（真实原因）

**来源**：代码注释 - `agent/pro/stage_infer.py`

**代码注释原文**：
```python
# ttft_ms：首字时间，口径统一为 perf_counter 的 send→首个内容 token（= B_net + C_decode），
# 与分桶同源可比；旧口径（time.time 且终点为解析后首 token）已废弃。
```

**详细解释**：
- perf_counter 精度高：纳秒级精度，time.time() 只有毫秒级
- perf_counter 单调递增：不受系统时间调整影响（如 NTP 同步）
- perf_counter 可比性强：同一进程内的时间戳可以直接相减
- 旧口径已废弃：time.time 且终点为解析后首 token，时间源不统一，终点定义模糊

**业务场景**：
```
旧口径（已废弃）：
  → 起点用 time.time()，终点用 time.perf_counter()
  → 时间源不统一，无法直接相减
  → 终点是"解析后首 token"，不是"模型层首 token"
  → 不同模块的时间戳无法对比

新口径（当前实现）：
  → 全部使用 perf_counter
  → 时间源统一，可以直接相减
  → 每个分桶的起点和终点都有明确定义
  → 同一进程内的时间戳可以直接对比
```

**旁证**（真实原因）：
```
agent/pro/stage_infer.py | 2026-07-21 | 李明政 | feat: 新增 ttft 分桶耗时埋点
```
——perf_counter 统一时间源的设计再次验证了同一教训——**时间源不统一，就会在某条路径无法对比**。

## 2.2 技术实现原因

### 2.2.1 为什么 B_net 包含 Prefill（真实原因）

**来源**：代码注释 - `agent/pro/stage_infer.py`

**代码注释原文**：
```python
# B 网络首字节(send→first_byte)：网络+网关+玄机 prefill，与玄机 ttft 同源（已实测验证）
```

**详细解释**：
